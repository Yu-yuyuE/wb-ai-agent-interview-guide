### J1-01 Token 是什么？为什么中文、英文、代码消耗的 Token 不一样？
**面试官**：Token 是什么？为什么中文、英文、代码消耗的 Token 不一样？
**我（60 秒口述）**：我的结论是，Token 不是字也不是词，是模型自回归生成时一步补出来的文本碎片，由 Tokenizer 用子词算法切出来的，跟字、词都没有固定对应。为什么会不一样？BPE、Unigram 这类算法要在"按字切"和"按词切"之间取平衡——高频片段尽量整体保留，低频词继续拆小，所以英文一个词可能占好几个 Token，中文可能一词多 Token 或多字挤一个 Token，生僻字、代码片段、特殊符号更容易被切碎。经验上英文 1 Token 约 3~4 字符、中文 1~2 汉字，但同一段文本换个模型或版本序列就变，o200k_base 和 Qwen2.5 的词表规模都不一样。所以容量规划我按经验值留余量，计费和监控一律读 API 返回的 `usage`，精确计数用官方 Tokenizer 工具，绝不拿换算数字去结算。
**追问 1**：为什么同一份中文文档换个模型供应商，账单会差一截？生产里怎么提前发现这种漂移？
**答**：因为各家 Tokenizer 词表和切分不同，跨模型 Token 序列会变。GPT-3.5 中文压缩率约 1 字 1.5~2 Token，GPT-4o 换成 `o200k_base` 词表约 20 万，切法就不一样。我会在网关里把 `model_version` 和 `usage` 一起落盘，上线前用官方 Tokenizer 跑一批样本对比，别等账单出来才发现。
**追问 2**：如果业务里混了大量代码和特殊符号，或者要上多模态图片，你这套预算估算还成立吗？
**答**：不成立，得单独折算。代码缩进、花括号、生僻标识符会被切得更碎，图片 Token 按分块数和 `detail` 模式算，和文本不是一个口径。我会把图片 Token 和文本 Token 一起计入单次预算，批量图片单独压测 TTFT，纯 OCR 场景先提文字再送纯文本，别让图片把窗口和首字延迟拖垮。

### J1-02 上下文窗口是什么？上下文窗口越大，效果一定越好吗？
**面试官**：上下文窗口是什么？上下文窗口越大，效果一定越好吗？
**我（60 秒口述）**：我的结论是，上下文窗口是一次调用模型能处理的总 Token 上限，相当于"工作记忆"，标称的 128K、200K 要被 System Prompt、历史消息、RAG 片段、工具 Schema 和输出预算一起瓜分。越大越好吗？不一定。自注意力是 O(N²)，输入翻倍算力可能变四倍，TTFT 和账单一起涨；更要命的是信息放进窗口不等于被同等利用，中间那段容易"中间丢失"，窗口扩到 1M 也消不掉。所以线上要是看到输入 Token、预填充耗时、TTFT 同时抬头，我先去查检索片段数量、历史裁剪和关键信息放的位置，而不是换个更大窗口。还要记住窗口不等于最大生成长度，`max_tokens`、`max_completion_tokens`、`max_output_tokens` 各家命名不同，调之前先读能力页。
**追问 1**：你说输出也占窗口，生产里怎么定 `max_output_tokens` 才不会把业务数据挤爆？
**答**：先定输出再倒推输入，别反过来。我用 `window ≥ input_tokens + max_output_tokens` 划桶，结构化任务先锁死输出上限，再给输入留 10%~20% 安全余量。不够就按减少 RAG Top-K、合并重复片段、摘要长字段这个顺序削，一轮塞不下才拆两阶段生成。
**追问 2**：推理模型把思考过程也放进来了，这块预算怎么算？会不会重复计一次？
**答**：按目标 API 的定义单独算，不能想当然。有的 `max_output_tokens` 已经同时包含推理 Token 和可见回答，再加一次 `reasoning_tokens` 就重复，有的分别限制。我一般用返回的 `usage` 反推真实组成再校准，`reasoning_content` 本轮照样消耗生成预算，不能当成"不占窗口"。

### J1-03 什么是 Lost in the Middle 问题？长上下文场景下怎么缓解？
**面试官**：什么是 Lost in the Middle 问题？长上下文场景下怎么缓解？
**我（60 秒口述）**：我的结论是，Lost in the Middle 就是模型对上下文开头和结尾利用得好、对中间那段召回弱，所以"塞进窗口"不等于"被用上"，换 1M 窗口也不会自动解决。它和长序列建模、位置编码、训练分布都有关系，直觉上中段既离起始指令远、又不像结尾紧邻生成位置，注意力容易被稀释，但这只是通俗解释。我的缓解办法是把关键约束放 System Prompt 前面、关键证据往回答位附近靠，控制 RAG 片段数量、合并重复 chunk、把历史做裁剪或摘要，尽量别让无关材料占中段。评测上我会单独看自定义指标 Context Usage 和 Noise Sensitivity，先分清是"没召回"还是"召回了却没用上"，而不是只盯最终答案准确率。
**追问 1**：怎么验证你这些摆放调整真的有用，而不是碰巧这批问题变简单了？
**答**：得在固定 Golden Set 上做对照，不能凭感觉。我会冻结同一批问题和检索语料，只改证据位置和片段数量，看 Context Usage 和 Faithfulness 的变化。指南里那个反例很典型——退款政策已经进 Top-3，回答却只给"请联系客服"，这时候问题在上下文排序或注入方式，不在检索。
**追问 2**：如果业务必须把整本长合同一次性喂进去做全局对照，RAG 切块反而割裂了上下文，你怎么取舍？
**答**：这种场景我认可用长窗口，但要接受代价。少量文档、要跨章节全局对照、对延迟成本不敏感时，全量进窗口比切块更合适；代价是 O(N²) 带来的 TTFT 和账单，以及中段仍可能被忽略。我会用 Prompt Caching 把不变的长文档放前复用，再把关键条款在结尾复述兜底，并且单独压测，不与常规 RAG 流量混在同一条预算里。

### J1-04 Temperature、Top-P、Top-K 分别控制什么？生产环境怎么设置更稳？
**面试官**：Temperature、Top-P、Top-K 分别控制什么？生产环境怎么设置更稳？
**我（60 秒口述）**：我的结论是，三者都作用在"logits 打分 → softmax 概率 → 抽样"这条链路上，只是切的位置不同。Temperature 在 softmax 前把分数除以 T，`p(t)=softmax(z_t/T)`，T 越低分布越尖越确定；Top-k 固定保留概率最高的 k 个，Top-p 从高到低累加概率到阈值就截断，候选数随分布浮动；Penalty 是给已出现的 Token 降分防复读。生产里我不靠单调一个参数求稳——结构化抽取用 `temperature` 0~0.3 配 Strict Mode 和解析失败重试，分析报告用 0.4~0.8 加 `top_p=0.9`，创意类才放到 0.8 以上；跨供应商先按能力表过滤不支持的参数，推理模型尤其别乱套。结构稳定最终还是靠 Structured Outputs、服务端校验和失败兜底，Temperature 只是其中一环。
**追问 1**：为什么结构化任务里你把 Repetition Penalty 保留默认，不干脆开高一点防重复？
**答**：开高了会误伤。JSON 里 `"name"`、`"score"` 这种字段名本来就要反复出现，Repetition Penalty 一视同仁降分，反而容易缺字段。同理 RAG 问答开 Presence Penalty 会诱导模型引入检索材料里没有的新词，削弱对证据的忠实度；没明确调参依据我就保持默认。
**追问 2**：如果同一个 Prompt、固定 `seed`、`temperature=0`，CI 里偶尔还是解析失败，你怎么排查？
**答**：这俩是两条排查路径，别混。输出不完全一致是采样和服务端非确定性，看模型版本、跨区域部署和 `seed` 的尽力而为；解析失败是结构问题，看上下文过长、指令冲突、`finish_reason=length` 截断、工具描述模糊。我会把 `seed`、模型版本、Prompt 版本、采样参数一起存档，CI 里稳定复现的逻辑测试用 Mock，真实 LLM 调用只留冒烟测试。

### J1-05 为什么 Temperature 设置为 0，模型输出仍然可能不完全一致？
**面试官**：为什么 Temperature 设置为 0，模型输出仍然可能不完全一致？
**我（60 秒口述）**：我的结论是，`temperature=0` 走贪婪解码，只保证"同一次采样"选最高分是确定的，但模型本身和服务端都不承诺逐字复现。原因有四类：底层模型版本更新权重变了、跨区域调用可能落到不同集群版本、服务端解码实现变化、并行计算和后端配置变化；`seed` 也只是"尽力而为的可复现"，DeepSeek 当前 API 甚至没公开 `seed`。所以我不把它当稳定手段，更不会当成 Schema 和服务端校验的替代品。要复现实验，我把 `seed`、固定模型版本、固定 Prompt、固定采样参数一起保存，CI/CD 里把真实 LLM 调用留给冒烟测试、需要确定性的逻辑测试用 Mock，并且接受供应商服务仍可能带来小幅非确定。
**追问 1**：跨厂商时你都按低温调，有没有反例？
**答**：有，Gemini 3 系列就是。官方建议保持默认 `temperature=1.0`，硬往下调反而可能触发循环或推理退化。所以我的习惯是先看目标模型文档再定参数，不把"低温=稳"当成跨厂商通用规则，结构稳定还是交给 Structured Outputs 加服务端校验。
**追问 2**：生产里到底怎么区分"输出不完全一致"和"结构化解析失败"这两种线上报警？
**答**：看报警挂在哪个环节和哪个字段。前者是内容层，同一 `requestId` 两次结果文本不同但都能解析；后者是契约层，`JSON.parse()` 或 Schema 校验直接报错，日志里 `error_type` 或 `finish_reason=length` 会有痕迹。我会在网关把两类计数分开，解析失败进有限重试和降级，内容漂移只做采样观测，别用同一套重试策略处理。

### J1-06 大模型为什么会产生幻觉？常见缓解方案有哪些？
**面试官**：大模型为什么会产生幻觉？常见缓解方案有哪些？
**我（60 秒口述）**：我的结论是，根子在自回归——模型按概率"补"下一个 Token，任务边界不清时就会偏题或补出不存在的信息，检索证据能收窄范围但消不干净。所以我不信"上了 RAG 就没幻觉""用了 Structured Outputs 就不用校验"这套话，检索错、上下文噪声、引用错配、模型不遵循指令照样出错。我的组合拳是：用 JSON Schema 把输出变成可校验契约，RAG 侧控制片段数量、做引用校验和拒答，工具超时后绝不让模型基于空结果编答案；评测侧把 Faithfulness、幻觉率、引证支持率单独设门禁，高风险条件不能被平均分抵消——退款结果错了，语气再好、再完整，这条任务我也判失败。Prompt 本身则把 Role、Task、Context、Format 四要素交代清楚，比堆修饰词管用。
**追问 1**：你说评测里高风险不能被平均分抵消，生产里具体怎么落地这条门禁？
**答**：把关键失败样本单独打标、单独看通过率，不并入总分。合规漏识别风险条款、医疗错误用药建议，占比再低也足以暂停发布；我给这类用例设高权重或一票否决，让它和大量正常样本分开统计，而不是算进一个平均 Faithfulness 里被稀释掉。
**追问 2**：工具超时返回空，模型却补了一句"已为您退款"，这种 Badcase 怎么从根上堵？
**答**：靠执行层的短路和契约，不是靠 Prompt 求它别编。工具失败返回明确错误码，我在编排层直接短路到"当前无法完成"，不让模型看到空结果继续生成；输出 Schema 里给 `NEED_MORE_INFO`、`Unknown`、`need_human_review` 这样的枚举，让"不确定"有合法出口，模型就不必靠编造把字段填满。

### J1-07 Token 预算怎么估算？输入、输出、历史消息、RAG 证据如何取舍？
**面试官**：Token 预算怎么估算？输入、输出、历史消息、RAG 证据如何取舍？
**我（60 秒口述）**：我的结论是，把上下文窗口当固定容量的桶，先满足 `window ≥ input_tokens + max_output_tokens`，结构化任务先定 `max_output_tokens` 再给输入留 10%~20% 余量。输入侧至少算 system prompt（含 schema 和工具定义）、变量替换后的 user prompt、历史消息、RAG context，输出 Token 也占窗口；16K 窗口的典型分配大概是 System 1500、User 6000、历史 2000、安全边际 1500、输出预留 5000，但那只是示意。不够时我按固定顺序削：先降 RAG Top-K、合并重复片段、摘要或截断长字段，一轮塞不下才拆分批评估或两阶段生成。Prompt Caching 我会把不变的 System Prompt、工具定义、RAG Context 放前面，变化的 User Prompt 放后面，再按响应里的缓存读取/写入 Token 验证命中率，不把缓存时长和折扣写死在业务代码里。
**追问 1**：输出单价比输入贵，成本估算上你怎么避免拍脑袋？
**答**：不套那套"2~4 倍"的行业比例，价格表更新太频繁。成本核算我读供应商当前价格页，在网关保存 `model_version`、各类 `usage`（输入/缓存输入/输出/reasoning tokens 分开）和实际账单单价；推理 Token 经常计在输出侧容易漏算，我拿 `usage` 反推真实组成再校准。
**追问 2**：推理模型的 `reasoning_tokens` 你到底加不加进预算？会不会重复计？
**答**：看 API 定义，不能一律加。有的 `max_output_tokens` 已同时包含推理 Token 和可见回答，再加一次就重复，另一些分别限制思考过程和最终回答。我会先用一批样本打 `usage` 看返回里到底怎么拆，再决定公式，而不是照搬某个厂商的字段名。

### J1-08 长上下文窗口会不会取代 RAG？二者分别适合什么场景？
**面试官**：长上下文窗口会不会取代 RAG？二者分别适合什么场景？
**我（60 秒口述）**：我的结论是，不会互相取代，它俩管的不是一件事——长窗口只提高"单次能装多少信息"，RAG 负责"从大规模、动态的知识源里挑出该放进来的那一小部分"。全量塞窗口的代价很直接：输入 Token 随内容涨、账单涨、预填充和 TTFT 变长，自注意力 O(N²)，攻击面也更大，而且片段太多反而抓不住真正相关的证据；RAG 是检索后只把相关 chunk 拼进去，还能按用户、租户、角色做权限过滤和引用溯源。我一般先用 Hybrid Search、Reranker 把检索片段数量和排序控好，再决定要不要长窗口。长窗口更适合少量文档、要跨文档全局对照、对延迟成本不敏感的一次性分析，RAG 适合知识库大、频繁更新、要权限和溯源的场景，二者常常先检索再放进长窗口组合用。
**追问 1**：这套取舍你在评测上怎么证明选对了，而不是只看答案顺不顺？
**答**：分检索和生成两张账看。检索侧盯 Recall@K、Context Precision、Context Recall，生成侧盯 Faithfulness、Context Usage、Noise Sensitivity；我会保留固定快照回归冻结语料和索引，再挂一条实时能力探针访问当前 API，两条轨道分数不混成一个总分，实时探针单独掉就先查外部数据和工具协议。
**追问 2**：如果知识库要全量重建索引、升级 Embedding 模型，怎么切才不把线上评测和回答搞乱？
**答**：索引和查询必须用同一套 Embedding 模型及版本，升级就建新索引、用同批评测数据对比后再切别名。旧索引保留一段时间可回滚，固定快照回归继续用冻结语料，这样分数变化能归因到改动本身而不是索引悄悄换了；多模态图片进 RAG 时我还会把图片 Token 和文本 Token 一起计入单次预算单独压测。

### J1-09 大模型 API 调用的完整链路是什么？
**面试官**：大模型 API 调用的完整链路是什么？
**我（60 秒口述）**：我的结论是，一次调用不能只封装成一个 HTTP 请求，我会按"业务请求进入 → 上下文组装 → Token 预算预估 → 模型网关路由 → 供应商 API 调用 → 响应解析 → 状态回写 → 观测与告警"八段来治理。请求要跨业务系统、上下文系统、网关、外部供应商和前端，哪一段缺状态和错误处理，最后都表现成"模型不稳定"；入口先校验身份、租户、权限和请求大小，网关里收口 API Key、超时、重试、限流、日志和供应商切换。我的落地判断是业务模块不直接调供应商 SDK，统一走 `LLMGateway`，结构化解析放在落库之前做，同步和流式分开处理；幂等 claim 必须落到 Redis `SET NX` 或数据库唯一约束，不能用"先查再写"代替。
**追问 1**：为什么你强调 claim 必须是原子的，生产里出过什么问题？
**答**："先查询、再写入"在并发下会漏，两个重试同时查到"没做过"就都去调模型、都落库。我踩过的坑就是网关超时自动重试，第一次其实已成功落库，第二次又写一条重复消息。所以 claim 用 `SET NX` 或带条件原子更新，幂等键还要绑 `requestFingerprint`，同一个键对应不同请求直接返回冲突，别把历史结果串给新请求。
**追问 2**：上线前你会拿哪几条失败链路当发布门禁？
**答**：四条——客户端取消能否传到供应商、可重试错误是否受总截止时间和原子幂等记录约束、RPM/TPM/并发与租户预算是否同时生效、结构化解析失败是否进入明确失败状态。这几条不过我不放量，因为它们分别对应"白烧 Token""重复落库""被限流打穿"和"半截 JSON 进下游"这四类最难查的线上问题。

### J1-10 Streaming 为什么能改善用户体验？它能减少总耗时和 Token 成本吗？
**面试官**：Streaming 为什么能改善用户体验？它能减少总耗时和 Token 成本吗？
**我（60 秒口述）**：我的结论是，Streaming 改善的是首字等待时间 TTFT，从"等完整答案"变成"等第一个片段"，但它不减少总生成 Token，也不保证端到端总耗时变短，更不天然省钱。同步返回要等模型把 800 个 Token 全生成完才一次性给，流式第一个 delta 出来就能展示，用户体感像聊天逐字出现；可模型该算的 Token 一个没少，计费照旧，还照样受限流和配额影响。所以面向用户展示的长文本我优先流式，后台批处理和必须拿到完整对象才提交的任务用同步；流式下取消、超时、断流、重连是四种不同状态，半成品 JSON 也不能边收边 `JSON.parse()`。尤其用户点取消时，后端要同时取消供应商请求、响应流解析、后续 TTS/工具调用/落库和未提交的增量缓存，不能只在前端停展示，否则前端停了 Token 还在烧。
**追问 1**：流式结构化返回你怎么处理，才不会把半截 JSON 交给下游？
**答**：增量阶段只展示文本或记片段，等收到正常结束事件再拼成完整内容做 Schema 校验。我不会一边收 delta 一边 `JSON.parse()`，供应商有结构化流式事件或 SDK accumulator 就用官方的，否则自维护 buffer、`sequence` 和结束状态；`finish_reason=length` 被截断的样本直接标记失败，不进下游。
**追问 2**：有人说流式省了用户等待就等于省了成本，你怎么反驳并度量？
**答**：体感指标和成本指标要分开看。TTFT 降了是体验，E2E Latency 通常仍取决于完整生成时间，`usage` 里的输出 Token 也没变。我会在日志里同时记 TTFT、总耗时、Input/Output Tokens 和 Cancel Rate，用数据说明流式没降账单，反而因为用户更容易中途取消，得额外盯 Cancel Rate 判断是不是响应太慢或生成太长。

### J1-11 SSE、WebSocket、HTTP Chunked 在流式输出场景下怎么选？
**面试官**：SSE、WebSocket、HTTP Chunked 在流式输出场景下怎么选？
**我（60 秒口述）**：我的结论是，单向文本增量我默认选 SSE，双向实时交互才上 WebSocket，HTTP Chunked 只是传输机制不是应用事件协议。SSE 是浏览器原生 `EventSource`、服务端单向推 `text/event-stream`，最省事；WebSocket 是双向长连接，适合语音、插话、多人协作，但鉴权、心跳、连接管理都得自己管；Chunked 是 HTTP/1.1 分块传输，偏后端到后端代理，业务层还得自定义事件。SSE 里空行 `\n\n` 才是事件分隔符，手写 `data:` 不给每行加前缀会丢内容，Markdown 列表和代码块特别容易踩，所以我用 `ServerSentEvent` 构造器别手拼串，前面挂 Nginx 一定配 `proxy_buffering off`，否则被攒成一整块，TTFT 体感又回到同步。
**追问 1**：SSE 的 `EventSource` 自动重连，生产里能真正做到断线续传吗？怎么验证？
**答**：大多数情况不能，重连不等于无缝续写。供应商侧流往往已经断了，没法从 Token 级别续上；我的做法是每个响应生成 `messageId` 加递增 `sequence`、已发片段写短期缓存，前端重连先补发缓存片段，供应商流已结束就提示"重新生成"而不是假装接上。验证要专门造断流用例，测 LF、CRLF、空行、代码块和"半个事件"这些边界。
**追问 2**：超时你怎么分层？如果 TTFT 正常但用户投诉后半段卡住，是哪一层？
**答**：连接超时、TTFT 超时、总时长超时三者分开记录。TTFT 超时通常指向模型排队、上下文过长或供应商抖动；TTFT 正常而后半段卡，更像总时长问题——用户让模型写太长、或生成中途被限流，我会看总时长超时和 `finish_reason`，而不是去调 TTFT 的参数。断流没正常结束标记就标 `INTERRUPTED`，前端显示"已中断，可重新生成"。

### J1-12 哪些大模型 API 错误可以重试？哪些错误不能重试？
**面试官**：哪些大模型 API 错误可以重试？哪些错误不能重试？
**我（60 秒口述）**：我的结论是，大模型重试的特殊点在"请求贵"和"输出非确定"——失败请求也可能消耗配额甚至部分 Token，同一 Prompt 第二次返回还可能不一样，所以必须按错误码严格分三类。网络瞬断、5xx（500/502/503/504）、过载 529 和 429 限流可以或谨慎重试；400 参数错误、401/403 鉴权、安全拒答不能重试同一 payload；解析失败只做 1-2 次带具体错误的格式修复。可重试的用指数退避加抖动，`sleep = min(maxDelay, baseDelay * 2^retryCount) + random(0, jitter)`，最多 2-3 次、总截止时间按用户 SLA 卡住比如 15 秒，到点就失败；429 先读 `Retry-After` 和限流头，别一上来疯狂重试把刚恢复的系统再打进限流。
**追问 1**：为什么抖动是必须的，出过什么问题？
**答**：没有抖动，所有客户端会在同一时刻一起重试，把刚恢复的供应商再次打挂，这就是原文那个"越重试越被限流"的反面教材。我给等待时间加随机量错开峰，再叠最大次数和总截止时间兜底；另外失败请求也计入每分钟限制，重试本身就在消耗 RPM 配额，不能无限试。
**追问 2**：流式中断算可重试吗？用户可见任务和后台任务你怎么区别对待？
**答**：视场景，用户可见任务不自动重试——体验差又浪费，前端展示"已中断，可重新生成"更合适；后台批处理任务才走幂等重试。我会用 `INTERRUPTED` 状态加幂等 Key 判断能不能重放，重试前确认 `attempt` 挂在同一业务消息下、只允许一个 `final`，避免重复落库。

### J1-13 为什么大模型调用必须做幂等？
**面试官**：为什么大模型调用必须做幂等？
**我（60 秒口述）**：我的结论是，只要有重试就得谈幂等，尤其涉及落库、扣费、发通知或工具写操作时，必须防止同一业务请求被执行多次；纯文本生成虽不一定要求业务幂等，但重试仍会产生重复费用和多份候选结果。两个高频坑是用户狂点"重新发送"创建多个模型调用，以及网关超时自动重试、第一次其实已成功落库、第二次又写一条重复消息。我的做法是幂等 Key 由业务生成，比如 `tenantId:userId:conversationId:messageId:attemptGroup`，服务端先查 Key——已成功直接返回历史结果，正在生成返回同一个流式任务订阅地址，失败可重试就新建 attempt 但挂在同一业务消息下；再把 `message_id`、`attempt_id`、`provider_request_id`、`stream_sequence` 四层 ID 分开，落库只允许一个 attempt 成为 `final`。
**追问 1**：幂等键为什么还要绑定请求指纹？生产里怎么落地这一层？
**答**：光有键不够，同一个键对应了不同请求内容，直接返回历史结果就是串数据。我让键绑定 `requestFingerprint`，发现同键不同指纹就返回冲突而不是旧结果；claim 落到 Redis `SET NX` 或数据库唯一约束，绝不用"先查询再写入"代替原子操作。
**追问 2**：工具调用链路上幂等键该由谁生成？模型给的能信吗？
**答**：必须由可信执行层生成，不能接收模型提供的键。模型参数属于不可信输入，我会根据业务请求 ID、动作和资源生成 `actionId` 作为幂等键，数据库唯一约束兜底，外部支付/退款接口携带相同幂等号，同一请求再次到达直接返回已有结果；如果一个工具本身不能安全重试，我就不该把它开放给 Agent 随意调用。

### J1-14 大模型限流为什么不能只按 QPS 做？
**面试官**：大模型限流为什么不能只按 QPS 做？
**我（60 秒口述）**：我的结论是，因为大模型 API 的成本和压力主要由 Token 决定，一次"请求"之间的消耗可能差几个数量级，按 QPS 限流等于没管住真正花钱的地方。原文那个对比很直观——请求 A 输入 500 Token 输出 100，请求 B 输入 80K 输出 8K，都是 1 次请求，对推理、配额和账单完全不是一个量级；所以至少要同时看 RPM、TPM、并发数、上下文大小、`max_tokens` 和日/月预算。请求进网关我先估算 `input_tokens + reserved_output_tokens`，在用户、租户、模型、供应商几个桶里扣减，扣不到就排队、降级或拒绝，别等 429 才管。生产里用户级用滑动窗口加日 Token 上限，模型级令牌桶加并发信号量，供应商级全局令牌桶加熔断器，具体数值从响应头和配置中心动态读，不写死。
**追问 1**：收到供应商 429 才开始限流，暴露了什么问题？你怎么改？
**答**：说明应用侧缺自己的容量管理，429 只能当外部保护信号。我会在发请求前就扣桶，收到 429 后按五步走：读 `Retry-After` 或限流头、标记是请求数/Token/日配额哪个维度打满、短请求进延迟队列、用户交互请求少重试或切轻量模型、连续 429 就熔断该供应商，别让所有请求继续撞墙。
**追问 2**：降级到轻量模型会不会偷偷把答案质量拉低？成本这边怎么权衡？
**答**：会，所以降级不能悄悄做。若轻量模型影响答案质量，我在业务层明确标记"当前为快速模式，复杂问题建议稍后重试"；降级链路是优先模型 429 切备用同级、备用也限流再切轻量并缩短输出、仍不可用时排队或返回"当前请求繁忙"。成本上我盯 `usage` 和 429 Rate，确认限流桶和配额是否合理，而不是靠压低输出上限硬省钱。

### J1-15 模型网关通常要承担哪些能力？
**面试官**：模型网关通常要承担哪些能力？
**我（60 秒口述）**：我的结论是，`LLMGateway` 是应用层和供应商之间的统一治理入口，把 API Key、超时、重试、限流、日志、供应商切换和模型选择收口，避免每个业务模块长出略有差异的失败语义。除了普通 API 的鉴权、限流、转发，它还要管模型选择、Token 预算、上下文长度、供应商差异、流式输出、工具调用、结构化响应、成本统计和 Prompt 版本；八阶段链路里的路由、预算扣减、幂等、响应解析与校验、状态回写、观测告警都落在它身上。真实项目我还会补 API Key 池和供应商路由、模型优先级与降级、Prompt 版本号、响应内容安全审查、`usage` 成本计算、traceId 与 providerRequestId 对齐、流式取消信号向供应商传播和 SSE 出站契约；成本核算在网关保存 `model_version`、各类 `usage` 和实际账单单价，不让静态数字散落在业务代码里。
**追问 1**：网关前面挂了 Nginx，为什么流式会失效？生产怎么验证？
**答**：缓冲型网关默认会攒够一整块才下发，`text/event-stream` 被攒住，TTFT 体感就退回同步接口了。我会把 `proxy_buffering off`、`proxy_cache off`、`proxy_read_timeout` 调大、`proxy_set_header Connection ""` 配好，再用一个逐字输出的用例实测首字到达时间，确认没被缓冲，而不是只看接口返回 200。
**追问 2**：如果供应商静默升级了底层模型版本，网关怎么帮你定位回归？
**答**：靠版本和 `usage` 全量落盘。我在网关里把 `model_version`、`prompt_version`、traceId/providerRequestId 和每次调用的输入输出 Token 一起记，线上一旦指标漂移，就能按版本切片对比，判断是供应商静默升级还是自己的 Prompt 改动；这也是为什么我把真实 LLM 调用和冒烟测试、Mock 逻辑测试分开，方便隔离变量。

### J1-16 AI 应用的调用日志里至少要记录哪些字段？
**面试官**：AI 应用的调用日志里至少要记录哪些字段？
**我（60 秒口述）**：我的结论是，只记"成功/失败"肯定不够，日志得能串起 `messageId`、`attemptId`、`providerRequestId`，并保存 TTFT、总耗时、usage、结束原因和解析结果。原文那句话我特别认同——用户说"刚才 AI 没返回"，没有这些字段，你连是哪家供应商、哪个模型、哪次 attempt、有没有收到第一个 delta 都查不到。我至少记 trace_id、tenant_id、user_id、conversation_id、message_id、attempt_id、model、provider、prompt_version、input_tokens、output_tokens、ttft_ms、latency_ms、retry_count、finish_reason、error_type、provider_request_id 这一组；配套看 TTFT、E2E Latency、Retry Count、429 Rate、Parse Failure Rate、Cancel Rate、Provider Error Rate 这些指标。字段不是堆得越多越好，我的取舍是看它能不能回答"哪次调用、卡在哪一段、花了多少钱"，并用 `requestId` 和 `runId` 把 Trace、Metrics 和审计记录串起来，而不是塞进一张大表。边界上审计日志字段要白名单化，敏感明文禁止进普通日志。
**追问 1**：`finish_reason` 和 `error_type` 为什么被你单独拎出来，生产里救过什么场？
**答**：它们是定位断流和截断的关键。`finish_reason=length` 说明输出被截断了，半截 JSON 直接进下游会引发解析失败；`error_type` 能区分是供应商 5xx、限流还是本地校验挂了。我就靠这两个字段把"AI 没返回"拆成"根本没生成完"和"生成完但被我们拒了"两类，排查路径完全不同。
**追问 2**：日志里要记用户问题和检索正文，合规上怎么不踩坑？
**答**：按字段白名单和脱敏分层。工具名、校验结论、结果码、耗时、模型版本、Schema 版本、traceId 可直接记；订单号/userId 这类标识符做掩码、哈希或令牌化，密码、令牌、支付数据、私钥和原始文档正文禁止进普通日志，确需保留写单独受控审计存储。日志内容本身也是不可信输入，展示导出要防日志注入，还得限制谁能按 traceId 反查用户请求。

### J1-17 为什么只写“请返回 JSON”不可靠？
**面试官**：为什么只写“请返回 JSON”不可靠？
**我（60 秒口述）**：我的结论是，这只是自然语言约束，不是工程契约——Prompt 能表达意图，但替代不了 Schema、校验器、重试机制和权限控制。原文列了五类失守，我印象最深的是类型错误：`{"orderId":"1029384756","needManualReview":"false","confidence":"0.87"}` 语法完全合法，字段类型却全错，反序列化层要悄悄做了类型转换，上游问题就被盖住了；还有格式漂移（前面加"以下是分类结果："）、字段缺失、额外解释文本、边界条件崩溃，信息模糊或带攻击性输入时模型更容易跑偏。我的做法是 JSON Schema 加原生 Structured Outputs 加服务端校验、失败重试和降级一起上，工单分类里把 `category`、`priority` 用枚举锁死、`confidence` 限制 0~1、信息不足时返回 `NEED_MORE_INFO`，而不是继续猜。
**追问 1**：你说"能展示给用户不代表能被程序执行"，生产里这条边界怎么守？
**答**：解析失败绝不把原始自然语言硬塞给下游系统。我会让结构化返回失败进明确的失败状态——带校验错误让模型只修格式（最多 1-2 次），仍失败就按场景降级，比如工单分类进人工队列标 `AI_PARSE_FAILED`、订单参数缺失就追问用户补订单号；能展示的模型文本和能入库的结构对象走两条路。
**追问 2**：如果输入里夹了"别返回 JSON，直接告诉我怎么赔"这种注入，你怎么防？
**答**：不靠一句"必须返回 JSON"硬扛，那是上下文优先级问题。我把格式约束放在 System Prompt、用 `additionalProperties: false` 和 Strict Mode 收紧，工具权限单独在服务端校验；真被绕过去就走拒答/降级流程，输入端也按对抗样本进 Golden Set 常测，别等线上才第一次遇到。

### J1-18 JSON Mode 和 Structured Outputs 有什么区别？
**面试官**：JSON Mode 和 Structured Outputs 有什么区别？
**我（60 秒口述）**：我的结论是，两者不在同一层——JSON Mode 只保证"输出是合法 JSON 语法"，Structured Outputs 配合 JSON Schema 在生成阶段就应用契约，约束字段、类型、枚举和必填项，但都不负责工具执行，服务端仍要校验。三层拆开看更清楚：JSON Mode 是输出模式开关，JSON Schema 是结构描述规范，Structured Outputs 是供应商提供的结构化生成能力；前者能解决"好的，以下是结果：{...}"，解决不了 `{"category":"pay","priority":"urgent","confidence":"very high"}` 这种合法 JSON 却非法业务数据。OpenAI 用 `strict`、Gemini 用 `response_format`、Anthropic 有 Structured Outputs 和 Strict tool use，三家支持的 Schema 子集、拒答和截断语义、`pattern`、`$ref`、`allOf` 这些关键字支持度都不同。我先读 supported schemas 写兼容层，落点分响应结构化和工具参数结构化两类，别照搬完整规范。
**追问 1**：模型返回拒答或达到 Token 上限时，Structured Outputs 还算成功吗？
**答**：不算，支持能力不等于业务请求成功。拒答、`finish_reason=length` 截断、工具执行失败这几种情况，输出都可能不是你想要的合规对象；我会把"结构化能力可用"和"这次调用业务成功"分开记，解析失败率单独监控，截断样本直接标失败不进下游。
**追问 2**：跨三家供应商你怎么保证 Schema 不用改三遍？
**答**：先定一份业务 Schema 当契约，再按各厂商支持子集做适配层，而不是给每家写一套。我把 `strict`、`response_format` 这些差异收在网关的兼容层里，用 `schemaVersion`（比如 `ticket_classification_v1`）统一版本边界；新增枚举或字段先确认旧消费者能识别，发布前用同一批样本跨模型跑一遍通过率。

### J1-19 JSON Schema 在大模型应用里解决什么问题？
**面试官**：JSON Schema 在大模型应用里解决什么问题？
**我（60 秒口述）**：我的结论是，它把"输出应该长什么样"变成一份可校验的数据契约，既给模型提供结构化约束，也给服务端做兜底校验，但本身不负责生成、更不负责外部调用。`properties` 定义有哪些字段、`required` 声明必填、`enum` 把取值锁在固定集合、`additionalProperties: false` 挡掉多余字段，再加 `type`、`minimum`/`maximum`、`pattern`、`const` 这些关键字。我设计时有几条硬规矩：一个字段只表达一件事（别把"支付问题，高优先级"塞进一个 `result`，拆成 `category`/`priority`/`needManualReview`/`reason`），枚举优先于自由文本（`"urgent"` 到底算不算 `HIGH`，模糊映射等于把模型不确定性扩散进业务规则），字段说明写清"何时用、何时不用"。落地时带 `schemaVersion`、校验失败把具体错误回给模型只修结构、字段不存在用 `null` 或 `NEED_MORE_INFO` 表达，而不是让模型编一个值填满。
**追问 1**：为什么你说"字段不存在 ≠ 未知"，生产里怎么落？
**答**：缺字段是协议异常，得让校验器报错，而不是当成"模型不确定"。我会在 Schema 里把该在的字段都列进 `required`，信息不足时用明确枚举 `NEED_MORE_INFO` 或 `"refundId": null` 这类合法值表达未知；否则模型为了凑齐必填会瞎编一个订单号，反而把错误藏进合法结构里。
**追问 2**：Schema 越复杂越保险吗？多消费者版本怎么不乱？
**答**：恰恰相反，太复杂会增加模型理解成本和供应商兼容成本，递归 `$ref`、`allOf`/`oneOf` 各家支持还不一致。我控制复杂度，用 `schemaVersion` 区分版本——新增字段尽量可选、删除字段先灰度、新增枚举先确认旧消费者识别；Prompt、Schema、解析代码和看板指标用同一版本边界，跨版本对比才不失真。

### J1-20 Function Calling 的完整链路是什么？
**面试官**：Function Calling 的完整链路是什么？
**我（60 秒口述）**：我的结论是，模型只生成"调用哪个工具、参数是什么"的结构化意图，真正执行工具的是业务服务、Agent Runtime 或 MCP Host，执行权始终在业务侧——"模型执行了你的 Java 方法"是新人最常犯的误解。七步链路是注册工具定义（工具名、描述、参数 Schema）→ 用户发起请求 → 模型选 `query_order` 并生成 `{"orderId":"1029384756"}` → 业务侧校验参数 → 业务侧执行工具 → 结果连同 `tool_use_id` 回填模型 → 模型生成最终回答；它的价值是弥合"自然语言意图 → 结构化参数"的语义鸿沟，用户说"昨天买的咖啡机没发货"，后端要的是 `userId`、`orderId`、`includeLogistics`。我用 `ToolCallDispatcher` 先按工具名分发、未知工具直接拒 `UNSUPPORTED_TOOL`，再做 JSON Schema 校验、权限校验、执行、全链路 `AuditEvent`，并行调用时 `callId` 必须原样带回，否则结果错配。
**追问 1**：如果把模型输出的参数直接传给订单服务，会出什么事？
**答**：等于把业务系统入口暴露给一个概率模型。Schema 只能知道 `orderId` 是个字符串，不知道订单是不是当前用户的、是否已退款、用户有没有客服权限；所以结构校验之后必须叠业务校验（归属、状态流转、金额范围）和权限校验（身份、角色、租户、数据范围），这三层都在服务端，不能藏在 Prompt 里。
**追问 2**：并行调多个工具时，结果回填最容易出什么 Badcase，怎么防？
**答**：最容易 ID 错配——两个调用返回顺序乱了，结果贴到对方头上。我要求每个 `functionCall` 的唯一 `id` 回填时原样带回，Anthropic 的 `tool_use_id` 严格匹配；派发层按 `callId` 路由结果，缺 ID 或未知工具直接进明确错误，不猜哪个结果对应哪次调用。

### J1-21 Function Calling 和 MCP 有什么区别？
**面试官**：Function Calling 和 MCP 有什么区别？
**我（60 秒口述）**：我的结论是，Function Calling 是模型侧"自然语言 → 工具名和参数"的调用意图生成机制，MCP 是应用层协议，负责工具如何被标准化发现、描述、调用和返回结果，两者不在一层。Function Calling 是供应商侧能力，各家请求响应格式不一样；MCP Tool 是协议里的工具能力，Server 暴露"名称 + 描述 Schema 的元数据"，Client/Server 之间走 JSON-RPC 2.0，调用动作是 `tools/call`。一个支持 MCP 的 Runtime 可以先通过 MCP 发现工具，再把工具定义转成某个供应商的 Function Calling 格式给模型，模型选完工具后 Runtime 再转成 `tools/call`——但这只是常见适配方式，不是协议前提。我按"结果会不会触发外部动作、工具要在多少个客户端复用"选型，工具多、客户端多、想跨 IDE 或跨 Agent 复用才考虑 MCP。
**追问 1**：MCP Client 一定要经过模型才能发起 `tools/call` 吗？
**答**：不一定，这是原文特意澄清的。MCP Client 可以由规则引擎、用户界面或其他程序直接发起 `tools/call`，MCP Server 也能直接访问 HTTP API、数据库、本地文件或进程，底层不要求再过一遍 Function Calling。把这些概念排成固定层级是错的，它们可以按需组合。
**追问 2**：如果团队已经有成熟 HTTP API，引入 MCP 的代价是什么，值不值？
**答**：代价是多一层协议和 Host 治理，收益是接入标准化。值不值看复用面——只有一两个 Agent、工具就几个，直接 Function Calling 包 HTTP API 更轻；工具很多、要跨多个客户端和团队共享时，MCP 把发现、描述、调用统一掉才划算。我会先数客户端数量和工具数量，再决定要不要上这层。

### J1-22 MCP Tool 和普通 HTTP API 有什么关系？
**面试官**：MCP Tool 和普通 HTTP API 有什么关系？
**我（60 秒口述）**：我的结论是，HTTP API 是面向程序调用的确定性业务接口，MCP Tool 是暴露给 AI Host 的标准化工具能力，内部可以再调 HTTP API、数据库或本地脚本——MCP 解决接入标准化，HTTP API 解决具体业务能力。比如普通接口是 `GET /api/orders/O202605070001`，Function Calling 输出 `{"name":"query_order","arguments":{"orderId":"...","includeLogistics":true}}`，两者之间需要一个工具执行层做映射："模型调用意图 → 服务端校验参数 → 调 HTTP API"。所以"Function Calling 可以包一层 HTTP API，但 HTTP API 本身不是 Function Calling"，MCP 消息是 JSON-RPC 2.0，也不直接规定模型输出。我不会把 MCP 理解成"新的 HTTP"或"替代 Function Calling"，权限、参数校验和业务状态仍落在执行层，MCP 只管把工具稳稳接进来。
**追问 1**：生产里这个映射层最该守住什么？出过什么问题？
**答**：最该守住的是"校验在映射层、不在模型侧"。我见过把模型参数直接拼进 URL 去查订单，结果越权读到别人数据；正确做法是执行层先做结构/业务/权限三层校验，再调 `GET /api/orders/{orderId}`，未知工具直接 `UNSUPPORTED_TOOL`，错误码 `INVALID_ARGUMENTS`、`FORBIDDEN`、`ORDER_NOT_FOUND` 分清楚。
**追问 2**：MCP Server 直接读数据库、不走 HTTP API，算不算违规设计？
**答**：不算，这正是规范允许的。MCP Server 可以访问 HTTP API、数据库、本地文件或进程，不要求底层再经过 Function Calling 或 HTTP API；我选哪种取决于复用和治理边界——只读、需要统一权限和审计时走现有 HTTP 服务更稳，内部脚本类能力让 Server 直连反而简单，关键是别把敏感库账号散落在多个 Host 里。

### J1-23 Agent Skill 和 Function Calling 是一回事吗？
**面试官**：Agent Skill 和 Function Calling 是一回事吗？
**我（60 秒口述）**：我的结论是，不是。Skill 保存可复用的任务说明和执行 SOP（注入上下文、约束步骤、编排流程），Function Calling 只负责生成工具名和参数，一个 Skill 可以指导 Agent 调多个工具、也可以完全不调工具。原文那个"线上事故复盘 Skill"很典型——先读事故时间线、再查监控截图、再拉发布记录、最后按"现象、影响、根因、改进项"输出，执行中可能调 MCP 工具、可能调 Function Calling 工具，也可能纯文本分析。"Skill 是 Function Calling 的语法糖"是错误命题，组件怎么组取决于 Runtime，不存在必须经过的固定链路。复杂任务有固定 SOP 时我才沉淀成 Skill，并且单独评四类用例——触发、核心逻辑、产物质量、异常容错，盯触发召回率、误触发率和异常稳态率。
**追问 1**：Skill 怎么评？为什么说触发用例单独算一类？
**答**：因为 Skill 第一道关是"该不该启动"。用户只是闲聊却启动了退款 Skill，后面逻辑再对也是事故；所以我把触发用例（该触发/不该误触发）和核心逻辑、产物质量、异常容错分开测，用触发召回率、误触发率量化，而不是只看最终产物合格率。
**追问 2**：如果 Skill 里要调工具，和直接写 Function Calling 比，代价在哪？
**答**：代价是多一层上下文注入和流程约束，Token 和延迟都会涨，也更容易出现"过早进入实现"这类问题。像 `grilling` 需求澄清 Skill，我会专门检查它有没有追问关键分支、有没有把模糊需求收敛成可执行计划再动手；简单单步任务用 Function Calling 更直接，别为了"有方法论"硬套 Skill。

### J1-24 结构化输出失败后怎么处理？
**面试官**：结构化输出失败后怎么处理？
**我（60 秒口述）**：我的结论是，原则是"可以降级，但不能让模型编造业务事实"——先本地校验拿到具体错误，再带错误让模型只修格式做有限重试，仍失败就按场景降级。失败不一定是供应商能力问题，可能是 Schema 太复杂、上下文冲突、`finish_reason=length` 截断、误触 Stop Sequences 或安全拒答；四级兜底是本地校验（JSON Schema、Jackson、Bean Validation）→ 轻量修复（只修格式不重生成内容）→ 降级 Schema（复杂对象拆小、先分类再抽字段）→ 人工或规则兜底。我绝不一失败就把原始问题重跑一遍，而是把 `$.priority: must be one of LOW, MEDIUM, HIGH`、`$.confidence: must be number` 这类具体错误连原输出回给模型，最多重试 1-2 次。降级按场景分——工单分类进人工队列标 `AI_PARSE_FAILED`、订单参数缺失追问用户、风险评分用规则引擎兜底、工具超时返回"系统繁忙"不让模型猜，所有失败样本写日志回喂优化 Schema 和 Prompt。
**追问 1**：怎么区分是截断导致的解析失败，还是模型真的没按 Schema 输出？
**答**：看 `finish_reason` 和结束标记。`finish_reason=length` 基本能定位是输出超长被截，这类不该进格式修复重试，而要先提 `max_output_tokens` 或精简输出；误触空行、代码块围栏这类 Stop Sequences 又是另一条路径。两条失败路径我分别覆盖、分别计数，别用同一套重试策略糊过去。
**追问 2**：高价值订单场景，自动修复到什么程度你就必须转人工？
**答**：金融、医疗、法务、赔付这类场景，我不把自动修复当终点。重试 1-2 次仍不过就进人工或规则兜底，哪怕只是非关键字段缺失用了默认值也要记告警；关键是别让模型为了凑齐 Schema 编一个退款金额或订单号，结构合法但业务事实错了，比解析失败更危险。

### J1-25 工具调用为什么必须做安全治理？
**面试官**：工具调用为什么必须做安全治理？
**我（60 秒口述）**：我的结论是，因为模型给出的工具参数属于不可信输入，Schema 只能检查类型和结构，检查不了业务权限；查询通常只读一条受权限约束的数据，退款、删数据、发短信、执行 SQL 会直接改系统状态，必须用更严的执行条件。我做三层校验——结构校验（类型、必填、枚举、长度、格式）、业务校验（订单归属、状态流转、库存、金额范围）、权限校验（身份、角色、租户、数据范围）；风险分级上，查天气基础限流记日志就行，查订单要身份和数据范围，退款、发券、改地址要权限校验、二次确认、审计，删数据、执行 SQL、批量操作默认禁止走人工审批。高风险退款拆 `prepare_refund`（生成金额、原因、影响的预案）和 `confirm_refund`（人或客服确认后执行），幂等 `idempotencyKey` 由可信执行层生成、数据库唯一约束兜底，工具超时就短路、模型只能解释"当前无法完成"。
**追问 1**：把"不要越权查询"写进 Prompt，算不算安全边界？
**答**：不算，那只是提醒。权限控制必须在服务端，"Function Calling 可以绕过业务权限"是误区；Prompt 能被注入、能被上下文挤掉，只有执行层的 `permissionService.canReadOrder()` 这类校验真正拦得住。审计日志我也按字段白名单记，订单号/userId 做掩码，密码、令牌、支付数据禁止进普通日志。
**追问 2**：工具是不是越多 Agent 越强？容量和误调用怎么权衡？
**答**：恰恰相反，工具越多误调用概率越高，我倾向设计得小而清晰。每个工具的字段说明要写清"何时用、何时不用"和排除条件，很多误调用根源就是描述太模糊；写操作还要确认"这个工具能不能安全重试"，不能安全重试的就不该开放给 Agent 随意调用，容量上按风险等级分层给限流和超时。

### J1-26 面试里怎么一句话概括结构化输出？
**面试官**：面试里怎么一句话概括结构化输出？
**我（60 秒口述）**：我的一句话是——用 JSON Schema 把"模型输出"变成可校验的数据契约，用 Structured Outputs / Function Calling 在生成阶段应用契约，再由服务端做校验、重试和降级兜底，目的是让程序能稳定消费，而不只是"看起来像 JSON"。拆开就是"JSON Mode 约束语法，JSON Schema 描述契约，Structured Outputs 在生成阶段应用契约，服务端仍要校验拒答、截断、权限和业务状态"；Prompt 能表达意图，但替代不了 Schema、校验器、重试机制和权限控制。选型我按两步走——先看结果会不会触发外部动作，再看工具要在多少个客户端复用：轻量抽取用 Structured Outputs，读写业务系统用 Function Calling，多工具多客户端用 MCP，固定 SOP 用 Skill。还要避开五个误区：`temperature=0` 不等于稳定、用了 Structured Outputs 不等于不用校验、Schema 不是越复杂越好、工具不是越多越强、Function Calling 绕不过业务权限。
**追问 1**：你说"让程序稳定消费"，生产里用哪个指标证明它稳了？
**答**：分三层看，不只看一个通过率——格式合法率（`JSON.parse()` 能不能过）、Schema 通过率、字段语义准确率。原文那句提醒很关键：一个对象 10 个字段 9 个对、1 个关键字段错，整体通过率再好看也没用；所以我把关键字段单独设门禁，统计高频非法枚举和错误类型。
**追问 2**：如果团队刚起步，只能先做一件事，你选哪个？
**答**：先把数据契约和服务端校验立起来，比急着接原生能力更值。我会定一份带 `schemaVersion` 的 Schema、一个本地校验器、一条解析失败进人工队列的降级路径，哪怕暂时只靠 Prompt 加 JSON Mode 也能兜住不把坏数据喂给下游；`strict` 这类能力可以后补，契约和校验没立住，上什么能力都会漏。

### J1-27 为什么不能只靠公开 benchmark 评估 AI 应用质量？
**面试官**：为什么不能只靠公开 benchmark 评估 AI 应用质量？
**我（60 秒口述）**：我的结论是，公开榜单适合粗筛模型（中文弱、上下文不够、工具调用达不到要求的先排掉），但不能直接当上线依据，因为业务分布、脏输入和少数高风险失败都不在榜单里。榜单任务和数据集固定，英文推理题高分说明不了模型会按电商退换货、快递时效、促销规则这些业务口径作答；真实请求带错别字、口语缩写、截图、多语言和前后矛盾，干净测试集覆盖不到。更要命的是少数不能出错的路径——合同审查漏掉高风险条款、客服答错退款流程、代码 Agent 执行危险命令，占比再低也可能被平均分掩盖，通用 benchmark 根本不会凸显。所以我用自己的 Golden Set 判断模型能不能接进业务，每条用例写清输入、预期结果或成功标准、场景标签和评分方式，高风险失败样本单独设门禁。
**追问 1**：那榜单分数在发布流程里到底放哪一步，怎么验证没被滥用？
**答**：只放在"候选模型粗筛"这一步，绝不进门禁。我会在发布记录里写清用了哪个 Golden Set、哪些业务指标（Faithfulness、任务完成率），确保放行依据是业务评测而不是榜单排名；一个简单检查是——如果有人拿"平均分提高了"当放量理由，却说不出关键路径有没有退步，那就是把榜单思维带进来了。
**追问 2**：模型供应商静默升级底层版本，榜单没变但线上感觉变差，你怎么定位？
**答**：靠自己的固定 Golden Set 加版本记录持续回归。我在网关和评测记录里绑定 `model_version`、`prompt_version`、`datasetVersion` 和 `gitCommit`，线上指标一漂移就按版本切片对比；再配合固定快照回归和实时能力探针两条轨道，先分清是供应商升级、外部数据变化还是自己的改动，别只凭"感觉不如以前准"就回滚。

### J1-28 Golden Set 应该怎么构建？冷启动阶段没有生产日志怎么办？
**面试官**：Golden Set 应该怎么构建？冷启动阶段没有生产日志怎么办？
**我（60 秒口述）**：我的结论是，Golden Set 是应用自己的标准测试集，关键不在数量，而在每条样本都有明确输入和判断好坏的标准；冷启动就用知识库文档作种子加人工构造加真实失败样本先把流程跑起来，但生成样本不能直接当发布门禁。数据来源三块——生产日志分层采样（别只取高频，重点看点了"不满意"、补充追问、转人工和"差点失败"的边缘案例）、人工构造（正常路径、信息缺失、对抗三类）、失败案例回填（每次投诉判断能不能转成评测用例）。分层比总量更关键，"200 条同类问题不如 100 条覆盖 10 类场景"，第一版用 20~50 条真实任务验证流程就够，样本量按分层和基线方差反推。无法穷举时用蜕变测试按输入、上下文、工具、状态扰动写关系断言，留一部分作保留集不参与调参，并且每季度复查覆盖度。
**追问 1**：生成出来的样本为什么不能当发布门禁，生产里出过什么问题？
**答**：因为生成问题通常太规整，错别字、截图描述、前后矛盾和非常规追问它补不上。我见过冷启动全用合成问题，离线分数很漂亮，一放量就被真实脏输入打穿；所以生成样本只补初始覆盖面，必须经人工抽样审核进候选集，再用日志、失败案例和人工审核逐步替换，门禁始终以真实分布为准。
**追问 2**：高权重失败样本数量很少，怎么保证不被大量正常样本稀释？
**答**：单独打标、单独看通过率，不并入总分。合规漏识别风险条款、医疗错误用药建议这类，数量可以少，但发布门禁里一票否决或高权重，和正常路径分开统计；Agent 场景还要分 Trial，区分 pass@k 的"至少一次成功"和 pass^k 的"连续成功"，后者才贴近生产稳定性。

### J1-29 LLM-as-Judge 有哪些主要偏差？怎么缓解？
**面试官**：LLM-as-Judge 有哪些主要偏差？怎么缓解？
**我（60 秒口述）**：我的结论是，Judge 适合评开放式回答、成本比人工低，但位置、冗长、自我强化和有限推理四类偏差让它不能当绝对裁判；硬错误先交规则评测，高风险样本留人工复核校准口径。位置偏差是 A/B 顺序影响判断，我做两次评判交换顺序取一致结论、或一次只评一个答案；冗长偏差是 Judge 偏爱更长的废话，我把"反复粘贴政策原文"和"只保留时间条件例外"放进校准集验证；自我强化是同源模型可能更宽容，重要节点交叉用不同厂商或模型族；有限推理是数学、SQL、复杂逻辑的正确性别只交给它，用 Reference-guided Judge 给参考答案或执行结果。Judge Prompt 给问题、参考资料、参考答案、回答，按 Faithfulness、Answer Relevance、Completeness 各 1-5 分输出结构化 JSON，证据不足允许 `Unknown`、`needs_human_review`。
**追问 1**：怎么验证 Judge 真的稳，而不是 Prompt 写得够长？
**答**：用人工校准集检查一致率、分维度误差和边界样本，不靠看 Prompt。我会算 Cohen's kappa 或加权 kappa、精确率召回率，把低 `confidence` 样本路由到人工复核；`judgeModel`、`graderVersion`、`judgeReasoning` 都进评测记录，方便复核和发现 Rubric 缺陷，而不是只报一个"80% 一致率"。
**追问 2**：如果 Judge 和被测模型是同一家，成本最省，你为什么不这么配？
**答**：因为自我强化偏差，同源可能对自己输出更宽容，省下的成本换来的是系统性偏高。MT-Bench 里 GPT-4、Claude-v1 对自身输出有一定胜率偏好，虽然论文也说差异有限、不能认定稳定偏差，但重要节点我仍交叉用不同模型族并留人工抽样；真要长期省成本，才考虑 ARES 那类用合成数据加少量域内标注训练轻量 Judge，它不是零标注方案。

### J1-30 RAG 评测为什么必须分检索和生成两段？
**面试官**：RAG 评测为什么必须分检索和生成两段？
**我（60 秒口述）**：我的结论是，因为最终表现都只是"答案不准"，但修复入口完全取决于问题出在哪一段——关键资料没召回，改 Prompt 很难救；资料已进上下文模型却没用上，继续调向量库也没用。我拆两张账：检索层看 Recall@K、Hit Rate@K、MRR、Context Precision、Context Recall，生成层看 Faithfulness、Answer Relevance、自定义 Context Usage 和 Noise Sensitivity（0~1 越低越好）；前四个传统 IR 指标要标相关文档 ID，标注太贵时先用 RAGAS 这类 LLM 指标起步但仍要人工抽样。两个陷阱必须躲——把检索结果直接当标准答案会混淆检索质量和生成质量，只评最终答案不分段则根本不知道该改哪层。用户问"怎么退款"答错，我先看退货政策有没有被召回，没召回查分块、混合检索权重和 Reranker；已进上下文却没给申请入口、时限和材料，再去看 Prompt、模型和上下文注入方式。
**追问 1**：怎么证明"政策已进 Top-3 但回答仍只给请联系客服"是生成层的问题？
**答**：做对照——固定同一份证据换 Prompt 或换模型重跑。如果证据已在 Top-3、Recall@K 满分，回答却没接住，那检索层无责，问题在上下文排序、注入方式或 Lost in the Middle；我会看自定义 Context Usage 和 Noise Sensitivity，把这类样本单独归到生成层，而不是继续加检索片段数量。
**追问 2**：RAGAS 里也有 Context Utilization，你为什么非要用自定义 Context Usage？
**答**：因为口径不一样，混用会把结论带偏。RAGAS 的 `Context Utilization` 是把每个 chunk 与生成回答比较再按 Context Precision 方式算排序分，不是"回答用了多少上下文信息"的直接度量；我要测后者就自己定义 Context Usage，报告里写清分母和口径，别拿一个同名不同义的指标去解释"为什么检索好回答仍差"。

### J1-31 Agent 评测为什么比普通问答和 RAG 更复杂？
**面试官**：Agent 评测为什么比普通问答和 RAG 更复杂？
**我（60 秒口述）**：我的结论是，因为 Agent 会在多轮里调工具、改状态、读反馈再决策，前一步的小错会在后面被放大，终点成功不代表过程可靠，必须把 Outcome 和 Transcript 分开看。先分清任务类型——对话/信息型看事实和证据，任务执行型看外部状态变化、权限、副作用，混合型还要看信息收集是否充分；检查层拆成最终状态、决策与执行、运行稳定性、交互与边界四层。测试通过的 Coding Agent 可能改了无关文件、回复"已退款"的客服 Agent 可能跳过身份校验，这些全藏在过程里；所以我不只算任务完成率，还看工具选择精确率/召回率、参数准确率、轨迹准确率、错误恢复率和 pass@k / pass^k。每个 Trial 从干净状态启动做环境隔离，参考轨迹只标不可省略的动作、不把调用顺序写死，代码、财务、权限类严格查关键路径，开放任务把轨迹当诊断工具。
**追问 1**：为什么"至少一次成功"和"连续成功"要分开报？
**答**：它们回答的是不同问题。pass@k 反映能力上限，pass^k 才贴近客服、支付、退款、合规要的稳定性；单次成功率 90% 时连续 5 次都成功概率约 59%，光看"跑通过一次"会高估生产可用度。高风险任务我直接重复 Trial 估这两个值并报样本量，而不是用一次成功当放行依据。
**追问 2**：工具失败后 Agent 安全停下转人工，算成功还是失败？怎么计？
**答**：算一种预定义的恢复结果，但不能和"任务完成"混成同一种成功。错误恢复率的分子是进入预定义恢复结果的次数，我把"补齐参数后完成""换方式重试成功""高风险前安全停止转人工"分开计数；工具一报错就原地结束的样本单独进回归集，这样既认可安全收敛，又不会把真失败粉饰成通过。

### J1-32 离线评测、Trace 回放、线上灰度分别解决什么问题？
**面试官**：离线评测、Trace 回放、线上灰度分别解决什么问题？
**我（60 秒口述）**：我的结论是，三者覆盖开发、发布前、上线后三个阶段，不能互相替换——离线评测在固定 Golden Set 上发现并阻断回归，Trace 回放补离线盲区，线上灰度用小流量看用户反馈和数据分布。流程是开发/实验 → 离线评测（跑 Golden Set）→ 核心指标过阈值 → Trace 回放 → 回放过阈值 → 灰度 1% → 10% → 100% → 持续监控，任一门禁不过就阻断发布；离线要把新结果和上一稳定版放同一张表，改动和评测记录绑定。Trace 回放依赖完整上下文记录（检索文档、工具结果、当时 Prompt 版本、Web 正文和内容哈希），否则只是"用新 Prompt 处理旧问题"；灰度门槛要实验前写进发布规则。我按历史方差、可接受损失和业务风险定非劣效界值再估样本量，分析看效应量和置信区间，不套"下降 3% 就暂停""连续 3 天告警"这种通用数字。
**追问 1**：Trace 回放为什么特别强调内容哈希？生产里漏了会怎样？
**答**：因为涉及 Web Search 或实时 API 时，只存 URL 和参数不够，网页正文会变。漏了正文快照、抓取时间和内容哈希，回放时拿的是"现在"的内容去评"当时"的回答，差异分不清是模型退步还是来源漂移；我会把正文或哈希存下来，并保留固定快照回归和实时能力探针两条轨道，分数不混成一个总分。
**追问 2**：灰度通过后评测能不能停？模型供应商静默升级怎么兜？
**答**：不能停，生产分布、用户行为、知识库和供应商版本都会变。灰度过了我继续做采样回评和告警，低频高风险场景全量评规则指标、语义质量分层抽样，告警基于历史基线和控制图而非固定天数；供应商静默升级这类问题靠版本绑定和固定快照回归发现，两条轨道一起降才去查模型、Prompt、检索或编排的共同改动。

### J1-33 CI 里的 AI 评测如何平衡速度和覆盖度？
**面试官**：CI 里的 AI 评测如何平衡速度和覆盖度？
**我（60 秒口述）**：我的结论是，核心是把"能力集"和"回归集"分开——PR 只跑能在团队等待预算内完成的核心回归集，完整 Golden Set 放主分支或定时任务，Trace 回放放重大发布前，样本量由等待预算、调用配额和希望发现的最小回归幅度反推。能力集保留目前还做不稳的任务、追踪模型、Prompt、工具设计是否真改善，初始通过率不必高，稳定后迁入回归集按门禁处理；阈值组合用绝对阈值守底线（如 Faithfulness < 0.75 不通过）加相对阈值防退步（任务完成率相比 baseline 下降不得超过 5%）。原文那笔账很实在——CI 里跑 500 条 LLM-as-Judge 可能要 10 到 30 分钟，太慢开发者就会想办法绕过 CI，所以评分器优先选规则检查和校准过的自动评分器。环境也要版本化，报告里把 harness error 和模型失败分开记。
**追问 1**：为什么不能把 harness error 算成模型失败，生产里怎么区分？
**答**：因为根因层不同，混算会误导优化方向。接口超时、并发资源不足、评分脚本 bug 属于 ENV/GRADER，不是模型能力退步；我在 `EvalRecord` 里用 `rootCauseLayer`（DATA/MODEL/AGENT/TOOL/ENV/GRADER）和 `errorCategory` 分开落，报告里单独统计 harness error，修环境而不是去调 Prompt。
**追问 2**：PR 阶段样本砍少了，漏掉一个回归怎么办？
**答**：靠分层和后续关卡补，不是靠 PR 一次性兜住。核心回归集专收此前已通过、必须继续稳的任务，配合绝对和相对双阈值加置信区间；完整 Golden Set 在主分支/定时跑、Trace 回放在重大发布前跑，三层接起来。发布时同时检查绝对底线、相对 baseline 和置信区间，避免只凭一个阈值阻断或放行。

### J1-34 如果 LLM-as-Judge 和人工评测结果不一致，应该怎么处理？
**面试官**：如果 LLM-as-Judge 和人工评测结果不一致，应该怎么处理？
**我（60 秒口述）**：我的结论是，把人工与 Judge 结论不同的样本单独收成校准集，先判断是评分维度不够细还是标注规范问题，再用一致性指标判断 Judge 可不可用，而不是急着改被测模型、更不是只看一个"80% 一致率"。原文那个例子很典型——人工因"事实正确但流程缺一步"只给 3 分，Judge 却因语气完整给高分，说明 Rubric 维度还没拆够；二分类看 Cohen's kappa、精确率和召回率，有序评分用加权 kappa，都得考虑类别基线。分歧本身也是发现 Rubric 缺陷的信号，长期分歧要回头查 Rubric、Judge Prompt、Judge 模型或标注规范。低 `confidence` 样本进人工复核，Judge 缺证据时允许 `Unknown`、`needs_human_review`，评测记录保留 `judgeModel`、`graderVersion`、`judgeReasoning` 便于复核，重要节点交叉用不同模型族 Judge 并留人工抽样。
**追问 1**：为什么"80% 一致率"不够，得看 kappa？
**答**：因为一致率没考虑类别基线，两类样本极不均衡时，全判多数类也能拿到高一致率却毫无区分力。Cohen's kappa 扣掉随机一致的部分，有序评分用加权 kappa 还能体现分差大小；我会配分维度混淆矩阵和低置信样本一起看，判断 Judge 是在哪一类、哪个维度上系统性偏，而不是一个总数了事。
**追问 2**：校准完之后，Judge 和人工到底谁说了算？
**答**：分工不同，不是谁替代谁。格式、枚举、引用缺失这类硬错误交规则评测，开放式语义判断交 Judge，高风险和边界样本保留人工复核作最终口径；校准集的作用是让 Judge 的可用边界可量化、让低置信样本能自动路由到人工，而不是把人工评测整个省掉。

### J1-35 客服机器人历史会话持续增长时，如何分配 Token 预算并保留关键业务状态？
**面试官**：客服机器人历史会话持续增长时，如何分配 Token 预算并保留关键业务状态？
**我（60 秒口述）**：我的结论是，先按 `window ≥ input_tokens + max_output_tokens` 划桶，给 System Prompt（含 Schema）、当前输入、历史消息、安全边际和输出预留分配额度；增长的历史靠"裁剪 + 摘要 + 状态外置"，绝不无限塞窗口。16K 窗口的典型分配大概是 System 1500、User 6000、历史 2000、安全边际 1500、输出预留 5000，但历史还要和 RAG 片段、工具 Schema、格式开销抢空间，输出 Token 也占窗口；窗口变长还有 O(N²)、TTFT、Lost in the Middle 和账单的代价。我按固定顺序削——减少 RAG Top-K、合并重复片段、摘要或截断长字段、一轮塞不下拆两阶段生成，并把固定 System Prompt 和工具定义放最前用 Prompt Caching 复用。关键业务状态（订单号、退款状态、身份校验结果、用户偏好）绝不靠模型"记住"长对话，我用结构化字段或外部存储显式回写、每轮只注入必要状态，关键约束放开头或结尾缓解中间丢失，`finish_reason=length` 截断单独处理。
**追问 1**：为什么摘要不够，非要把状态外置？出过什么问题？
**答**：摘要会丢细节，高风险状态丢不起。我见过摘要把"已退款"压成"已处理"，下一轮模型据此又发起一次退款；订单号、身份校验结果、退款状态这种必须精确，我用结构化状态字段落库、每轮按 `runId` 注入，摘要只用来压缩闲聊和无关上下文，两者职责分开。
**追问 2**：换个更大窗口的模型能不能省掉这套治理？成本上怎么算？
**答**：省不掉，还更贵。更大窗口不解决状态丢失和 Lost in the Middle，输入 Token、预填充耗时和账单反而一起涨；成本上我盯 `usage` 和缓存读取/写入 Token 验证命中率，Prompt Caching 把不变前缀复用来压单价，而不是靠扩窗口硬扛，缓存时长和折扣不写死在业务代码里。

### J1-36 流式响应中途断开后，服务端如何处理重试、续传和重复计费问题？
**面试官**：流式响应中途断开后，服务端如何处理重试、续传和重复计费问题？
**我（60 秒口述）**：我的结论是，断流既不能当成功、也不能盲目自动重试——先记 `INTERRUPTED` 状态，按幂等 Key 决定能不能重试或续传，用 `messageId` 加 `sequence` 补发已缓存片段，供应商流失效就提示重新生成，并用 `usage` 和 attempt 记录对齐账单。流式异常分四类：用户取消要同时取消供应商请求、响应流解析、后续 TTS/工具调用/落库和未提交增量缓存；超时分连接、TTFT、总时长三层记录；断流看 `finish_reason` 或最后事件状态，无正常结束标记就标 `INTERRUPTED`；重连靠 SSE `EventSource` 但多数供应商侧流已断，没法从 Token 级续上。我给每个响应生成 `messageId` 和递增 `sequence`，`onDelta` 用 `buffer.seen(sequence)` 去重、`onComplete` 才拼 `fullText` 做 `parseAndValidate` 再 `markSuccess`、`onError` 走 `markInterrupted`；落库只允许一个 attempt 成为 `final`，用户可见任务不自动重试、后台任务才幂等重试，重复计费靠"只让一个 attempt 计费/落库 + 读 `usage` 对齐账单"来兜。
**追问 1**：重复计费具体靠什么堵住？失败请求也可能烧了 Token 啊。
**答**：靠幂等和账单口径两层。只让一个 attempt 计费和落库，其余 attempt 留作诊断不进下一轮 Prompt；取消信号要传播到供应商请求，避免前端停了后端还在生成。失败请求确实可能已消耗部分 Token 并计入每分钟限制，所以我不假设"没成功就没花钱"，而是读 API 返回的 `usage` 对齐实际账单，重试也受最大 2-3 次和 15 秒 SLA 约束。
**追问 2**：断的是半截 JSON，前端又催着要结果，你怎么处理？
**答**：绝不把半截 JSON 交给下游。结构化流式我等正常结束事件后拼完整再做 Schema 校验，没结束标记就按 `INTERRUPTED` 处理、前端展示"已中断，可重新生成"；`message_id`、`attempt_id`、`provider_request_id`、`stream_sequence` 四层 ID 分开，重连先用短期缓存补发已发片段，供应商流已结束就老实重新生成，不假装无缝续写。

### J1-37 上游模型触发 RPM 或 TPM 限制时，模型网关如何排队、降级或切换模型？
**面试官**：上游模型触发 RPM 或 TPM 限制时，模型网关如何排队、降级或切换模型？
**我（60 秒口述）**：我的结论是，网关先按 RPM/TPM/并发/上下文/预算自己扣桶，收到 429 后按"读 header → 标维度 → 排队或切换 → 熔断"处理，降级要显式告知业务层，不能偷偷变差。429 只是外部保护信号，不能代替应用侧容量管理；请求进来先估算 `input_tokens + reserved_output_tokens` 在用户、租户、模型、供应商几层桶里扣减，扣不到就排队、降级或拒绝，同时看 RPM、TPM、并发数、`max_tokens` 和日/月预算。处理顺序是读 `Retry-After` 或限流头、标记是请求数/Token/日配额哪个维度打满、短请求进延迟队列、用户交互请求少重试或切轻量模型、连续 429 就熔断；典型降级链是优先模型 → 备用同级 → 轻量模型并缩短输出 → 仍不可用排队或返回"当前请求繁忙"。我用供应商级全局令牌桶加熔断器、模型级令牌桶加并发信号量、流式请求并发信号量加总时长限制，数值从控制台、响应头、配置中心动态读，不写死。
**追问 1**：为什么降级要显式告知业务层，生产里出过什么问题？
**答**：因为悄悄切轻量模型会把答案质量拉低却没人知道，业务方只感觉"最近不太准"。我会在响应或业务标记里写明"当前为快速模式，复杂问题建议稍后重试"，让上层能决定是否重问；同时盯 429 Rate 和 `usage`，确认是配额真打满还是限流桶配得不合理，别靠压输出上限硬省。
**追问 2**：所有请求一起重试为什么会把系统再打进限流，抖动怎么落地？
**答**：同一时刻集体重试会形成尖峰，刚恢复的供应商再被打挂，这就是抖动的用处。我在退避等待里加随机量错开峰，配合最大次数、总截止时间和读 `Retry-After` 尊重明确恢复时间；用户交互类请求本来就该少重试，后台短请求才进延迟队列排队，两者策略分开。

### J1-38 模型生成退款工具的调用参数后，业务系统还需要执行哪些校验？
**面试官**：模型生成退款工具的调用参数后，业务系统还需要执行哪些校验？
**我（60 秒口述）**：我的结论是，模型参数是"不可信输入"，Schema 只管类型结构，必须做结构校验 → 业务校验 → 权限校验三层，高风险退款还要二次确认、幂等、审计和超时短路。Schema 只能知道 `orderId` 是个字符串，不知道订单是不是当前用户的、是否已退款、用户有没有客服权限；退款属高风险工具，删数据、执行 SQL、批量操作更是极高风险默认禁止。我用 Jackson 加 JSON Schema Validator 校验 `^O[0-9]{12,20}$`、`required`、`additionalProperties: false`、`query_order_v1` 这类契约，未知工具直接 `UNSUPPORTED_TOOL`，错误码 `INVALID_ARGUMENTS`、`FORBIDDEN`、`ORDER_NOT_FOUND` 分清；再查订单归属、状态流转、金额范围和 `permissionService.canReadOrder()`，拆 `prepare_refund` 和 `confirm_refund` 做二次确认，`idempotencyKey` 由可信执行层生成、数据库唯一约束兜底、外部退款接口带同一幂等号，审计按字段白名单脱敏，工具超时短路、模型只能解释"当前无法完成"。
**追问 1**：并行调用时结果回填最容易错在哪，怎么防？
**答**：错在 `tool_use_id`、`functionCall.id` 没原样带回，结果贴错对象。我要求回填必须带唯一 `callId`，派发层按 ID 路由；Anthropic 严格匹配 `tool_use_id`，Gemini 3 每个 `functionCall` 都有唯一 `id`，缺了就进明确错误而不是猜对应关系，并行退款场景这一步尤其不能省。
**追问 2**：为什么幂等键不能接收模型给的，超时未知又怎么处理？
**答**：模型参数不可信，键必须由可信执行层按业务请求 ID、动作和资源生成 `actionId`，数据库唯一约束兜底。退款请求超时属于 `TIMED_OUT_UNKNOWN`，不能当失败直接重试——我按 `actionId` 先查状态：查到成功就回填、明确失败才重试、仍未知转对账或人工，三种结果都写进 Trace 且不能都记成调用失败，确认事件也只消费一次。

### J1-39 更换模型或修改 Prompt 后，如何用离线评测、Trace 回放和线上灰度验证效果？
**面试官**：更换模型或修改 Prompt 后，如何用离线评测、Trace 回放和线上灰度验证效果？
**我（60 秒口述）**：我的结论是，三段证据按顺序串起来——离线评测在固定 Golden Set 上比对新旧版本并绑定变更记录，Trace 回放在真实生产轨迹上补盲区，线上灰度用 1% → 10% → 100% 小流量验证用户反馈与数据分布，任一门禁不过就阻断发布。离线评测把新结果和上一稳定版放同一张表，Prompt、模型、检索策略改动和评测记录绑定，提前定义"Faithfulness 从 0.82 降到 0.79 算不算回归"；CI 里 PR 只跑核心回归集（规则评测加校准过的自动评分器），完整 Golden Set 放主分支/定时，同时查绝对阈值（Faithfulness < 0.75 不通过）、相对阈值（任务完成率相比 baseline 下降不得超过 5%）和置信区间。Trace 回放采样真实请求带原始输入和完整上下文（检索文档、工具结果、当时 Prompt 版本），涉及 Web 要存正文和内容哈希；灰度结构化输出用规则自动评测、开放式回答每天一批 LLM-as-Judge 采样，满意率、转人工率作辅助，按非劣效界值估样本量、看置信区间。
**追问 1**：定位时为什么强调"一次只替换一个变量"？生产里怎么做？
**答**：因为同时换模型和 Prompt，分数一变就分不清是谁的锅。我做对照实验时保留相同证据只换模型、保留相同模型只换检索结果、绕过 Agent 直接调工具、固定被测输出只换 Grader；Badcase 先复现原始快照再归因，记录按现象→候选层表查证据，修复后把原始 Case、根因层、修复动作和验证运行 ID 回填回归集。
**追问 2**：一次线上失败修完就结束了吗？怎么让它不再复发？
**答**：不算结束，必须回流成自动回归用例。我会把确认过的失败 Trace 脱敏后补进 Golden Set 和回归集，绑定 `inputHash`、`promptVersion`、`modelId`、`datasetVersion`、`gitCommit` 和环境快照，让后续每个版本都自动跑这条；否则它就只存在群聊截图里，下次同样的坑还会再踩，这就是"一次线上失败应变成后续版本的自动回归用例"的意思。
