### J2-01 AI Agent 是什么？和普通 Chatbot 有什么区别？
**面试官**：AI Agent 是什么？和普通 Chatbot 有什么区别？
**我（60 秒口述）**：我的判断是区别不在有没有调大模型，而在有没有把执行路径走完的闭环。Chatbot 生成一段回复就收工，Agent 是感知、决策、动作、观察的循环，模型自己选工具、读结果，再决定下一步还是结束，工具结果必须写回上下文变成 Observation。撑起这件事最少三层：LLM Call、Tools Call、Context Engineering。落到工程上边界得写死，轮次、Token、时间、费用上限由运行时卡住，否则长任务失忆、烧 Token 还难排查。真上线我最怕的不是模型笨，是决策和调用原因追不回来。
**追问 1**：为什么把 Agent 说成"会调工具的聊天机器人"不够？
**答**：不够，因为任务一长，它就得处理状态、记忆、权限、失败重试、上下文裁剪和执行边界，这些 Chatbot 全没有。反例很直观：排障任务里聊天模型最多给一份排查清单，不会自己去查监控、翻慢 SQL、查通讯录再把结论发出去。
**追问 2**：换个更强的模型，Chatbot 就能变成 Agent 吗？
**答**：不能，闭环是运行时和 Harness 提供的能力，不是模型参数。模型只负责意图理解和决策，工具执行、状态保存、失败恢复都在模型之外，`Agent = Model + Harness` 讲的就是这件事。

### J2-02 Agent = LLM + Planning + Memory + Tools 这条公式怎么理解？
**面试官**：Agent = LLM + Planning + Memory + Tools 这条公式怎么理解？
**我（60 秒口述）**：我把它当能力拆解，用来说明项目跑不起来往往不是模型不行，而是基础没搭好，缺一块就有明显短板。LLM 管意图和决策，Planning 定下一步动作但路径确定的部分我交给代码，Memory 短期在上下文、长期放外部库，Tools 执行外部操作，返回值必须回填成 Observation，不然闭环断。四块正好映射到 LLM Call、规划器、会话与记忆库、工具执行器。少 Tools 停在给建议，少 Memory 长任务就失忆。顺带一提，`Agent = Model + Harness` 是另一视角，拆模型与运行环境，两条能同时成立。
**追问 1**：这条公式里最容易被漏掉的是哪一块？
**答**：Observation 回填。很多人只讲"调工具"，不讲结果写回上下文这一闭环。参数上也有硬约束：Anthropic 要求 `tool_use_id` 严格匹配，Gemini 为每个 `functionCall` 生成唯一 id，并行调用时缺对应 ID，返回结果就可能配错工具请求。
**追问 2**：Tools 是不是接得越多越好？
**答**：不是，工具越多执行路径越不能随意放开。订单扣库存、审批流这类步骤明确的工作仍该由传统程序或 Workflow 控制；像 `execute_sql(sql)`、`call_api(url,method,body)` 这种万能工具把操作范围和权限都交给模型猜，参数越多误用与越权空间越大。

### J2-03 Agent Loop 的完整流程是什么？
**面试官**：Agent Loop 的完整流程是什么？
**我（60 秒口述）**：一句话，它把模型决策、工具执行、结果写回这条反馈链连续跑起来，直到不再调工具或命中停止条件。初始化载入三件套：System Prompt、工具列表、用户请求；每轮模型在直接回复和调工具之间选，运行时把结果和状态写回，模型不请求工具就结束。我想强调退出条件不止一种，轮次、Token、时间、费用四类上限都由运行时强制停止，生产里常见 10 到 20 轮，用来拦住错误判断把任务带进死循环。每轮进窗口的消息和 Token 我都会记，不然没法回放。
**追问 1**：退出条件为什么不能只交给模型自己判断？
**答**：因为模型会"看起来在推进其实偏题"，深度多步推理容易局部最优，所以停止边界得写死在运行时而不是 Prompt 里。参数上就是 10–20 轮上限或按 Token 消耗终止，达到就强制收工。
**追问 2**：循环跑久了，最大的隐性代价是什么？
**答**：上下文随每轮工具结果不断变长，早期约束被后续内容稀释，模型更容易跑偏，这正是 Context Engineering 的切入点。光加长窗口不解决问题，得靠压缩、卸载重型结果、清理旧 `tool_result` 来控。

### J2-04 Agent 和传统编程、Workflow 的核心区别是什么？
**面试官**：Agent 和传统编程、Workflow 的核心区别是什么？
**我（60 秒口述）**：我用一句话判：谁决定执行路径。程序员写代码是传统编程，产品画流程图是 Workflow，用户说意图由 AI 动态决策才是 Agent。扣库存、支付流转这类固定高频逻辑用程序最稳；审批、内容发布路径清晰交给 Workflow，出问题能落到具体节点；而排查服务变慢该查监控还是日志要看中间证据，写不死分支，才是 Agent 的地盘。口径就一条：执行路径能不能提前确定。To B 我更倾向 Workflow 或 Agentic Workflows，因为动态路径的调试难度高一个数量级。
**追问 1**：很多人觉得自己的任务"路径不确定"，怎么验证这是真判断还是需求没拆清？
**答**：认真拆一遍，大部分会发现其实是"LLM 在固定节点里做生成或判断"。判据很朴素：能写出来执行步骤就用 Workflow，写不出来再上 Agent，这个判断先做好比追框架有用得多。
**追问 2**：传统工作流是不是"完全确定、相同输入必得相同结果"？
**答**：不是。BPMN 2.0、Camunda、Temporal、Airflow 都能编排人工任务、外部 API 和非确定性活动。真正的差异是 AI 工作流里"结果是否达标"要运行时评估，同一节点可能因输出不确定被反复执行，所以经常出现回边。

### J2-05 ReAct、Plan-and-Execute、Reflection、Multi-Agent 分别适合什么场景？
**面试官**：ReAct、Plan-and-Execute、Reflection、Multi-Agent 分别适合什么场景？
**我（60 秒口述）**：四种对应边走边看、先规划再执行、做完自检、分角色协作，我按任务结构组合用，不单选。ReAct 每步看工具返回再定下一步，适合查什么取决于中间证据的排障；Plan-and-Execute 先出全局计划再逐项做，适合步骤多、依赖明确的长任务，但环境变了旧计划会失效；Reflection 用自然语言反馈纠正、不改权重，一般叠加在前两者上；Multi-Agent 要任务能拆成独立职责、每角色有独立工具权限和交付才成立。落地我一般先 Planning 拆任务、子任务内跑 ReAct、最后 Reflection 验收，跑通了再按失败模式升级。
**追问 1**：Plan-and-Execute 在生产里最容易出什么问题？
**答**：环境变化时旧计划会失效，而它动态调整和容错弱于 ReAct，行为更接近静态工作流。所以执行中出现未预料结果时要重新规划，不能照原步骤一路跑到底；可以和 ReAct 嵌套，用 CoT 给全局步骤、每个步骤内部再跑 ReAct 子循环。
**追问 2**：Reflection 能单独搭成一套 Agent 吗？
**答**：不能，它是叠加校验关系，不是独立范式。Reflexion、Self-Refine、CRITIC 三种实现都依附在 ReAct 或 Plan-and-Execute 的执行轨迹上做纠正；而且 Multi-Agent 的收益前提是每个角色有独立 Prompt、工具、上下文、权限和交付结果，否则只是多阶段 Prompt Chain。

### J2-06 Tools 注册时，工具 description 为什么很关键？
**面试官**：Tools 注册时，工具 description 为什么很关键？
**我（60 秒口述）**：因为模型是否调用、怎么填参数主要就看 description 那几句话，它同时是路由条件、参数说明和禁用场景声明。JSON Schema 只是格式，真正决定选择的是描述里写没写清"什么时候该用、什么时候不该用"。像查慢 SQL 的工具，我会写明服务响应慢、CPU 飙升且怀疑数据库相关时用，问网络或内存问题时不要调。我的底线是：连人类工程师都看不出这工具该不该用，Agent 一定会犯错，参数里还得给格式示例。写得省力气，后面会双倍还回来。
**追问 1**：只写"这个工具能做什么"会出什么事？
**答**：缺反例条件，模型就会误调用或填错参数。得把约束写进描述和 Schema，比如 `query_slow_sql` 的 `required: ["service_name", "time_range"]`、`threshold_ms` 默认 1000、`time_range` 格式 HH:MM-HH:MM；这些不写清，只能靠运行时重试兜底。
**追问 2**：工具描述本身有没有安全风险？
**答**：有，它和 Prompt 模板、返回内容一样是不可信输入，可能夹带提示词注入，引导模型读取更多文件或外传信息。所以第三方 MCP Server 的 `description`、Prompts 模板和返回内容都要进审核范围，供应链不能只看代码。

### J2-07 什么时候用纯 Agent，什么时候用 Workflow 或 Agentic Workflow？
**面试官**：什么时候用纯 Agent，什么时候用 Workflow 或 Agentic Workflow？
**我（60 秒口述）**：判据最简单：执行路径能否提前确定。纯 Agent 只留给提前写不出步骤的任务，其余优先 Workflow，混合场景用 Agentic Workflows。生成初稿、审核、按反馈修改这类顺序和重试条件能写进图，LLM 只在节点里生成或判断，问题能定位到具体节点；纯 Agent 由模型运行时决定调什么工具、走哪条路。Agentic Workflows 全局固定主流程，只在不确定局部嵌 Agent 子循环、由外层卡住范围。靠一段超长 Prompt 塞全部逻辑早晚会炸，得是可分支、可循环、可观测的路径，比如审核不过回修改、最多 3 次就是一条条件边。
**追问 1**：所谓"两者都有"的混合，生产里具体怎么落地？
**答**：步骤稳定、权限明确的流程交给 Workflow；遇到无法提前穷举的检索、分析或工具选择，就在那个节点嵌 Agent 子循环，局部决策交给模型、执行范围由外层流程卡住。LangGraph 和 Spring AI Alibaba Graph 都能用 Node、Edge、State 把这条结构表达出来。
**追问 2**：To B 场景为什么你更倾向 Workflow？
**答**：主要是容错和可排查性。Workflow 路径固定、出问题落到具体节点，Agent 动态路径的调试难度高一个数量级。除非拆完需求确实写不出步骤，我不会一上来追框架，先把任务执行路径写出来这个判断比选框架有用得多。

### J2-08 Multi-Agent 协作的主要问题是什么？为什么生产里不能盲目上多 Agent？
**面试官**：Multi-Agent 协作的主要问题是什么？为什么生产里不能盲目上多 Agent？
**我（60 秒口述）**：多 Agent 换来职责隔离与并行，代价是通信、协调、状态归并和调试成本翻倍，所以我永远先单 Agent 或固定 Workflow、收益可衡量后再拆。只有不同环节需要明显不同的工具、权限、上下文，或任务能分成相对独立方向时我才考虑；而且每角色得有明确交付，结构化结论、引用、代码 Diff、测试报告，只交几段自由文本后面全耗在拼接和定位上。上线前我用同一批任务做对照测试，比质量、耗时、Token、失败率，没有可衡量收益就保留较简单实现。
**追问 1**：怎么判断几个角色是真 Multi-Agent，而不是换个名字的 Prompt Chain？
**答**：看三件事：能否独立接收子目标、能否在受限上下文和工具里完成、能否按约定 Schema 交付结果。反例是四个角色共用一份上下文和一组工具、每步只改写上一步文本，那仍是一条多阶段 Prompt Chain；另外并行只说明任务怎么执行，和系统里有几个 Agent 没有必然关系。
**追问 2**：两个分支同时写同一个结果字段，能让模型自己商量解决吗？
**答**：不能，这是并发写入问题，不是语义判断。得按角色分槽、由单一归并节点写 `finalOutput`；LangGraph 里并行节点同时覆盖一个用 Replace 语义的字段会直接抛 `INVALID_CONCURRENT_GRAPH_UPDATE`，线程安全容器也只能保证写入不损坏，判断不了哪个业务结果该留。

### J2-09 Agent 的短期记忆和长期记忆有什么区别？
**面试官**：Agent 的短期记忆和长期记忆有什么区别？
**我（60 秒口述）**：短期是 Session 级、依托上下文窗口、服务当前任务，长期是跨 Session 外部存储、沉淀偏好和历史决策，两者物理逻辑都要分开。短期包括每轮提问、回复和工具中间结果，直接进当轮 Prompt；但窗口大不等于能无限塞，成本随 Token 线性涨，还有 Lost in the Middle 让中间段利用率更低。长期走 Record 和 Retrieve 两条链路：对话结束后台异步做语义提纯再落库，新 Session 按当前问题检索、只把命中条目 prepend 进 System Prompt。写入按 Best-Effort 加幂等 Key，检索 P99 会直接吃进 TTFT。这层的取舍是宁可少存，也别把整段历史搬回新会话。
**追问 1**：短期记忆快撑满窗口了，生产里你会怎么控？
**答**：三种手段。一是 Context Reduction，滑动窗口丢最早 N 轮或让轻量模型压成摘要；二是 Context Offloading，完整网页、CSV 这类重型结果放外部存储，Prompt 里只留 UUID 或文件路径；三是 Context Isolation，主 Agent 只把子任务说明和必要片段交给子 Agent。Offloading 的读取接口要定义超时和大小上限，超限返回截断结果或明确降级信息。
**追问 2**：长期记忆和 RAG 技术上很像，边界到底在哪？
**答**：服务对象不同。RAG 从外部知识源取回证据，长期记忆管的是和特定用户交互中动态沉淀的个性化经验，高度因人而异。排查"记忆没生效"时我先看检索 Trace——query 改写、过滤、候选集、Reranker 打分，确认候选库确实缺信息，再改抽取规则或加写入预算。

### J2-10 Agent 记忆系统要解决哪些核心问题？
**面试官**：Agent 记忆系统要解决哪些核心问题？
**我（60 秒口述）**：一句话，同时保住当前对话关键事实和新 Session 能取回偏好、背景、历史决策，还要回答写入时机、存哪里、存多久、何时读、过期冲突怎么办。背后三条硬约束：窗口有上限、Token 账单一路涨、Session 结束没落库轨迹就随进程消失。我按六步生命周期搭：编码、存储、提取、巩固、反思、遗忘，对应抽事实、写向量库或图库、混合检索、异步归并、提 Meta-Knowledge、权重衰减加废弃。关键判断是不能只 append，否则长期记忆很快变流水账，得有代谢机制让它能被反思、合并、清理和遗忘。
**追问 1**：把每轮对话都送去抽取、直接入库有什么坑？
**答**：寒暄、临时猜测和重复描述也会进库。我先拿 `importance` 之类的规则拦住无用内容，再用 JSON Schema 约束字段、复查低置信度条目，高 importance 条目保留源对话和抽取结果；像"我可能会……"这种假设性陈述不能直接固化成稳定偏好。
**追问 2**：除了读写，记忆系统还有哪类容易被漏掉的问题？
**答**：权限与多租户隔离。隔离条件必须由数据访问层统一注入，否则一个用户的偏好可能出现在另一个用户的结果里；写入前还要做 PII 脱敏、按冷热分离，高频偏好缓存加低频背景 RAG。没到多租户体量之前，单向量链路先把写入幂等、检索 trace、rerank 跑顺通常更划算。

### J2-11 向量记忆和 Markdown 记忆分别适合什么场景？
**面试官**：向量记忆和 Markdown 记忆分别适合什么场景？
**我（60 秒口述）**：我的分法：少量、明确、可结构化、要人工审阅和版本控制的约定用 Markdown，大量非结构化、要按语义召回的用向量检索，两者并存不一刀切。Markdown 是人机共写的明文长期记忆，透明可审计、能提交 Git 做回滚和 Code Review、零迁移成本；代价是启动时全量注入，上下文成本跟文件大小线性相关。向量库按需检索、上下文高效，但要维护向量服务。边界很清楚：文件涨起来后目录和人工命名很难定位相关片段，就该交给向量检索；反过来记住项目编码规范这类明确信息，Markdown 更合适。
**追问 1**：说"Markdown 更省上下文"对不对？
**答**：不对，`@` 引用不减少上下文消耗，被引用文件在启动时全量加载。真要省只能用 `.claude/rules/` 的 path-scoped rules 按需加载；而且 `CLAUDE.md` 官方建议每个控制在 200 行以内，超了反而降低指令遵守率。
**追问 2**：哪些东西不该写进 Markdown 记忆？
**答**：大段日志、完整对话记录、敏感密钥、Token、账号信息都不适合，高频变化的运行时数据和能实时查询的动态信息也不该放。还有两个细节：`@` 引用最多 5 层递归深度，首次使用外部引用时误拒审批会被永久禁用，得手动重置。

### J2-12 Auto Memory 是什么？它为什么不能无限自动写入？
**面试官**：Auto Memory 是什么？它为什么不能无限自动写入？
**我（60 秒口述）**：Auto Memory 是 Claude Code 自动把调试方式、代码习惯、工作流偏好写成笔记的机制，和人工 `CLAUDE.md` 构成双轨制。笔记在 `~/.claude/projects/<project>/memory/`，`MEMORY.md` 是入口但只加载前 200 行或 25KB，超出不进上下文。不能无限写有三层原因：入口有硬上限、经过 20 到 30 个会话就会积累矛盾过时条目、LLM 抽取本身还会误写和重复，写越多有效密度越低还挤占上下文。生产里写入按 Best-Effort 加幂等键，CI/CD 这种不需要沉淀临时笔记的环境我直接关掉它。所以规则要可验收，写不进检查项的我会直接删掉。
**追问 1**：怎么控制 Auto Memory 写进去的质量？
**答**：先用 `importance` 等规则拦住寒暄和临时猜测，再由离线任务处理冲突、重复条目和过期记录，社区 dream-skill 的 Orient、Gather Signal、Consolidate、Prune 四阶段就是做这个整合，但它不是官方功能。禁用入口是 `/memory`、`autoMemoryEnabled` 配置和那个环境变量。
**追问 2**：写进笔记的规则，怎么判断它到底有没有用？
**答**：规则得可验收，"注意代码可读性"没法检查，"函数名动词开头、单函数不超过 40 行"能判断；整篇都是 `IMPORTANT:` 等于没有重点。同一规则反复被忽略时，我先查是不是被无关内容挤到后面或彼此冲突，而不是加感叹号；更可靠的是备份后实际删掉，在真实任务上观察行为变化，别只信对话式自评。

### J2-13 哪些团队共享记忆适合走 Git 和 Code Review，哪些更适合数据库？
**面试官**：哪些团队共享记忆适合走 Git 和 Code Review，哪些更适合数据库？
**我（60 秒口述）**：少量、要人工审阅、变更低频、要追溯原因的团队约定走 Git 加 Code Review 加 PR；高频变化、大体量、要按语义检索或跨租户隔离的更适合数据库或向量库。项目规范、编码标准、踩坑记录落到项目级 `CLAUDE.md` 和 `.claude/rules/` 里天然适合 Git，每次更新都 commit，能回滚、能追溯为什么改；反过来它明确不适合存大段日志、完整对话、敏感密钥，也不适合高频变化的运行时数据。私有记忆放 `CLAUDE.local.md` 加 `.gitignore`。数据库侧才谈多维索引、PII 脱敏和多租户隔离由访问层统一注入。
**追问 1**：Code Review 在这条链路里只用来回滚吗？
**答**：不止，它把"为什么有这条规则"沉淀成可审查的决策记录。比如"使用 QueryWrapper"后面补一句"SQL 审计系统依赖 Wrapper 解析记录操作日志"，架构规则带上原因，后人才敢删敢改；这也是共享记忆比单纯存文件更值钱的地方。
**追问 2**：多人同时更新共享记忆，怎么防写冲突？
**答**：写入要有幂等 Key 和版本控制，多端并发对话时实体库合并与覆盖引入乐观锁或 MVCC。另外别把所有记忆都塞进 Git，Markdown 是全量注入、无检索机制，大文件会线性挤占上下文；文件一多，就该把按语义召回的部分交给向量检索。

### J2-14 记忆压缩、记忆过期、记忆冲突应该怎么处理？
**面试官**：记忆压缩、记忆过期、记忆冲突应该怎么处理？
**我（60 秒口述）**：这三件事得分开，我各给一条主线。压缩用摘要、滑动窗口和卸载换空间，但必须保留可回查引用，Compaction 保留架构决策和未解决 Bug、移走冗余工具结果，更轻的是留 `tool_use`、清旧 `tool_result`。过期用权重衰减加冲突标记废弃加定期 Vacuum，得分是 `score = relevance × importance × decay(t)`；我不每次对全量算衰减，向量库先静态语义召回、Reranker 阶段再实时调权。冲突先分类型：观点冲突保留来源交给归并器，写入冲突靠版本 CAS 归并，绝不简单覆盖。软删除会破坏 HNSW 连通性，所以还得定期重建。
**追问 1**：压缩最容易丢掉的是什么？
**答**：证据。排障信息要保留 traceId、请求时间、错误码、日志文件位置、工具调用参数和原始结果摘要链接；只留一句"接口报错了"后面排障会断线，可原始日志洪流直接塞进去又会把模型淹没，摘要丢失的兜底就是这些回查字段。
**追问 2**："事实结论冲突"和"写入冲突"能一样处理吗？
**答**：不能混。前者保留各自证据、时间、适用范围由 Reviewer 或归并节点判断，后者是并发写入问题，模型讨论解决不了，得靠按角色分槽、版本 CAS、Lease 加 Fencing Token。还有个边界：LoRA 写进参数后不好删，会碰到 Machine Unlearning，所以参数记忆只适合变化很慢的偏好，向量库删一行就行。

### J2-15 如何避免长期记忆污染上下文？
**面试官**：如何避免长期记忆污染上下文？
**我（60 秒口述）**：靠四道关，不是靠调 Prompt：写入前校验、检索时过滤与重排、进上下文后标来源时间可信度、定期遗忘。写入侧用 JSON Schema 约束字段、复查低置信度，多租户请求一进检索层就带 UserID、组织 ID、时间范围这些硬过滤条件由访问层统一注入，少了这层，一个用户的偏好会出现在另一个用户结果里。检索侧走混合检索加元数据过滤加 Reranker，上下文侧按四级 Token 预算把 System Constraints、当前目标、安全边界放高优先级固定区。只做压缩还不够，Anthropic 遇到上下文焦虑会直接 context resets，代价是交接文档漏项新 Agent 就从错误状态继续。
**追问 1**：怎么验证污染真的被挡住了，而不是自我感觉？
**答**：先保存真实调用轨迹建立可回放基线，再看召回条目里旧偏好、旧状态有没有被当成当前事实；40% 上下文利用率只是来自特定模型和任务的待验证初始观察值，我不该在缺少回放数据时直接把它设成告警线。
**追问 2**：压缩后摘要把价格、版本这类关键数字洗掉了怎么办？
**答**：兜底是保留 traceId、原始证据位置、关键字段和可回查链接。涉及价格、版本、法规、实验数据这类时效性信息，采集时间、来源、关键字段都得留，摘要不能脱离证据；高信噪比比信息量更重要，我会从真实轨迹找出完成决策所需的最小信息集。

### J2-16 面试里怎么讲“有记忆”不是简单保存聊天记录？
**面试官**：面试里怎么讲“有记忆”不是简单保存聊天记录？
**我（60 秒口述）**：我会说"有记忆"指的是一整套生命周期加分层的工程链路，聊天记录只是原始素材，不等于可复用记忆。短期 Session 级、长期跨 Session 分开存；写入要语义提纯、抽高价值结构化事实而不是整段搬回；检索按当前问题取相关条目；再往上是六操作生命周期，编码到遗忘，配幂等 Key、PII 脱敏、混合检索、权重衰减、冲突废弃和 Vacuum。我会主动抛反例：只把聊天记录写进 Redis，并不能从"两个检索任务完成、一个分析超时"的位置继续整条 Workflow，恢复得能重建依赖和已确认产物。不会遗忘的记忆库越大噪声越大。
**追问 1**：会话状态、共享业务状态、外层 Workflow 状态能存一起吗？
**答**：不能，要分别保存、不能相互替代。会话状态记对话、工具调用和角色内部进度；Workflow 状态还得记当前阶段、已完成角色、产物引用、模型与 Prompt 版本、预算使用和失败记录；共享业务状态又是另一类，恢复时只有把这些都对齐才谈得上层。
**追问 2**：为什么讲"有记忆"一定要把"遗忘"讲进去？
**答**：不会清理的记忆库越大噪声越大，向量库堆了几十万条后每次 Top-K 都混着过时噪音，Agent 的建议还停留在三年前，这种体验很难靠调 Prompt 补回来。所以巩固、聚类合并、权重衰减、冲突标记废弃、Vacuum 要和写入检索一起设计，才算完整生命周期。

### J2-17 Prompt Engineering 和 Context Engineering 有什么区别？
**面试官**：Prompt Engineering 和 Context Engineering 有什么区别？
**我（60 秒口述）**：Prompt Engineering 处理指令怎么写，关心措辞、顺序、格式、语气；Context Engineering 决定这一轮实际把哪些信息、以什么结构、什么时机放进有限窗口。我很认一个类比：它就是 LLM 的内存管理，窗口是有限内存，管装什么、换出什么、何时读写，满了要淘汰，跟操作系统页面置换一个思路。它管得宽得多：System Prompt、Memory、RAG 和工具、参数结构与返回约束、Observation 保留策略、摘要压缩和 Token 预算。两者不是同一层，Prompt 说清指令、Context 给对信息、Harness 保证持续执行与恢复，一层套一层。上下文不够时模型再强也只能靠猜。
**追问 1**：怎么证明一次 Context 改动真有效，而不是体感？
**答**：先选 20 到 50 条真实任务轨迹做小评测集，固定模型、Temperature、System Prompt 和检索材料，每次只改一个变量，看任务成功率、工具质量、上下文成本、延迟指标、结果质量五类指标。别凭一句"感觉更顺了"就上线。
**追问 2**：把 `.claude/rules`、`AGENTS.md` 直接叫 System Prompt 对不对？
**答**：不对，那是宿主读取的规则来源，和 API 消息里角色意义上的 System Prompt 不是一个概念，宿主按自己的加载规则把其中一部分转成模型上下文。另外 Cursor 早期的 `.cursorrules` 已是旧版形式，新项目用 `.cursor/rules`，把这些混为一谈很容易在追问里露馅。

### J2-18 Prompt 四要素 Role、Task、Context、Format 分别解决什么问题？
**面试官**：Prompt 四要素 Role、Task、Context、Format 分别解决什么问题？
**我（60 秒口述）**：四要素是把任务边界、必要背景、约束和输出形式交代清楚，缺信息时模型只能自行补全条件，输出更容易偏题或编造。Role 定领域知识和语气，Task 定动作，Context 补背景，Format 定输出长什么样。差 Prompt 只有"分析这段代码性能问题"一个动作，模型不知道视角、负载和结果粒度；好的会给出 10 年 Java 架构师、线上 QPS 2000 响应超 500ms、输出瓶颈点标注行号加优化方案附预期指标。还有个细节我会用：Lost in the Middle 让中间信息更易被忽略，所以角色和格式要求分放输入两端。别写成说明书，Prompt 好不好不看长度看有没有把任务说清楚。
**追问 1**：怎么验证一条 Prompt 改好了没有？
**答**：最小评测五步——准备 10 到 30 条覆盖正常、边缘、异常的样例，固定变量，记格式合规率、事实错误率、字段缺失率、人工修改次数，每次单点修改，最后保留失败样例定期回放，防止"新规则修一个坏三个"。换模型或 API 版本后要把当前 Prompt、模型版本、采样参数和工具定义一起固化成基线重跑回归集。
**追问 2**：角色设定能补足缺失的业务背景吗？
**答**：不能。"你是一位 10 年经验的架构师"给不了线上 QPS 2000、响应超 500ms 这种业务背景，也定不了输出粒度。而且长对话里加入大量无关内容后，早期角色设定的影响会减弱，所以背景和输出格式得靠 Context 和 Format 实打实补上。

### J2-19 Few-Shot、CoT、任务分解、结构化输出分别适合什么场景？
**面试官**：Few-Shot、CoT、任务分解、结构化输出分别适合什么场景？
**我（60 秒口述）**：四种都是可选手段，我按任务复杂度、格式严格度、要不要显式检查过程来选，用不用由评测结果和成本决定，从不靠堆技巧。Few-Shot 给 1 到 3 个示例，复杂或格式严格任务比大段说明管用，超过 3 个收益下降还多花 Token；CoT 用于数学、逻辑、多步分析，简单查询硬加只增延迟；任务分解把复杂任务拆成输入输出都能单独检查的子任务，某步出错能定位；结构化输出先定义 Schema，JSON 方便但字段缺失易解析失败，要有降级。CoT、Few-shot、多次采样都会加 Token 或延迟，我只在评测显示有收益时启用。
**追问 1**：结构化输出解析失败，生产里怎么处理？
**答**：先记录原始响应、模型版本、Prompt 版本、请求 ID；字段缺失可重试一次并把缺失字段和期望类型反馈模型，类型错误转换前先校验别让脏数据写进业务库，枚举越界映射 `UNKNOWN` 或人工审核，不要静默吞掉，重试仍失败走兜底模板并统计失败率。更稳的是用原生结构化输出把 Schema 作为 API 参数传入，切换模型、SDK 或网关后要重验 Schema 兼容性。
**追问 2**：对 reasoning model 还能要求它吐完整思维链吗？
**答**：不该假设能拿到原始 reasoning tokens，按 API 支持使用 reasoning summary；生产里更适合要求输出关键依据、检查步骤和最终结论。另外减少幻觉时 Best-of-N 和一致性检查是两回事，后者比较多次采样的关键字段、引用证据和结论，必要时投票或聚合。

### J2-20 Prompt 注入攻击是什么？常见防护方式有哪些？
**面试官**：Prompt 注入攻击是什么？常见防护方式有哪些？
**我（60 秒口述）**：Prompt Injection 是攻击者把恶意指令放进模型可见输入，试图改变应用原本指令或工具行为，防护必须落在模型之外的权限、隔离、审批三层，Prompt 只能参与不能替代。来源不只用户输入，藏在网页、邮件、文档、RAG 片段和工具返回里的叫间接注入，邮件总结 Agent 被诱导调 `delete_database` 就是典型。三层我按这个顺序搭：执行环境进沙箱、Key 和库权限收窄；用 `---USER_CONTENT_START---` 把 System Prompt 和 User Input 分开；改库、发邮件、转账在执行前中断请求审批。最典型的错答是加一句"不要理会恶意指令"，分隔符只帮模型区分边界，挡不住危险操作。
**追问 1**：工具返回的内容也要做注入防护吗？
**答**：要。用户输入、网页、邮件、文档、图片、RAG、Memory、工具结果、其他 Agent 消息和模型生成的参数都按不可信数据处理。Server 的 `description`、Prompts 模板和返回内容同样要审核，第三方 Skill 和 MCP 的供应链也得审，靠一句"忽略外部指令"覆盖不了完整调用链。
**追问 2**：高危操作审批只弹一句"确定吗"够不够？
**答**：不够。审批要绑定具体工具、参数、资源版本和有效期；HITL 暂停时把 `runId`、Checkpoint、待执行工具、规范化参数、当前 State、`actionId`、工具 Schema 和策略版本都持久化，恢复时重新校验身份、权限、订单状态和任务版本，等待期间任一条件变化就让原确认失效。

### J2-21 为什么 Agent 场景下只优化 Prompt 不够？
**面试官**：为什么 Agent 场景下只优化 Prompt 不够？
**我（60 秒口述）**：因为单条 Prompt 只能约束当前输入，Agent 多轮推理、调工具、读记忆时还会看到历史消息、工具结果和检索材料，输出质量同时取决于 Context、工具定义、权限和校验。一个真实窗口里挤着系统提示词、工具签名和上一步返回、短期长期记忆、RAG 段落，我得按任务决定留哪些、各留多长。工具系统四条原则：名称描述对 LLM 友好、只封装技术逻辑、一工具一件事、能读不给写。System Prompt 两个极端都要避，过度设计塞 if-else 和过度抽象只写"做个有帮助的助手"，中间那段叫 Goldilocks zone。我先拿最小 Prompt 测基线，再按 failure case 一条条补规则。
**追问 1**：多模块协作时，一个 Prompt 硬扛所有任务会怎样？
**答**：要提示词路由，先识别请求类型再选对应链路：无业务上下文直接回复、基础知识走文档检索加 QA、复杂分析走数据分析工具加总结、代码调试走代码检索加诊断 Agent。低置信度请求必须进追问或人工确认流程，像"删数据"这种高风险意图不能被当成普通问答处理。
**追问 2**：基线还没跑通就上记忆分层和复杂检索，坑在哪？
**答**：`do the simplest thing that works`，失败后你会分不清问题来自检索、摘要、工具描述还是模型选型。我会先保存真实调用轨迹建立可回放基线，再去调 Context Assembler 里 `rank` 和 `fit_token_budget` 这两个最关键的步骤，一次只动一个变量。

### J2-22 Context Engineering 要解决哪些问题？
**面试官**：Context Engineering 要解决哪些问题？
**我（60 秒口述）**：核心是调用前的信息组装：哪些规则进消息、哪些证据按需检索、哪些工具当前阶段可见、历史何时压缩、原始结果怎么保留引用，长任务还要跨窗口状态交接，别让摘要丢了约束、版本号和未完成事项。先说为什么会失效：Context Rot 指输入变长噪声增多后关键证据利用不再稳定，Lost in the Middle 指首尾更敏感；但准确说法是长上下文增加筛选难度和成本，退化程度取决于模型和结构，能放进去和能用好是两回事。运行时加载我按三策略选：预检索适合 FAQ，Just-in-Time 先留引用、需要再读，混合策略最常见。
**追问 1**：怎么衡量上下文工程做得好不好？
**答**：五类指标一起看。任务成功率看是否完成目标、是否需人工补救、能否稳定复现成功路径；工具质量看错选漏调参数错误重复调用危险操作拦截率；上下文成本看输入输出 Token、缓存命中率、压缩后信息保留比例；延迟看首 Token、端到端耗时、工具等待、p95/p99；结果质量看幻觉率、证据引用准确率、摘要丢失率、关键字段遗漏率。
**追问 2**：Just-in-Time 有什么代价，选型时看什么？
**答**：代价是工具调用次数和延迟增加，导航能力不足时会沿错误路径继续搜索。我按材料是否稳定、探索空间多大、实时性要求、证据是否必须可追溯来选，而不是比哪种方案"更高级"；另外别把 40% 阈值当通用规律，也别检索回来什么就塞什么、历史能放多少放多少，最后窗口一半是噪声。

### J2-23 静态规则、动态信息、工具结果、记忆应该如何进入上下文？
**面试官**：静态规则、动态信息、工具结果、记忆应该如何进入上下文？
**我（60 秒口述）**：四类各走各的路。静态规则是出厂设置，用结构化 Markdown 拆角色、目标、约束、执行流、输出格式，放 `.claude/rules` 或 `AGENTS.md` 由宿主按作用域加载。动态信息别一股脑塞，稳定文档走预检索，代码库分析和故障排查走 Just-in-Time，现实多是混合。工具结果可裁剪摘要，但排障信息一定要留原始引用，traceId、请求时间、错误码、日志位置、调用参数和结果摘要链接一个都不能丢。记忆按重要性排序并做检索 Trace。落地上按四级 Token 预算排：早期历史压成摘要、RAG 背景二次裁剪、System Constraints 和当前目标放高优先级固定区、工具 Schema 按阶段加载且卸载后要能重新发现。
**追问 1**：规则文件和 System Prompt 是什么关系？
**答**：宿主按自己的加载规则把其中一部分转换成模型上下文，两者不是同一概念。另外 Few-shot 示例别堆太多，3 到 5 个能代表策略差异的 canonical examples 通常比把几十个 edge case 全塞进 Prompt 更有效，示例要说明面对一类输入该采取的策略。
**追问 2**：大规模并发下怎么省重复计费，动态上下文常见故障怎么兜？
**答**：可以配合 Prompt Caching，把稳定 System Prompt 和工具说明作为缓存前缀，但命中率取决于厂商实现、前缀变化和缓存生命周期，得按业务负载验证。动态上下文的故障多出在检索结果错误、记忆过期、工具超时或摘要遗漏证据，`context` 那张降级表里对应给了降级关键词检索、超时重试熔断、保留回查链接、写入前校验等兜底路径。

### J2-24 长任务上下文溢出时，Compaction、结构化笔记、Sub-agent 分别怎么用？
**面试官**：长任务上下文溢出时，Compaction、结构化笔记、Sub-agent 分别怎么用？
**我（60 秒口述）**：三者都是抵抗上下文腐化的手段，但各管一段：Compaction 保持连续对话的连贯、结构化笔记保存可恢复状态、Sub-agent 隔离专门任务上下文，按任务形态选、可组合。Compaction 在窗口快满时把历史压成摘要再接着走，保留架构决策和未解决 Bug、移走冗余工具结果，难点全在取舍，留太多没意义、留太少丢关键。结构化笔记让 Agent 把进展写到外部 `NOTES.md`，重置后读回来继续。Sub-agent 把检索放独立上下文，主 Agent 只收汇总，回传摘要通常约 1000 到 2000 Token。短任务还没出现上下文膨胀时，我不会引入这套复杂记忆层。
**追问 1**：Compaction 和 context resets 是一回事吗？
**答**：不是。Anthropic 发现 Sonnet 4.5 在上下文快填满时变犹豫甚至提前收工，出现"上下文焦虑"，只压缩不够，于是直接清空窗口、用结构化交接文档保留关键状态再做 context resets。代价是交接文档一旦漏掉已改文件、失败原因或下一步验证命令，新 Agent 就会从错误状态继续。
**追问 2**：Sub-agent 汇总会丢证据吗，笔记算不算长期记忆？
**答**：会丢，所以需要保留 Artifact URI 供回查。边界也要讲清：笔记是"可恢复状态"，不等于长期记忆；只把聊天记录写进 Redis 无法恢复整条 Workflow，恢复时必须能重建依赖关系和已确认产物。这三条我都依赖先记录每轮实际进入窗口的消息这一可回放基线。

### J2-25 MCP 解决什么问题？为什么常被类比成 AI 领域的 USB-C？
**面试官**：MCP 解决什么问题？为什么常被类比成 AI 领域的 USB-C？
**我（60 秒口述）**：MCP 解决的是同一个工具交给多个 Host 时的重复集成，用统一协议让 Host 自动发现并调用外部能力，所以叫 AI 领域的 USB-C。以前得手动维护"工具名到执行函数加 JSON Schema"的映射，同一个 Git 工具接 Claude Desktop、Cursor、自建 Agent 要各写一层适配，参数或鉴权一变多个客户端跟着改。Anthropic 2024 年 11 月推出，基于 JSON-RPC 2.0，Server 暴露能力、宿主连上就自动发现注册。更准确说它是 Client 和 Server 之间的通信协议，Host 承载用户交互和模型调用。我想强调它统一了接入方式，但不替代鉴权、审计、日志、版本和限流，更不是给模型加内置插件。
**追问 1**：为什么说模型不会因为接 MCP 获得内置插件能力？
**答**：因为 MCP 改的是 Host 与外部工具、数据源之间的发现和调用方式，模型还是只输出调用意图，执行在 Server 和后端。还有个边界：一个 Server 在某个 Host 里可用，不代表换到另一个 Host 后仍支持 Sampling、Elicitation、Tasks 这些可选能力，所以不能只按某个客户端的表现下结论。
**追问 2**：接第三方 Server 前，版本口径要确认什么？
**答**：协议 revision、SDK 版本和 Host 能力三者一起确认。当前稳定是 2026-07-28 revision，改为无状态自描述请求、移除 `initialize`/`initialized` 握手和 `Mcp-Session-Id`、要求 Server 实现 `server/discover`；上一代 2025-11-25 还用初始化握手和传输层会话，兼容旧版客户端和 SDK 可能仍在用，排查"工具未出现"先查这个。

### J2-26 MCP Client、MCP Server、Host 分别是什么？
**面试官**：MCP Client、MCP Server、Host 分别是什么？
**我（60 秒口述）**：Host 是用户使用的 AI 应用，Client 在 Host 内部负责和 Server 交换协议消息，Server 由开发者编写、对外暴露能力，Server 后面的数据源不属于 MCP 协议角色。Host 比如 Claude Desktop、Cursor、VS Code 插件；一个 Host 可连多个 Server，通常每个 Server 对应一个 Client；开发者主要写 Server，文件读取、SQL 查询、内部工单都由它暴露。一次调用时序是模型生成调用、Host 交给 Client、Client 通过 JSON-RPC 请求 Server、Server 查数据源、结果沿原路返回。我会特别提一句：Server 收到的参数必须视为不可信输入，读文件限目录、SQL 参数化、高危操作审批、返回脱敏，这些协议不替你做。
**追问 1**：为什么数据源不算 MCP 角色，Host 和 Client 也不能混？
**答**：数据源是 Server 内部的本地文件、数据库、内部平台或第三方 API，协议只定义到 Server 这一层；Client 是 Host 内部的协议组件，Host 只通过 Client 调 Server，查库和请求 API 的底层实现留在 Server 内。分层清楚了，连接失败、协议错误、工具执行失败才好分开排查。
**追问 2**：Roots、Sampling、Elicitation 到底是谁的能力？
**答**：是 Client 侧提供给 Server 使用的能力，别记反。Roots 是 Host 通过 Client 告诉 Server 当前工作范围预期在哪些文件系统根目录，是能力协商和范围提示，不会自动形成文件系统沙箱，Server 仍要做路径规范化、越界检查和 OS 级权限隔离；Sampling 让 Server 请求 Host 侧 LLM 做一次生成，Elicitation 让 Server 执行中向用户补问信息。2026-07-28 还把 Roots、Sampling、Logging 标了 deprecated。

### J2-27 MCP 的 Tools、Resources、Prompts 分别解决什么问题？
**面试官**：MCP 的 Tools、Resources、Prompts 分别解决什么问题？
**我（60 秒口述）**：三类原语分别对应动作、上下文、任务入口。Tools 是 LLM 主动调用的函数，查库、发消息、创建工单，会主动执行逻辑、可能改外部状态；Resources 是按需读取的只读数据，本地文件、日志片段、数据库 Schema；Prompts 是可复用模板，像按团队规范做代码审查。关键差别是 Tools 通常由模型选择调用，Resources 和 Prompts 的展示选择还可以由 Host、UI 或应用逻辑决定。用生活类比，Resources 像食材和菜谱，Tools 像切菜开火下单，Prompts 像家里少放辣的固定偏好。技术群聊 MCP 常只讲 Tools，我会主动补另外两类；大多数 Server 先只提供 Tools 就够。
**追问 1**：把只读上下文做成 Tool 会有什么问题？
**答**：权限模型不同，只读数据和可执行动作要分开，别把 Resources 当工具用。还有个高频易混：MCP Server 对外暴露工具时内部还是用 JSON Schema 描述参数规范，JSON Schema 是数据格式、MCP 是通信协议层，两者解决的问题不同，不能说成谁替代谁。
**追问 2**：Prompts 模板会不会有安全隐患？
**答**：会。它和 `description`、返回内容一样可能夹带提示词注入，需要审核，第三方 Skill 和 MCP 供应链也要一起审。而且通过 MCP 接入的工具本质是副作用入口，读文件、查询数据库、发请求、修改配置要分别区分权限、调用条件和审计边界，不能因为只是"模板"就默认可信。

### J2-28 MCP 和 Function Calling 有什么区别？
**面试官**：MCP 和 Function Calling 有什么区别？
**我（60 秒口述）**：Function Calling 让模型输出调哪个工具、参数是什么的结构化意图，MCP 规定宿主如何发现外部能力并把请求接到实际工具，一个管数据格式与意图、一个管通信接入。OpenAI 叫 Function Calling、Anthropic 叫 Tool Use，模型借它输出 `{ "name": "read_file", "arguments": ... }` 这类结构化数据；MCP 负责工具从哪个 Server 发现、请求怎么传、结果怎么回；Agent 关心任务下一步，读结果后决定继续调用还是结束。一句话链路：FC 产生命令，MCP 传递命令并连接工具，Agent 决定何时继续何时结束。FC 七步里业务侧校验字段、必填项、用户权限、订单归属和幂等键这步最易漏，恰是权限审计落点。
**追问 1**：说"MCP 是 Function Calling 的升级版"错在哪？
**答**：两者在不同层次、常一起出现，不是替代关系。看侧重就清楚：让模型判断要不要查天气重点是 FC 把意图转成结构化参数，让 Claude Desktop 读本地文件重点是 MCP 提供宿主和文件系统之间的标准接口，让 AI 自动排查线上故障重点是 Agent 的多步决策和结果反馈。
**追问 2**：只给 Schema 文本、不配生成约束会怎样？
**答**：模型仍可能返回不合规内容。JSON Mode 管语法、JSON Schema 管契约、Structured Outputs 把契约前移到模型生成阶段，三层约束要分清；而且 FC 或 Tool Calling 只让模型生成结构化调用意图，真正执行工具的是后端服务、Agent Runtime、MCP Host 或供应商托管环境，模型自己不执行。

### J2-29 生产级 MCP Server 要做哪些安全治理？
**面试官**：生产级 MCP Server 要做哪些安全治理？
**我（60 秒口述）**：Demo 里装一个 Server、问一句、拿结果的链路很短，生产要补齐五大类，而且安全必须落在 Server 代码层，不能靠相信模型。Schema 和版本上，时间字段是 ISO-8601 还是时间戳、金额单位元还是分、分页默认值都写进 Schema 并据此校验；观测上一条回答可能经过多个 Server 和工具，Trace ID 和结构化日志要记参数、耗时、结果摘要、错误码；权限上能访问哪些文件库 API、能否写生产、能否发邮件都明确授权，删除修改发送还要二次确认和回滚预案。成本和依赖也别漏，Token、检索、第三方 API 要能关联到用户业务线工具，工具接口不兼容变更得有版本号、灰度和兼容性测试。我会避开 `execute_sql` 这类万能工具，路径规范化、SQL 参数化、脱敏、限速熔断都由 Server 自己落实。
**追问 1**：本地 stdio 模式有个很容易踩的坑是什么？
**答**：stdout 是 JSON-RPC 消息通道，不能拿来打印调试日志，一行 `print()` 就可能破坏消息格式导致 Host 解析失败或 Server 断连，调试日志得写 stderr 或文件。本地 Server 还应放 Docker、cgroups、namespace 隔离，第三方 Server 别直接裸跑。
**追问 2**：排查工具调用失败时怎么区分层次？
**答**：区分连接失败、JSON-RPC 错误和工具返回的 `isError: true`，仅收到 HTTP 200 不代表工具执行成功，参数错误能落到 `-32602 Invalid params` 这类错误码。传输上本地工具本地文件个人使用优先 stdio，团队服务远程 API 多用户访问优先 Streamable HTTP，涉及写操作和敏感数据不管哪种都要额外鉴权、限流、审计。

### J2-30 Agent Skills 是什么？它和 Prompt、MCP、Function Calling 的边界是什么？
**面试官**：Agent Skills 是什么？它和 Prompt、MCP、Function Calling 的边界是什么？
**我（60 秒口述）**：Skill 是可被 Agent 发现、按需读取的任务说明，解决这类任务该按什么规则做，它不提供工具能力，本质更接近一次按需的上下文注入。用"帮我分析这份报表"拆最清楚：用户说的话是 Prompt，模型决定调 `read_file` 生成结构化参数是 Function Calling，`read_file` 由 MCP Server 提供时 MCP 负责连接，"先确认字段含义再找异常值最后给业务结论"属于 Skill。执行链五步：宿主把可用 Skill 简短描述放进上下文、模型判断命中、宿主加载完整 `SKILL.md`、模型按流程调工具读资料写结果。工具不是 Skill 必备部分，传统 Toolkits 是黑盒，Agent Skills 白盒加延迟加载才是关键差异。我会把它和全局项目约定 `AGENTS.md` 分开讲。
**追问 1**：为什么说 Skill 不是"工具集合"？
**答**：因为工具能力来自 Function Calling 和 MCP，Skill 只描述处理顺序和约束。那句边界我常背：FC 表达调用意图、MCP 连接外部能力、Agent 决定下一步、Skills 保存完成某类任务所需的流程和经验。反例是 sanyuan-skills 的 Code Review Expert，只规定从 SOLID、安全、性能维度审查，不提供任何工具。
**追问 2**：Skill 和 Prompt、和 `AGENTS.md` 的区分在哪？
**答**：Prompt 承载这一次请求，Skill 保存这类任务反复要用的操作说明，不是为当前对话临时拼的一段 Prompt；全局项目约定留在 `AGENTS.md`，随任务加载的部分才放 Skill。目录上 `.claude/skills/code-reviewer/` 里 `SKILL.md` 触发时加载、`scripts/` 不进上下文、`references/` 和 `assets/` 按需加载。

### J2-31 Skills 为什么要延迟加载？
**面试官**：Skills 为什么要延迟加载？
**我（60 秒口述）**：因为上下文窗口有限，而且能装下不等于能用好，把所有 Skill 一次性塞进去会造成 Context Rot。上下文越长信息越杂，模型利用的稳定性越可能变差，Lost in the Middle 又让中间信息更易被忽略，所以 Skill 不该写成资料库，正确做法是渐进式披露：先给轻量目录，用到哪块再加载哪块。具体三层：广告层启动时只加载 `name` 和 `description`；指令层判断相关才读 `SKILL.md` 正文，放流程、规则、边界和关键示例，正文建议 500 行以内；资源层正文引用的 `references/`、`scripts/` 按需读取或执行。延迟加载不是少写内容而是分层，它和 Just-in-Time、Progressive Disclosure 是同一思路。
**追问 1**：延迟加载依赖什么才不出错？
**答**：依赖 `description` 质量。Agent 不会先把每个 `SKILL.md` 都读一遍，而是先看描述判断该不该加载，描述写得不好，这个 Skill 就没法在该调用时被调用。启动阶段通常也只有 `name` 和 `description` 参与路由，正文加载后会与系统提示、用户请求和已有资料共用上下文空间，所以正文别写太长。
**追问 2**：多层引用会有什么 Badcase？
**答**：必需规则经过多层引用，比如 `SKILL.md → advanced.md → details.md` 把最关键规则藏在最后一层，Agent 很难定位。我会把基本用法和下一层资料都列在主文件里，参考文件较长时在开头列目录。另外 `context` 里 `@` 引用是启动时全量加载、不减少上下文消耗，和 Skills 延迟加载机制完全不同，别混为一谈。

### J2-32 Skill 路由怎么做？为什么它和 RAG 相似但目标不同？
**面试官**：Skill 路由怎么做？为什么它和 RAG 相似但目标不同？
**我（60 秒口述）**：路由是召回候选、重新排序、作出决策三段，把请求映射到可直接加载的 Skill 集合。只有三五个 Skill 时模型读 `description` 就够选；涨到几十个我按三阶段：粗召回把请求与名称、描述、典型 Query 向量化取 top-5 余弦相似度，精排比较命中情况且高风险 Skill 用更高阈值，决策阶段最高分满足阈值才加载、分数整体偏低就不加载任何 Skill 走默认流程。同一请求含互不依赖任务要先拆再路由。它和 RAG 同样用向量相似度和重排，但 RAG 取回证据内容，Skill 路由要得到的是加载哪个 Skill 的决策，可能一个、多个或零个，还要叠加高风险阈值和任务拆分。
**追问 1**：为什么路由索引不能写进所有 `SKILL.md`？
**答**：Agent Skills 规范没有规定通用的 `triggers` frontmatter 字段，各宿主也不保证读自定义字段。自建调度器可以把典型 Query 放进独立路由索引，和 `name`、`description` 一起向量化，但第三方宿主只使用它明确支持的字段；几十个 Skill 用 NumPy 在内存算相似度就够，耗时主要来自外部 embedding API，先缓存 Query 向量，到数百数千再评估 ANN 索引。调度器里路由引擎不读 Skill 正文、加载器不参与打分，改正文才不会动召回结果。
**追问 2**：请求只写"帮我处理一下"，路由器该怎么办？
**答**：保留默认流程，不猜测用户要做数据库迁移或生产操作，语义线索不足就不加载任何 Skill。这正好点出和 RAG 的目标差异：RAG 回答检索什么、结果怎么放进上下文，取回文本证据；Skill 路由输出是 Skill 集合且允许零个，Claude Code 里还可以用 `/skill-name` 主动调用或让模型按任务选择。

### J2-33 写一个 `SKILL.md` 最容易踩哪些坑？
**面试官**：写一个 `SKILL.md` 最容易踩哪些坑？
**我（60 秒口述）**：`SKILL.md` 是 YAML 前置元数据加正文两段式，元数据里 `name`、`description` 负责发现与触发，正文放流程、约束、示例和失败处理。最常见的坑我数得出来：把它当 README 写、写得太全、给 Agent 太多选择、术语来回换、让 LLM 做确定性工作、description 缺触发条件。`name` 最多 64 字符、小写字母数字连字符、优先动名词；`description` 要说清做什么和什么场景用，最好带用户会说的词。正文只留默认方案、项目约定、输入输出和失败处理，私有约束写清比如"正式查询必须加 `WHERE deleted_at IS NULL`"。格式转换和精确计算交给脚本，清单每项都得是可核验动作，"保证质量"不能当验证节点。
**追问 1**：给 Agent 太多选择会怎样？
**答**：只罗列 pypdf、pdfplumber、PyMuPDF、pdf2image，Agent 判断不了普通 PDF 和扫描版分别走哪条路径，可能在文本 PDF 上误用 OCR。正确写法是默认路径和例外条件一起给："默认使用 pdfplumber 提取文本，如果是扫描版 PDF 需要 OCR，再改用 pdf2image + pytesseract"；自由度也分三档，操作脆弱出错代价高的低自由度任务要给精确命令并写明不能改、不能加参数。
**追问 2**：脚本读不到必需输入文件时该怎么返回？
**答**：返回明确错误，而不是创建空文件掩盖输入缺失，比如 `raise FileNotFoundError(f"必需输入文件不存在：{path}。请检查路径或先生成该文件。")`；反例 `return open(path).read()` 让 Agent 只能猜原因。另外术语前后要一致，前文"API 端点"后文别改成 URL、API 路由、路径，名称不一致会制造歧义；主文件过长时把只在特定步骤用的内容拆到 `references/`。

### J2-34 Harness Engineering 是什么？它和 Prompt Engineering、Context Engineering 有什么关系？
**面试官**：Harness Engineering 是什么？它和 Prompt Engineering、Context Engineering 有什么关系？
**我（60 秒口述）**：Agent Harness 是跑在大模型外部的一套执行系统，负责组织上下文、提供工具和执行环境，把权限控制、状态管理、结果验证与失败恢复接进任务流程。三者不适合并列比较，更像一层套一层：Prompt Engineering 解决怎么把指令说清楚，Context Engineering 解决该给 Agent 看什么，Harness Engineering 解决系统怎么持续执行、纠偏、观测和恢复。简单任务改句文案 Prompt 就够，需要外部知识时 Context 更重要，到长链路、可执行、低容错的商业场景 Harness 才成主要矛盾，因为 Agent 要的不只是会回答，还得能执行、验证、回滚。组件可以反推：记不住历史补记忆系统，执行不了代码给 Bash 和沙箱，判断不了对错给测试和浏览器自动化。Prompt 提供不了文件访问、测试执行和失败恢复，这些都得 Harness 承担。
**追问 1**：有没有证据说明瓶颈常常不在模型？
**答**：有，Can.ac 一次编码评测里 Grok Code Fast 1 仅替换文件编辑接口，得分就从 6.7% 升到 68.3%，模型参数没变，差别在接口提供了什么操作、怎样返回结果、错误能否被下一步利用。这类差异也解释了重复调工具、忽略约束、长任务丢状态，为什么不能只靠换模型或补一句提示词解决。
**追问 2**：Harness 是不是越厚越好、能不能照搬别家？
**答**：不是，最适合当前任务的 Harness 不一定是模型后训练时用的那一套，选型以任务的工具、约束和验证需求为准。LangChain 在 Terminal Bench 2.0 排行榜还观察到 Opus 在 Claude Code Harness 下的得分低于它在其他 Harness 中的得分，这种 model-harness 耦合得靠实测，不能照抄别人的配置。

### J2-35 为什么说 Agent = Model + Harness？
**面试官**：为什么说 Agent = Model + Harness？
**我（60 秒口述）**：模型只负责推理和生成，不会自己保存跨会话状态、执行命令、读测试结果或区分该保留哪些信息，这些都得由模型之外的 Harness 补齐，所以这条公式提醒运行环境同样决定任务能否持续执行。Harness 管系统提示词、工具调用、文件系统、沙箱、编排、Hooks、反馈回路和约束，把任务状态、操作入口、执行环境和安全边界接起来，使模型输出转成可验证的动作。LangChain 把它拆成文件系统、Bash 执行、沙箱、记忆机制、上下文压缩五块。排查时我除了看模型输出，还要看上下文是否完整、工具是否可用、执行环境是否受控、失败后能否恢复。只有目标而没有文件权限、验证命令和失败处理，任务仍然没法无人值守执行。
**追问 1**：这条公式和 `Agent = LLM + Planning + Memory + Tools` 冲突吗？
**答**：不冲突，视角不同，一条拆"能力组件"、一条拆"模型 vs 运行环境"，两条可以同时成立，面试里主动点明会加分。另外别把 Harness 理解成某个框架或协议，六层检查框架是本文为便于检查系统是否缺项归纳的分析框架，不是协议或业界统一标准。
**追问 2**：有没有不改模型、只改 Harness 就涨分的证据？
**答**：有，LangChain 调整系统提示词、工具和中间件、借追踪分析优化验证回路后，Terminal Bench 2.0 从当时前 30 名之外进到前 5 名、得分从 52.8% 升到 66.5%，模型没有更换。反过来 Opus 在 Claude Code Harness 下得分低于其他 Harness，也说明环境和模型是耦合的，换环境得重测。

### J2-36 JavaGuide AI Agent 专题归纳的 Harness 六层检查框架分别解决什么问题？
**面试官**：JavaGuide AI Agent 专题归纳的 Harness 六层检查框架分别解决什么问题？
**我（60 秒口述）**：六层是从信息边界到故障恢复的分析框架，用来检查系统是否缺项，不是协议或业界标准。我用新员工类比记：L1 信息边界层是岗位说明，定角色目标、裁剪无关信息；L2 工具系统层是办公工具，选工具、控调用时机、提炼结果；L3 执行编排层是标准操作流程，让模型按理解目标到检查的轨道推进；L4 记忆与状态层是项目管理系统和笔记本，独立管当前状态、中间产物和长期记忆；L5 评估与观测层是质检流程，建独立于生成的验证机制；L6 约束校验与恢复层是红线规则和应急预案，拦截错误并重试回滚降级。起步不用同时建六层，我先补 L1 和 L6 最划算，等多步骤执行再补编排、状态和观测。
**追问 1**：落地优先级具体怎么排？
**答**：P0 是创建并持续维护 `AGENTS.md`、写报错自带修复方法的自定义 Linter、把团队知识放进仓库；P1 是分层管理上下文、建进度文件和功能列表、给 Agent 端到端验证能力、控制上下文利用率；P2 才是 Agent 专业化分工、定期垃圾回收和可观测性集成。Level 0 升到 Level 1 已经能覆盖一部分高频错误，不必以 Level 4 自治循环为起点。
**追问 2**：`AGENTS.md` 该写多厚？
**答**：别当超级 System Prompt 写。很多团队一上来把所有规则都塞进去，结果上下文被撑爆、Agent 反而更容易跑偏；OpenAI 的做法更克制，只当目录用、大约 100 行，详细规则放子文档按需加载。Hashimoto 更极端，Ghostty 的 `AGENTS.md` 每一行都对应一个过去的 Agent 失败案例，是持续积累的防错系统。

### J2-37 模型能力升级后，Harness 里的某些机制为什么需要重新验证？
**面试官**：模型能力升级后，Harness 里的某些机制为什么需要重新验证？
**我（60 秒口述）**：因为 Harness 的每个组件都编码了"模型自己做不到什么"的假设，模型变强后这些假设可能失效，冗余机制只会增加上下文和编排成本，所以要重新压测并删除。原文那句我记得很牢：每个组件都编码了一条关于模型不能独立做什么的假设，这些假设值得压力测试。Anthropic 从 Sonnet 4.5 换到 Opus 4.6 后，Sprint 机制可以完全移除，Evaluator 从每个 Sprint 检查变成最后只检查一次。我的落地动作是每次换模型、换 SDK、换网关后重跑回归集与对照实验，逐组件做消融，比质量、耗时、Token、失败率，保留能捕获真实错误的、移除只加成本的。model-harness 耦合是另一面，换环境得重测。
**追问 1**：只答"要重新测"为什么不够？
**答**：说不出机制。核心是组件等于一条对模型能力的假设；而且工具接口字段、枚举或返回结构的不兼容变更同样会改变模型判断，Prompt、模型或 API 版本一变都要重跑回归集，不能假设旧 Prompt 会保持同样表现。
**追问 2**：重新验证时，哪类机制最该先动？
**答**：先动那些"限制它别做错"的，比如逐轮 Evaluator、额外 Sprint、多 Agent 校验环节。但功能正确性的独立验证仍是空白，Böckeler 批评用 AI 生成的测试验证 AI 生成的代码像"用同一双眼睛检查自己的作业"，所以别把独立验证信号也一并删掉。

### J2-38 上下文污染、代码熵积累、工具调用可靠性分别怎么治理？
**面试官**：上下文污染、代码熵积累、工具调用可靠性分别怎么治理？
**我（60 秒口述）**：这三者分别是信息边界加清理、机械化约束加垃圾回收、工具接口加反馈回路加验证闭环的问题，都不能靠换模型或补一句提示词解决。上下文污染是早期判断、重复工具结果持续挤占窗口，靠分层管理、Compaction、结构化笔记和 Sub-agent，再监控利用率找压缩触发点。代码熵积累是生成越多重复逻辑和文档不一致越多，靠自定义 Linter 和结构测试机械化执行，OpenAI 后来改成后台 Agent 定期扫描提交清理 PR。工具可靠性看接口能不能让模型表达意图、错误能否被下一步利用。验证闭环还得独立于生成过程，Anthropic 用 Planner、Generator 加独立 Evaluator 实际点击应用打分，专治 Agent 自信地夸自己做得好。
**追问 1**：为什么说"不能机械化执行的约束等于没有"？
**答**：原话是 If it cannot be enforced mechanically, agents will deviate，只写在文档里 Agent 迟早偏离。所以定 `Types → Config → Repo → Service → Runtime → UI` 固定分层、违反时 Linter 不只报错还告诉 Agent 怎么改；测试框架日志也要写成 grep 友好的单行格式如 `ERROR: [reason]` 并写进文件，Carlini 那句"我是在为 Claude 写这个测试框架，不是为自己写"就是这个意思。
**追问 2**：40% 上下文利用率能直接设成告警线吗？
**答**：不能，它来自 168K Token 窗口的特定观察，Smart Zone 约 0–40%、Dumb Zone 超过 40% 会出现幻觉增多、兜圈子、代码变差，但 40% 只是待验证的初始观察值，得有回放数据再定。另外 Garbage Collection 要和上下文治理并行做，生成速度高于清理速度时，后续 Agent 检索到的上下文也会跟着变差。

### J2-39 Agent 工程里为什么需要评测器、验证器和任务状态管理？
**面试官**：Agent 工程里为什么需要评测器、验证器和任务状态管理？
**我（60 秒口述）**：因为模型输出不等于可交付结果。需要评测器和验证器提供独立于生成的做对了没有的信号，任务状态管理保证长任务可恢复、可观测、可验收，否则只看最终回复会被语句流畅但工具调用失败的结果骗过。六层里 L5 的职责就是建独立于生成过程的验证机制，判断自己有没有做对本是模型做不到的事，由 Harness 用沙箱、测试工具、浏览器自动化补上。反例很典型：检索工具调用失败，模型仍能生成结构完整的报告。所以验收要核对必要工具是否调用成功、每角色是否按契约交付、引用能否回到原始材料、归并节点有没有隐瞒失败分支。测试退出码、CI 状态、截图对比才是完成证据，Agent 的说明只能作为补充。
**追问 1**：把验证器做成"让模型自己再检查一遍"行不行？
**答**：不行，这等于用同一双眼睛检查自己的作业，AI 生成的测试验证 AI 生成的代码破不了两者共享的假设。功能正确性要靠独立信号，比如测试退出码、CI 状态、截图对比，或者由一个 Agent 实现、另一个 Agent 在独立上下文中检查。
**追问 2**：Trace 里怎么把一次运行串起来？
**答**：根 Span 记 `runId`、租户、任务主题、代码和 Prompt 版本，角色任务作子 Span 带父任务 ID、Agent 角色、模型、Skill、状态、`attempt`、停止原因；一次重试继续挂在原角色任务下并保留新 `attempt`，不能伪装成全新调用；人工审批或异步恢复后可创建新 Trace，但必须沿用同一 `runId`。前端 SSE/WebSocket 事件流不承担任务状态保存。

### J2-40 一线团队做 Agent 工程化时，共同遇到的难点是什么？
**面试官**：一线团队做 Agent 工程化时，共同遇到的难点是什么？
**我（60 秒口述）**：共同难点集中在几件没有通解的事上：上下文怎么给、约束怎么机械化执行、生成物熵怎么清理、功能正确性怎么独立验证、Harness 该厚该薄、单 Agent 还是多 Agent，公开案例不少但让人信服的方法论还不多。绿地和棕地差别很大，对缺少模块边界、技术债重的老项目，得先让编译测试流程可重复执行，再加局部规则和结构检查，最后才扩大自动执行范围。四家实践放一张表讲：OpenAI 把 `AGENTS.md` 当目录用约 100 行、Stripe Minions 的 Toolshed 近 500 个工具但每个 Minion 只拿筛后子集、Anthropic 用 context resets 和结构化交接、Hashimoto 坚持一次只跑一个 Agent。我会明确说这些是公开案例、都带团队投入限定，不是我自己的项目指标。
**追问 1**：单 Agent 还是多 Agent，你站哪边？
**答**：不站队，规模决定。Hashimoto 坚持单 Agent 深度参与、明确说不想跑多个，Carlini 用 16 个并行 Agent 做 C 编译器，两者都成了；`agent-basis` 和 `multi-agent` 都主张先简单后复杂、用对照测试验证收益，小项目单 Agent 往往够用，大项目更容易走向专业化分工。
**追问 2**：把这些实践搬到自己团队，最容易犯的错是什么？
**答**：直接照搬数字和"人只在最后审查"。原文三处都加了限定，Stripe 那套靠的是 Devbox、编排状态机、集中式 MCP 和反馈回路一整套成熟工程环境，不是某个超强 Agent；Böckeler 也提醒模板能减少重复配置，却替代不了项目自身的测试、模块边界和运行数据。棕地项目先把编译测试跑可重复，比什么都实在。

### J2-41 为什么 AI 系统需要工作流？
**面试官**：为什么 AI 系统需要工作流？
**我（60 秒口述）**：单轮对话能回答问题，但很难稳定地交付结果。线上真实任务要检索、调工具、结构化输出、校验、失败重试、不满意再来一轮，靠一段超长 Prompt 塞全部逻辑早晚会炸，得有可分支、可循环、可观测的执行路径。加了 LLM 后三个直接问题：下一步不唯一要根据当前结果动态决策，结果不理想要自动修正而不是直接失败，中间状态必须记录否则难调试追踪恢复。拿写一篇文章说，结构化为审查、修改、再审查并设停止条件，稳定性明显更好。我的判断是好工作流关键看 Node、Edge、State 的抽象能否经得起复用，和步骤多少关系不大，宁可抽象成 `DraftNode`、`ReviewNode`、`ReviseNode`、`ExitNode` 四个稳定职责。
**追问 1**：为什么"超长 Prompt 塞全部逻辑"一定会炸？
**答**：因为一旦要表达"下一步不唯一"或者"不满意就再来一轮"，线性列表就不够用，自然会落到 Graph 结构和 Loop 回溯。而且中间状态没被记录，出问题追不回；`workflow:42` 也提醒传统流程并不线性，BPMN 2.0、Camunda、Temporal、Airflow 都能编排人工任务、外部 API 和非确定性活动。
**追问 2**：AI 工作流比传统引擎多出的麻烦具体在哪？
**答**：部分节点输出由 LLM 生成，"结果是否达标"也可能需要模型或评分器在运行时判断，同一节点因输出不确定性反复执行，所以经常出现回边；节点间传递的不只是参数，还有上下文、草稿、评分、错误信息和历史轮次。控制权放在代码或图结构、还是交给模型运行时决定，是核心差别。

### J2-42 Workflow、Graph、Loop 三者是什么关系？
**面试官**：Workflow、Graph、Loop 三者是什么关系？
**我（60 秒口述）**：一句话收束：Workflow 是目标与过程，Graph 是结构与载体，Loop 是图上的控制模式，同一件事的三个观察角度，不是三个可替换方案。先生成初稿再审核、不达标就修改、达标输出描述的是 Workflow；把生成、检查、修正画成节点连线共享同一份状态得到 Graph；规定审核不通过回修改、直到评分达标或达上限定义的是 Loop。落到结构是图三要素：Node 读状态执行逻辑写回结果，Edge 含顺序、条件、动态路由、循环、终止、并行边，State 是持续被读写的共享上下文，`input`、`messages`、`tool_result`、`next_step` 都挂上面。只看 Node 和 Edge 是能跑起来的路径图，加上 State 才能运行时决策。State 是工作记忆不是日志，字段按业务含义分块。
**追问 1**：条件边和动态路由是不是非此即彼？
**答**：不是，是连续谱系。条件边候选集设计时确定但选择逻辑可依赖运行时状态如 LLM 评分，动态路由候选集本身运行时才确定。框架上 Spring AI Alibaba 用 `OverAllState` 加 `KeyStrategyFactory`、`addConditionalEdges(source, fn, map)`，LangGraph 用 `TypedDict` 加 `Annotated[type, reducer]`、`add_conditional_edges`，抽象的是同一套结构。
**追问 2**：答成"三者选型对比"为什么跑题？
**答**：因为它们是同一链路的三个视角，Graph 是 Workflow 的结构表达、Loop 是 Graph 上的回溯控制，不是三选一。原文那句总结可以直接用：Workflow 描述任务怎样完成，Graph 用 Node、Edge 和 State 表达执行结构，Loop 则是 Graph 上的回溯控制；另外 State 粒度别走两个极端，太粗谁改了哪个字段不好查，太细每个节点都要拼。

### J2-43 Graph Loop 和 Agent Loop 有什么区别？
**面试官**：Graph Loop 和 Agent Loop 有什么区别？
**我（60 秒口述）**：Agent Loop 是 Agent 的顶层运行引擎，整个 Agent 在 while 里反复推理、行动、观察直到完成；Graph Loop 是 Graph 内部特定节点子集通过回边形成的迭代修正循环，两者可嵌套，Agent Loop 是外层、Graph Loop 嵌在某个节点或子图内。Loop 也不等于多跑几次，是当某条边按当前状态把控制流送回先前节点，重点在判断是否达标，循环内部让 LLM 评分、不满足就打回重写。两种形态：固定次数像 for 最多重试 3 次，条件驱动像 while 评分低于 80 分继续改，AI 场景后者更常见但一定叠加固定上限。一个可靠 Loop 必含继续条件、退出条件、安全边界，嵌套两层的作用域和计数器还得各自独立。
**追问 1**：这题的标准答案怎么背？
**答**：Agent Loop 是 Agent 的顶层运行引擎（推理→行动→观察循环），Graph Loop 是 Graph 内部的回溯控制模式（特定节点子集通过回边迭代修正），两者可以嵌套。再补 `README` 的三层循环表：内层 Agent Loop、工作流图上的回边、外层 Loop Engineering，别把图上的回边和外层工程循环混为一谈。
**追问 2**：外层 Loop 和内层循环能共用一套计数器吗？
**答**：不能，停止条件本就不同。内层发生在一次任务执行中，停止是"不再需要工具、返回最终结果"；外层 Engineering Loop 在任务结束后由调度系统工作，停止是达成目标、超预算或失败转人工。代码上 `review → revise → review` 第三次审核后无论评分是否达标都退出，`iteration_count >= 3` 跳 ExitNode，内层 Agent Loop 则常见 10–20 轮上限。

### J2-44 外层 Loop 由谁触发下一轮：CI 事件、定时任务、目标检查还是人工审批？
**面试官**：外层 Loop 由谁触发下一轮：CI 事件、定时任务、目标检查还是人工审批？
**我（60 秒口述）**：四种触发分别对应时间驱动、事件驱动、目标驱动、人工审批四类 Loop，差别主要在谁触发下一轮。时间驱动每 N 分钟或每天，适合 PR babysit、CI 检查、日志巡检，用 `/loop`、cron；事件驱动是 CI 失败、Issue 创建、PR 更新，适合故障分拣和告警摘要，走 Webhook、GitHub Actions；目标驱动是上一轮结束检查目标是否满足，适合修测试、迁移 API，用 `/goal`、Stop hook；人工审批是关键动作前停下确认，适合高风险改动和发布。Claude Code 两个命令一句话记：`/loop` 决定下一次什么时候醒，`/goal` 判断什么时候算做完。生产上 Loop Engineering 落在触发、目标、上下文、行动、观察、状态、停止七项。
**追问 1**："每天 9 点运行"为什么还不够？
**答**：它只提供了启动时间。CI 链接和失败日志确定排查入口，最小复现命令和测试结果决定是否继续，PR diff 与人工确认状态决定改动能否进下一步；没有这些外部证据，定时任务只能重复发送同一个 Prompt。七项里"触发"要写清是手动命令、定时任务、CI 失败、PR 创建、Issue 更新还是某个消息事件。
**追问 2**：`/loop` 能当生产调度器吗，跑之前要收紧什么？
**答**：不能，它是 session-scoped 的临时调度，只在 Claude Code 运行且空闲时触发，终端关闭、会话退出都受影响，循环任务最多 7 天自动过期；跨机器长期稳定得用 GitHub Actions、CI/CD 或自己的调度系统。跑 `/loop` 前收紧权限、写清轮询目标和停止条件，关键路径先 commit 再让 Agent 改；跑 `/goal` 前把完成条件写成可验证结果，要求展示测试、build 或 diff 检查结果，Stop hook 或 Agent SDK 还能在每轮结束后做确定性检查、权限拦截和状态落盘。

### J2-45 外层 Loop 与一次任务内部的 Agent Loop 有什么区别，状态和验证结果怎样交接？
**面试官**：外层 Loop 与一次任务内部的 Agent Loop 有什么区别，状态和验证结果怎样交接？
**我（60 秒口述）**：内层 Agent Loop 由 Agent 自己在一次任务中循环，每轮思考、调工具、观察结果，以不再需要工具为停止条件；外层 Engineering Loop 由调度系统或人写的流程在任务结束后工作，每轮唤醒 Agent、分配任务、验证结果、记录状态，以达成目标、超预算、失败转人工为停止条件。两者靠外部状态、可检查的验证结果、稳定 `runId` 交接。Loop Engineering 把触发、每轮可读材料和可执行动作、验收信号、状态保存位置、停止或人工接管条件放进同一条流程，Prompt 和工具描述仍只决定一次模型调用怎么执行。任务跨天新会话不会知道昨天试过什么，所以目标、范围、证据、已执行动作、结果、下一步和停止条件都要写进外部状态让下一轮读得到。
**追问 1**：验证结果为什么必须是外部可检查信号？
**答**：测试退出码、CI 状态、lint、类型检查或截图对比才是完成证据，Agent 的说明只能作为补充，把 Agent 自评当验收是明确要踩的坑。原文说得很直白：没有这些外部证据，定时任务只能重复发送同一个 Prompt；需要语义审查时，可由一个 Agent 实现、另一个 Agent 在独立上下文中检查。
**追问 2**：状态只存聊天记录行不行，恢复时还有哪些硬约束？
**答**：不行，只把聊天记录写 Redis 无法从"两个检索任务完成、一个数据分析超时"的位置继续整条 Workflow，恢复必须能重建依赖关系和已确认产物。SSE/WebSocket 事件流不是任务状态的事实源，断线恢复、重放和审计仍要读持久化状态；人工审批或异步恢复后可创建新 Trace 但沿用同一 `runId`，HITL 恢复还要重新校验审批人权限、订单状态、退款金额和任务版本，等待期间任一条件变化让原审批失效。

### J2-46 哪些任务不适合无人值守？缺少可靠验收信号、涉及高风险写操作或需要业务判断时，怎样停止并转人工？
**面试官**：哪些任务不适合无人值守？缺少可靠验收信号、涉及高风险写操作或需要业务判断时，怎样停止并转人工？
**我（60 秒口述）**：循环执行需要重复出现的任务加可检查的验收信号。目标虚、验证信号弱、做错影响大、强依赖审美与业务判断、没有测试日志回滚方式的老项目大改，都不适合无人值守，我会写清停止条件转人工队列。值得做的是 CI 失败初排、依赖版本变更、覆盖率补齐、文档同步、机械迁移、PR 分拣；不值得的是让产品体验更好、只能靠 Agent 自己说我觉得可以了、生产库写操作、支付链路改造、品牌文案定调。停止转人工的具体条件是权限不足、无法复现、需要业务判断、连续失败达上限；创建 PR、改生产配置和自动合并不该是同一条 Loop 的默认后续。第一版我只做只读 triage，不自动改代码也不自动合并。
**追问 1**：权限分级怎么落地，HITL 具体怎么暂停？
**答**：按执行阶段逐级开放 L0 只读摘要、L1 本地复现、L2 草稿修复、L3 创建 PR、L4 自动合并；删文件、改生产配置、发外部消息、写数据库默认等人确认，L4 要同时满足问题类型固定、测试覆盖主要风险、回滚路径经过验证。HITL 发生时编排器把任务转为 `WAITING_INPUT`，保存 Checkpoint、退款依据和待执行参数，然后释放计算资源，审批人稍后打开任务可批准、拒绝或修改参数。
**追问 2**：自动修复第一版该有哪些硬限制？
**答**：四条——修改前创建独立 worktree 或分支、修改范围白名单、只允许跑指定测试和格式化命令、通过后只开草稿 PR 不自动合并。目标也要写成带执行范围的形式，比如限定 `src/auth`、`tests/auth`、每轮跑 `npm test -- tests/auth` 并展示退出码、最多 5 轮、连续 2 次失败原因相同就停止并汇报，别把验收标准留给 Agent 猜测；成本上限还要加最大迭代、最大工具调用、单任务 Token 金额预算和无进展检测。

### J2-47 Loop 如何防止死循环？
**面试官**：Loop 如何防止死循环？
**我（60 秒口述）**：靠三要素——继续条件、退出条件、安全边界，边界里是最大轮次加超时加预算加熔断，再加无进展检测这类独立边界；条件决定是否继续，边界负责强制退出。文章审核那个例子最直观：`review → revise → review` 第三次审核后无论评分是否达标都退出，`iteration_count >= 3` 跳 ExitNode；内层 Agent Loop 常见 10 到 20 轮上限。成本上限我按五项设：最大迭代、最大工具调用、单任务 Token 金额预算、无进展检测、低价值任务只做摘要。只写 `iteration_count` 不够，还得有独立 Token 预算防放大攻击——恶意输入让 ReviewNode 永远返回低分、烧满轮次才退出；我还记 `lastProgressAt` 识别进程活着但一直兜圈子。
**追问 1**：无进展检测为什么比单纯轮次上限更早止损？
**答**：因为它的信号是"两轮失败原因相同"，不用等轮次跑满就停，用于阻止失败原因不变时继续消耗 Token。配合 `multi-agent` 那四层预算：单次模型调用、单次工具调用、单个 Agent 迭代次数、整条任务或某阶段的 Deadline，超任一层都收口。
**追问 2**：嵌套循环和多层重试怎么不互相放大？
**答**：每层要有独立退出条件和安全边界，内层重试耗尽不影响外层迭代预算，外层退出也不意味着内层可无限制重试。而且"重试预算应该只有一个主要持有者"，模型 SDK、角色执行器和网关若各自独立重试，同一次故障会放大成多轮嵌套调用；内外层停止条件不同，别混用同一套计数器。

### J2-48 State 的更新策略怎么选？Replace、Append、Reducer 分别适合什么字段？
**面试官**：State 的更新策略怎么选？Replace、Append、Reducer 分别适合什么字段？
**我（60 秒口述）**：单值字段用 Replace 覆盖、累积字段用 Append 追加、并行写入字段必须用自定义 Reducer，设计 State 时我会先规划哪些字段可能被并行写。Spring AI Alibaba 里 `ReplaceStrategy` 对应分类结果这类单值、`AppendStrategy` 对应 `messages` 对话历史，LangGraph 对应无 reducer 默认行为和 `Annotated[list, operator.add]`。看 `KeyStrategyFactory` 配置就清楚：`current_draft`、`review_score`、`iteration_count`、`next_node` 全用 Replace，只有 `messages` 用 Append，因为历史持续追加而草稿每轮覆盖。关键风险是多个并行节点同时写一个覆盖语义字段会出竞态，LangGraph 抛 `INVALID_CONCURRENT_GRAPH_UPDATE`；所以并行 Agent 各更自己的槽，`finalOutput` 只允许归并节点写。落地时我会先按业务含义把字段分块，别让单个节点什么都能改。
**追问 1**：并行写用线程安全容器就够了吗？
**答**：不够，它只能保证写入过程不损坏，判断不了哪个业务结果应该保留。两个 Agent 都能覆盖同一个 `finalOutput` 时得按角色分槽、单一归并节点写入，Token、耗时这类计数通过事件汇总；分布式提交还会用带 `owner_agent_id`、`fencing_token`、`version` 的 CAS 更新 SQL，受影响行数为 0 就说明任务已被接管，Worker 不能继续补写。
**追问 2**：State 里哪些字段要额外防污染？
**答**：路由控制字段如 `next_node`。恶意输入经节点处理后改写它，可能影响后续条件边、跳过审核节点直接到达输出，防御是对 State 中的路由控制字段做白名单校验。检查点上 `MemorySaver` 只在当前进程和同一 Saver 实例内保留 checkpoint，进程重启后恢复得换 Redis 或数据库 Saver，并验证序列化、过期和并发更新行为。

### J2-49 条件边和动态路由有什么区别？
**面试官**：条件边和动态路由有什么区别？
**我（60 秒口述）**：分界只有一句话：条件边的候选集在设计时确定、选择逻辑可依赖运行时状态；动态路由的候选集本身在运行时才确定，两者是连续谱系，多数场景条件边已够用。条件边在预定义候选路径里选，Spring AI Alibaba 用 `addConditionalEdges()`，`next_node` 是流程控制字段；动态路由对应 LangGraph 的 `Send` API，能动态决定并行调用次数，适合 map-reduce 这类运行时决定分支数的场景。我想强调分界是候选集是否设计时确定，不是用不用 LLM；也别和提示词路由、Skill 路由混了，那是另外两套机制。Edge 抽象的是什么状态允许去哪、何时结束，用条件边表达分支与循环，而不是图外写满 if-else。
**追问 1**：条件边、提示词路由、Skill 路由别混，差异点在哪？
**答**：条件边和动态路由是图上的控制流；提示词路由是应用层分发，先识别请求类型再选检索、分析、诊断链路，低置信度请求进追问或人工确认；Skill 路由是粗召回、精排、决策三阶段，输出是 Skill 集合且允许零个。一句话分界：条件边选预定义路径、动态路由运行时生成分支数、Skill 路由选加载哪个 Skill。
**追问 2**：条件边依赖 `next_node`，会不会被攻击？
**答**：会，这正是 State 污染，所以 `next_node` 要做白名单校验，恶意输入经节点改写它可能让条件边跳过审核直达输出。另外别把动态路由和提示词路由混淆，前者候选节点运行时确定，后者是把请求分发到不同链路；Graph 抽象三原则是 Node 抽象职责边界、Edge 抽象流转规则、State 抽象必须持久记住的信息。

### J2-50 工具调用失败时，哪些错误适合重试？认证失败和非幂等写操作怎么处理？
**面试官**：工具调用失败时，哪些错误适合重试？认证失败和非幂等写操作怎么处理？
**我（60 秒口述）**：只有瞬时错误——网络超时、API 限流、临时 5xx——适合有界重试，指数退避加抖动；认证权限失败应停止分支、重新认证或转人工，不能跳过鉴权；非幂等写操作必须靠幂等键、业务唯一约束和单一执行者保护，不能盲目重试。Spring AI Alibaba 把错误分四类：瞬时错误按 1s、2s、4s 退避重试并设总时限，LLM 可恢复错误把错误塞进 State 让模型调整，用户可修复错误用 `interruptBefore` 暂停等人工，意外错误让异常冒泡交给开发者。恢复动作要落到真正负责的层级，角色执行器管模型工具迭代次数，编排器决定取消哪些分支、保留哪些结果、下游能否继续。
**追问 1**：认证失败"重试几次再说"为什么是错的？
**答**：必须停止分支、重新认证或转人工，跳过鉴权继续执行等于把权限判断交给模型。相关地，排查时要区分连接失败、JSON-RPC 错误和工具返回的 `isError: true`，仅 HTTP 200 不代表工具执行成功；弹性模式还包括熔断器（连续 N 次格式校验失败就降级到模板输出）、舱壁隔离（给不同外部 API 设独立并发上限）和补偿事务 Saga。
**追问 2**：写操作超时、结果未知该怎么处理？
**答**：按 `TIMED_OUT_UNKNOWN` 处理，先按 `actionId` 查询原请求状态，查到成功就回填工单号、明确失败才按策略重试、状态仍不确定进对账或人工。补偿不是数据库回滚的同义词，"发送了一封邮件"通常无法真正撤回，只能再发更正通知，补偿本身也可能失败，需要幂等、重试和人工入口；只要存在重试，就要把业务消息、模型调用尝试和供应商请求分别记录，避免重复回答或重复执行带副作用的工具。

### J2-51 工作流中断后怎么恢复？
**面试官**：工作流中断后怎么恢复？
**我（60 秒口述）**：靠持久化加 checkpoint 机制，在结果已落盘、可独立校验的位置保存检查点，恢复时用稳定会话标识重建状态与依赖，人工中断用 `interruptBefore` / `updateState` 回填后继续。`MemorySaver` 只保存当前进程内 checkpoint，进程重启恢复要换 `RedisSaver`、`SqliteSaver` 并验证序列化、过期和并发更新。检查点适合放结果已落盘的位置：检索完成保存带引用材料清单、分析完成保存可复用 Artifact、Reviewer 结束记录通过或退回原因，需授权的动作暂停前保存待执行参数。单 Agent 会话状态和外层 Workflow 检查点是两类数据，后者还要存当前阶段、已完成角色、产物引用、模型与 Prompt 版本、预算和失败记录；恢复通常不是从某一行 Java 代码继续。
**追问 1**：恢复时怎么防旧 Worker 的迟到写入？
**答**：调度器发现 Lease 过期，先查 Worker 和下游系统是否已产生可用 Artifact，产物存在且校验通过就任务直接推进，结果仍未知时递增 `attempt` 和 `fencingToken` 把任务放回 `READY`，新 Worker 从最近 Checkpoint 和 Artifact URI 恢复；原 Worker 随后提交时旧 Fencing Token 或版本让这次写入失败。任务超过最大尝试进入 `FINAL_FAILED`，现场和已完成产物继续保留等人工处理。
**追问 2**：回放测试要覆盖哪些场景？
**答**：正常退出、达到迭代上限、工具超时、人工中断、认证失败和 checkpoint 恢复六类；框架 API 会变化，Node 的职责、Edge 的合法流转和 State 的更新规则应当在测试中固定下来。另外 HITL 恢复要重新校验审批人权限、订单状态、退款金额和任务版本；一次重试要继续挂原角色任务下并保留新 `attempt`，不能伪装成一次全新的正常调用，人工审批后可创建新 Trace 但沿用同一 `runId`。

### J2-52 工作流有哪些特有的安全风险？
**面试官**：工作流有哪些特有的安全风险？
**我（60 秒口述）**：除了通用的 LLM 输出不可信，Graph 特有的两类是 State 污染和 Loop 放大攻击，另外还有提示词注入经由工具结果和 State 传导、以及审批绕过。LLM 输出进数据库、前端模板、Shell 命令前要做对应校验和编码，每个节点只拿当前任务所需工具权限，删除发送付款走审批节点。State 污染是恶意输入改写 `next_node` 这类路由控制字段，跳过审核节点直达输出，防御是字段白名单校验；Loop 放大是构造输入让 ReviewNode 永远返回低分、打满轮次烧 Token，防御除 `iteration_count` 外还要加独立 Token 预算。我会点全那条清单：用户输入、网页、邮件、RAG、Memory、工具结果、其他 Agent 消息都按不可信数据处理，安全控制落在模型之外。
**追问 1**：为什么不能只答通用 Prompt Injection？
**答**：因为题目问的是"工作流特有的"，得点名 State 污染与 Loop 放大攻击两条，防御要具体到字段级（白名单校验路由控制字段）和预算级（独立 Token 预算），不能只说"加个最大轮次"。`workflow:445` 的追问标准答案就是这两条；回放测试要覆盖达到迭代上限、人工中断、认证失败和 checkpoint 恢复。
**追问 2**：审批节点靠 State 路由会不会被绕过？
**答**：会，攻击路径正是"跳过审核节点直接到达输出"，说明审批若靠 State 路由就可能被绕过，审批应绑定具体工具、资源、有效期。权限按阶段 L0–L4 逐级开放，删文件、改生产配置、发外部消息、写数据库默认等人确认；MCP Server 的来源、工具 `description`、返回内容和 Prompt 模板也要进审核范围，无人值守 Loop 写权限过大还可能被提示词注入诱导读取无关文件、重复调用昂贵接口。

### J2-53 如果让 Agent 完成一次需要调用多个工具的长任务，你会如何拆分执行步骤？
**面试官**：如果让 Agent 完成一次需要调用多个工具的长任务，你会如何拆分执行步骤？
**我（60 秒口述）**：先按执行路径能否提前确定做拆分——能写出来的步骤交给 Workflow 或代码，写不出来的局部嵌 Agent 子循环，每个工具调用作为可独立校验的节点、输出走结构化契约。长流程只有少数环节不确定时我用 Plan-and-Execute 在固定框架留动态子任务，还能嵌套：用 CoT 给全局步骤，每步内部跑 ReAct 子循环，计划提供结构、子循环处理局部不确定。技术调研外层 Workflow 固定为制定计划、检索、分析、复核四阶段，检索阶段再由 Agent 选搜索词和工具；角色间只交付结论、引用和 Artifact。子任务要拆成可执行契约，派发时给子目标、成功标准、依赖的上游、可用工具权限、输出 Schema 和产物位置，超时和重试由运行时强制。
**追问 1**：为什么不能一上来全交给模型动态推理？
**答**：`agent-basis` 那句"先用最简单的方式跑通，再根据实际失败模式决定升级哪一层"是准则，上来就搞 Multi-Agent、全靠模型动态推理、上下文不做任何管理，踩进去再爬出来会很费劲。拆分还要落到工具边界：一个工具只做一件事、名称动词加名词、`description` 写清适用与禁用条件；`AgentTask` record 里 `taskId`、`parentTaskId`、`dependencies`、`allowedTools`、`outputSchema`、`maxIters`、`deadline`、`maxAttempts` 正好把契约落地。
**追问 2**：每步输出为什么必须可独立校验？
**答**：结构化任务契约要求交付带 Schema 的结果而非自然语言，"产品经理 Agent"应输出含 `TaskID`、`Dependencies`、`AcceptanceCriteria` 的标准 JSON Payload，而不是"我写好了，你开发一下"。某一步持续出错时先单独调试该步的输入、约束和输出；另外任务分解过细会增加调用次数和状态传递成本，并行分支还要避开同一权威字段、外部副作用交给单一执行者或幂等与唯一约束保护。

### J2-54 哪些节点适合交给模型判断，哪些节点应该由规则或代码控制？
**面试官**：哪些节点适合交给模型判断，哪些节点应该由规则或代码控制？
**我（60 秒口述）**：需要语义判断的交给模型——选检索方向、解释矛盾材料、综合多角色结论、生成评审内容；有明确规则的交给代码和状态机——输入合法性、角色能调哪些工具、上游产物是否齐全、超时取消、重试次数、阶段顺序，还有权限金额。依据是确定性规则塞进 Prompt 不但更慢，还会把可稳定复现的行为变成概率问题；模型负责理解意图、生成内容、提出工具调用，身份、权限、金额、审批、幂等由代码和业务系统决定。Stripe 混合状态机很典型：跑 lint、push 走确定性流程，实现功能、修 CI 交给 Agent。格式转换、精确计算、批量处理交给脚本，架构约束靠 Linter 和结构测试机械化执行。
**追问 1**：把所有分支判断都写进 Prompt 有什么问题？
**答**：过度设计，大量 if-else 硬塞进去会让 Prompt 又长又脆弱；而且权限和审批不能交给模型"自觉遵守"，分隔符只帮模型区分内容边界，无法在安全层面阻止危险操作。低置信度或高风险意图要转人工或追问，"删数据"不能被当普通问答处理；`context` 里另一个极端是过度抽象，只写"做个有帮助的助手"，模型同样拿不到决策依据。
**追问 2**：并行写冲突能让模型自己商量吗？
**答**：不能，这是并发写入问题，模型讨论解决不了，必须由按角色分槽、单一归并节点和幂等键解决。参数校验、路径边界、SQL 参数化、脱敏、限速由 Server 代码落实，安全问题不能靠相信模型解决；`harness` 那句 If it cannot be enforced mechanically, agents will deviate 讲的就是同一件事。

### J2-55 Agent 的计划、工具结果和中间状态如何保存？中断后怎样恢复？
**面试官**：Agent 的计划、工具结果和中间状态如何保存？中断后怎样恢复？
**我（60 秒口述）**：三类数据分开存——计划与进度走外层 Workflow 检查点或结构化状态，落到外部文件、Issue 或数据库；工具结果以可回查引用加 Artifact URI 保存；会话状态留在单 Agent 内；中断靠持久化 checkpoint、稳定 `runId` 和幂等恢复。单 Agent 会话状态记对话与工具进度，Workflow 状态记执行到哪个角色，共享业务状态又是一类，三者不能相互替代；共享状态只存跨角色协作需要的信息，用户请求、租户、资源和权限通过显式 `TaskContext` 传入，别依赖 `ThreadLocal` 隐式读取，并发远程调用后容易串任务。工具结果要留 traceId、请求时间、错误码、日志位置、调用参数和结果摘要链接，原始材料存 Artifact 库、只交付结论摘要和引用，摘要不能脱离证据。
**追问 1**：计划只写在对话里会怎样？
**答**：Compaction 后早期判断、版本号、未完成事项容易丢，长任务还要处理跨窗口状态交接。结构化笔记 `NOTES.md` 或 to-do list 保存的是可恢复状态，不等于长期记忆；工具结果也别全量长期留在窗口，清理旧 `tool_result` 但保留可回查引用，排障信息和原始日志洪流之间要取平衡。
**追问 2**：恢复时哪些细节最容易漏？
**答**：前端 SSE/WebSocket 事件流不是事实源，断线恢复、重放和审计仍要读持久化状态；模型路由结果要在调用开始时写 Trace，执行结束后重新路由再补日志可能把观测数据记到另一个模型上。外层 Workflow 检查点还要保存当前阶段、已完成角色、产物引用、模型与 Prompt 版本、预算使用和失败记录；读取类工具可以有界重试，加入交易、通知等外部副作用后还得额外保证幂等。

### J2-56 工具包含写操作时，权限、参数校验、二次确认和审计怎么设计？
**面试官**：工具包含写操作时，权限、参数校验、二次确认和审计怎么设计？
**我（60 秒口述）**：写操作统一收敛到 Action Executor 或服务端，按身份与权限校验、参数校验、风险分级与二次确认、幂等执行、外部状态核验、审计留痕这条链路处理，模型只提交动作意图与参数。退款、发邮件、创建工单、发布版本都会改外部状态，Executor 先校验身份权限风险等级，高风险等人工确认，执行用幂等键和业务唯一约束，按业务需要记事务、Outbox 或 Saga，完成后核验外部状态保存审计，失败按已执行步骤选补偿或转人工。Function Calling 七步里第 4 步业务侧校验字段、必填项、用户权限、订单归属和幂等键正是落点。我认那句底线：模型可以提出操作建议，最终权限、业务规则、审批和执行结果必须由服务端校验。
**追问 1**：二次确认只在 Prompt 里问一句够不够？
**答**：不够，高危操作应在执行前中断流程并请求审批、得到授权后才继续调用工具。HITL 要保存 `runId`、Checkpoint、退款依据和待执行参数并释放计算资源，恢复时用原 `runId/taskId` 重新校验审批人权限、订单状态、退款金额和任务版本，等待期间任一条件变化让原确认失效，确认事件也只能消费一次。
**追问 2**：审计和幂等键有哪些细节？
**答**：审计要能还原完整链路，回答"谁在什么权限下执行了什么操作"（用户身份、审批记录、权限决策、外部写操作），一条 Agent 回答可能经过多个 Server 和工具，需要 Trace ID 加结构化日志。幂等键应基于源消息 ID 加批次 ID 而非结果文本，温度采样会让语义相同字面不同；副作用冲突用单一执行者、幂等键和业务唯一约束，重试存在时把业务消息、模型调用尝试和供应商请求分别记录。

### J2-57 什么情况下需要 Multi-Agent？如何控制通信成本和状态一致性？
**面试官**：什么情况下需要 Multi-Agent？如何控制通信成本和状态一致性？
**我（60 秒口述）**：只有不同环节需要明显不同的工具、权限和上下文，或任务能分成相对独立方向且每角色有明确交付结果时我才上 Multi-Agent；通信成本靠结构化结果加按角色隔离上下文加单一归并节点控制，状态一致性靠幂等、版本 CAS、Lease 加 Fencing Token、检查点保证。Anthropic 的 Research 系统主 Agent 分方向、Subagent 分别搜索、主 Agent 汇总，适合并行；但分支频繁依赖彼此中间结论时通信成本很快抵消收益。通信方式按复杂度选：参数和返回值、共享状态、消息、结构化结果、A2A 跨团队，能在方法调用里完成就没必要改消息系统。共享状态只存协作需要的信息，原始材料留 Artifact 库只交结论摘要和 URI，`finalOutput` 只允许归并节点写。
**追问 1**：A2A 能顺带解决状态一致性吗？
**答**：不能，A2A 解决远程 Agent 如何发现彼此、交换消息、跟踪任务和交付产物，不会替应用决定执行拓扑，也不会自动解决内部一致性；A2A 1.0 的 `TaskState` 里 `INPUT_REQUIRED` 和 `AUTH_REQUIRED` 只是等待外部补充信息后继续的中断状态。一致性还得靠带 `owner_agent_id`、`fencing_token`、`version` 的 CAS 更新、Lease 加 Fencing Token（7→8 那个例子）和检查点。
**追问 2**：怎么证明多 Agent 真的比单 Agent 值？
**答**：必须设对照组——单 Agent 全工具、固定多 Agent Workflow、Supervisor 动态编排三组，相同输入快照、模型、预算，比较必要工具调用率、证据覆盖、事实错误、P95、Token、成本，再做角色消融，去掉一个检索 Agent、Reviewer 或归并节点重新评测，若质量、覆盖率和失败恢复几乎不变，这个角色很可能只增加调用次数。另外部分失败策略要写进任务契约：必答维度缺失可整体失败、同类分支达规定数量按 Quorum 归并、允许部分完成就返回已有结果并标出缺失项；研究员必须成功、两个补充角色都失败就不让投资经理硬凑结论。

### J2-58 你会记录哪些 Trace，并用哪些指标评估任务完成率、工具调用和执行轨迹？
**面试官**：你会记录哪些 Trace，并用哪些指标评估任务完成率、工具调用和执行轨迹？
**我（60 秒口述）**：Trace 要保留父子 Span 关系并覆盖模型、检索、工具、Agent、审批全链路，指标分任务完成率、工具调用、执行轨迹、成本延迟、观测治理几组，而且必须能回放 Badcase 并做对照组实验。AI 接口返回 HTTP 200 不代表回答正确，RAG 可能在改写召回重排截断阶段出错，Agent 还可能选错工具、重复执行副作用操作、归并漏结果。五类信号我按这个分：Metrics 看请求量错误率 P95 Token 用量，Logs 看异常堆栈状态变更重试原因，Trace 看一次请求经历哪些步骤，Evaluation 看正确性忠实度工具选择任务完成度，Audit 看谁在什么权限下执行了什么。长任务区分 Session、Run、Trace、Span、Attempt，确认过的失败 Trace 脱敏后回流 Badcase 集合，工具参数和结果可能含敏感数据，生产里用摘要、脱敏、采样、分级访问。
**追问 1**：只看最终回复为什么不行，评测要核什么？
**答**：即使某个检索工具调用失败，模型仍能生成一份语句流畅、结构完整的报告，所以验收要核对必要工具是否调用成功、每角色是否按契约交付、引用能否回到原始材料、归并节点有没有隐瞒失败分支。ReAct 每次工具顺序可能不同，评测不必逐节点匹配固定轨迹，先查子 Agent 是否按任务契约交付，再查编排器是否遵守依赖、并发和跳过条件，最后确认归并节点没漏上游冲突、引用或失败信息；有确定规则的用单元测试集成测试，恢复能力靠故障注入验证。
**追问 2**：多 Agent 特有指标和三种评分方式怎么配合？
**答**：各角色成功率、超时率、重试分布下钻模型与工具错误率和 P95，并行阶段记队列等待、实际并发数和最慢分支耗时，角色交付后统计结构化结果校验失败、返工、下游跳过次数，最终看整次任务 Token、成本、P95 及首条前端事件与完整结果分别等待多久，端到端耗时仍由最慢分支和最终归并决定。评分方式各有分工：规则评测适合 JSON 格式、字段完整性、枚举值、数值边界、测试结果，LLM-as-Judge 适合相关性忠实度完整性但有位置长度偏差，人工评测留给高风险、复杂语义和争议结果；Golden Set 每条要含输入、预期结果或成功标准、场景标签和评分方式，Prompt、模型、检索策略、工具版本和评测结果必须关联，否则分数变化后找不到原因。
