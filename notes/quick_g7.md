### X2-01 1. 什么是 RAG？详细描述一个完整 RAG 系统的详细工作流程？
**面试官**：1. 什么是 RAG？详细描述一个完整 RAG 系统的详细工作流程？
**我（60 秒口述）**：我理解 RAG 就是让大模型开卷考试：回答前先从外部知识库捞出相关片段和问题拼进 Prompt，让答案落在可核对的证据上，而不是靠参数记忆硬编。链路分两段。离线六步是解析、清洗、提取来源章节版本权限等 metadata、按语义边界切 Chunk、Embedding 转向量、写入向量库和全文索引，可批处理或由变更事件触发增量。在线五步是 Query 改写并抽过滤条件、用和离线同一个 Embedding 模型把问题向量化、混合召回加 Rerank 精排、组装带「只依据给定资料作答、标注引用」指令的上下文、生成答案并附出处。我死卡两点：查询和索引必须同模型，权限过滤必须在召回前参与查询，否则越权和引用错配在生成层都补不回来。
**追问 1**：你反复说离线在线要用同一个 Embedding，生产里怎么保证不混用，混了会怎样？
**答**：靠 metadata 把 `embedding_model`、`embedding_model_version`、`embedding_dimension` 写进每条记录，查询前校验不匹配就拒绝或告警。不同模型的向量空间不通用，维度相同也不可比，混用等于在两个空间里算相似度，整个排序基础就坏了，不是结果随机而是压根不能信。
**追问 2**：那要换更强的 Embedding 模型，怎么升级不中断服务？
**答**：走蓝绿：在新索引用新模型全量重建，新旧并行一段时间对比召回率和答案质量，确认稳定后用索引别名切流，保留旧索引一段时间用于回滚再删除。切回时要把模型和索引一起切回旧版本，具体能力以官方文档为准。

### X2-02 2. 大模型的 RAG 主要用来解决什么问题？
**面试官**：2. 大模型的 RAG 主要用来解决什么问题？
**我（60 秒口述）**：我归成三个问题。一是知识时效性，模型知识停在训练截止点，新政策、新手册、实时数据得靠外部检索或工具动态注入；二是私有数据，内部制度和客户资料不能进公开训练集，RAG 按权限只取相关片段送入上下文、还不用重训；三是事实性幻觉难核查，模型缺依据也照样生成通顺错误结论，RAG 给原文、要求基于证据作答并附出处，把无根据编造压下来。还有个实在动机：文档涨到几十万字，全量拼接会顶到 Token 上限、推高首字延迟。但要讲清边界，RAG 不是把文档塞进上下文，核心价值是把回答约束在可检索、可引用、可做权限控制的外部证据上。
**追问 1**：很多人把 RAG 说成专门解决幻觉，生产里你怎么验证它到底降没降？
**答**：不能只看答案通不通顺，要在固定评测集上分开看 Faithfulness 和 Citation Accuracy，并主动加知识库外问题看拒答表现。RAG 降低的是无根据编造，但漏召回、上下文噪声、引用错配、模型不遵循指令这四类照样会出错，所以还要配引用校验和拒答机制。
**追问 2**：什么场景下你反而不上 RAG？
**答**：用户只想找到原始材料时走传统搜索更直接，比如下载制度原文、核对接口定义、找合同模板，链路短、成本低、结果可控；单篇长文档要通读全局时用长上下文窗口；答案压根不依赖外部知识时也没必要。别把「不适合 RAG」等同于「不适合检索」。

### X2-03 3. 相比直接微调 LLM，RAG 解决了什么问题？微调和 RAG 各自的优劣势是什么？
**面试官**：3. 相比直接微调 LLM，RAG 解决了什么问题？微调和 RAG 各自的优劣势是什么？
**我（60 秒口述）**：我一句话划职责：RAG 解决「模型缺外部或最新知识」，微调解决「输出风格、格式、指令遵循不稳」，开卷考试和闭卷背诵的比喻最清楚，制度改版只更新索引。按六维度比：知识更新上 RAG 改知识库即可、微调要重训重评；数据安全上 RAG 按用户 ACL 动态过滤、微调把信息训进参数没法细粒度隔离；幻觉控制上 RAG 能要求只依据召回原文并标引用、微调凭参数生成给不出出处；成本、场景、风险也各不同。所以我会先把 RAG 链路和评测集搭稳，确认痛点真是领域语言风格或固定格式，再评估微调；复杂垂直场景才两者配合，微调管术语和推理规范，RAG 注入实时事实和可追溯证据。
**追问 1**：业务细则每周都变，为什么不能直接用微调把知识训进去？
**答**：训练和评估周期长、仍可能张冠李戴，而且天然给不出原文出处、没法按用户权限做细粒度隔离，知识过期后回滚和更新成本都很高。更麻烦的是灾难性遗忘和训练数据过拟合，把微调当知识注入手段是这题最常见的跑偏。
**追问 2**：那什么时候你会把两者一起用，代价是什么？
**答**：法律、医疗、金融投研这类场景，用微调让模型熟悉领域术语、推理规范和固定输出格式，再用 RAG 注入实时业务数据和可追溯原文。代价是两套链路都要维护：训练集清洗标注、训练算力、多版本模型托管，还要和 RAG 的评测集一起做回归，别先上微调再补 RAG。

### X2-04 4. RAG 中的文档是怎么存的？粒度是多大？详细说说文档切割（Chunking）策略？
**面试官**：4. RAG 中的文档是怎么存的？粒度是多大？详细说说文档切割（Chunking）策略？
**我（60 秒口述）**：不是整篇丢进去，我的存法是「检索表示与生成素材分离」：每个 Chunk 存向量、原文和 source_id、section_path、页码、版本、acl，完整表格、父段落、原图放 DocStore，命中后按 doc_id 回查组装。粒度没有万能值，事实型偏 256 到 512 Token，分析型偏 1024+，通用我从 400 到 800 Token、10% 到 15% 重叠起步做实验。切法按成本排：固定长度只配当评测基线，它会把条件与结论、表头与数值硬切开；往上是递归字符、按 Markdown 和 HTML 标题、代码按 AST 类函数、法规按条款；再上是 Parent-Child，子块 200 到 400 Token 建索引、靠 parent_id 回查 1000 到 1500 Token 父块；语义切分按句子向量距离突变找边界。选型最终都在同一批问题上比 Context Recall 和答案准确率。
**追问 1**：为什么不能一律按 512 Token 切，代价在哪？
**答**：固定长度不感知段落、表格和代码块边界，售后政策「除以下情况外均可退货」和例外清单被切到两块，召回哪块都不完整，模型很容易漏掉限制条件。单块 Embedding 每次只看到当前 Chunk，跨段落主语、适用范围、表头没保留，向量救不回丢掉的上下文，所以固定长度只用来跑通基线。
**追问 2**：语义切分听起来最好，为什么不默认全用？
**答**：它离线要对大量句子算 Embedding，索引耗时和成本明显高于字符切分，还得配 min_chunk_size/max_chunk_size 防主题切换处切出极小块。文档频繁增量更新时变更文档要重算句子向量不划算，结构本身清晰的 Markdown 或接口文档反而该按结构切，精确查编号字段的场景也不适合。以官方文档和自有评测集为准。

### X2-05 5. 怎么规避语义被切割掉的问题？
**面试官**：5. 怎么规避语义被切割掉的问题？
**我（60 秒口述）**：我先把问题说准：本质不是文字丢了，而是完整语义被拆散后每一半相关度都不够，检索时全军覆没，所以按三组配，不指望一招解决。切法侧是重叠兜底，取 chunk_size 的 10% 到 20%，再加语义边界切割，按句子、段落、标题切并把章节路径写进每个块。补法侧是命中后把语境补回来：句子窗口按单句建索引、命中带前后 N 句返回，Parent-Child 靠 parent_id 回查父块，高要求再上 Contextual Retrieval 给每块生成背景说明，或 Late Chunking 先整篇编码再按块池化。重组织侧是命题化切割，用 LLM 把段落拆成自包含命题。顺序是重叠兜底、语义边界保质量、高要求才叠父子或上下文增强，收益一律在固定评测集上比 Context Recall。
**追问 1**：面试官说「加个 overlap 不就行了」，你怎么回，怎么验证有效？
**答**：重叠只保证跨边界文字不丢，救不了完整语义被拆散；单纯把 chunk 设大也不行，块越大语义越杂、精度越差，是用一个问题换另一个。验证要在固定评测集上比 Context Recall 和答案准确率，光看单条样例变好不算数。
**追问 2**：Contextual Retrieval 和 Late Chunking 都要额外成本，你怎么决定上哪个、成本怎么压？
**答**：Contextual Retrieval 不改动 chunk，让 LLM 看着整篇为每块生成背景说明再做 Embedding 和 BM25 索引，用 Prompt Caching 复用整篇前缀能把成本压到很低；Late Chunking 先对整篇做一次前向传播再按块均值池化，先编码后切分、无需生成模型。两者都只先在高价值文档和高频失败样本上验证收益，命题化更是要额外 LLM 调用，别全量铺开，具体方案版本以官方文档为准。

### X2-06 6. 在 RAG 中 Embedding 究竟是什么？如何选择和评估一个 Embedding 模型？
**面试官**：6. 在 RAG 中 Embedding 究竟是什么？如何选择和评估一个 Embedding 模型？
**我（60 秒口述）**：Embedding 就是把一段文本映射成固定维度的稠密向量，相当于给文本一个语义坐标，语义近的距离就近，这样「如何申请退款」和「退货与退款办理指南」字面不重叠也能召回。它决定语义召回的理论上限，向量库只负责在可接受延迟内兑现。选型先看约束：闭源 API 开箱即用少运维，开源 BGE、Qwen3-Embedding、E5、GTE 适合数据不出内网和控成本；用 MTEB 初筛，但必须在业务自己的问题集上验证召回率、延迟和部署成本。语料含大量内部缩写、型号、错误码时通用 Embedding 不够，我会配 BM25；索引的距离度量也要和模型推荐对齐。常见维度 768 到 3072，不是越高越好。
**追问 1**：为什么不能只看 MTEB 榜单就定模型？
**答**：榜单是公开评测，业务里有领域术语、脏输入、权限规则和特定问法，必须自有评测集验证。而且维度越高直接增加内存占用、索引构建时间和距离计算开销，把「维度高=效果好」当结论是常见误区；向量库索引用余弦还是内积，也要和模型训练的度量方式对齐，否则召回质量下降甚至无法命中索引。
**追问 2**：上线后怎么判断该不该换模型，换的时候验证什么？
**答**：在固定评测集上比 Recall@K、Context Recall、答案准确率，同时记延迟和成本，收益不明显就别换。真要换必须重建索引：不同模型向量空间不通用、维度相同也不可比；把模型信息写进 metadata，走新索引重建、双索引并行、别名切流、保留旧索引回滚这一套，具体能力以官方文档为准。

### X2-07 7. Embedding 有哪几种算法你了解过吗？
**面试官**：7. Embedding 有哪几种算法你了解过吗？
**我（60 秒口述）**：我按三代演进讲，逻辑是每代补上一代的坑。第一代静态词向量，Word2Vec 的 CBOW 和 Skip-gram、GloVe 共现矩阵分解、FastText 用字符 n-gram 解决未登录词，解决了词变向量，但「苹果」在「我吃了苹果」和「苹果手机发布了」向量完全一样，处理不了多义词。第二代 ELMo、BERT 上下文相关、表达力强，可比两句相似度得把 query 和每个候选 doc 拼接过一次模型，百万文档就是几小时，检索等不起。第三代 SBERT、SimCSE、BGE、E5 用双塔把 query 和 doc 独立编码只算余弦，文档向量能提前算好入库，才是 RAG 标配，分水岭就是能不能独立编码加预计算。落地是 bi-encoder 粗排、Cross-Encoder 精排，两代各归其位。
**追问 1**：BERT 效果更强，为什么反而不能做检索？
**答**：它用 cross-encoder 思路，query 和每个 doc 拼接后过一次模型，有 token 级交叉注意力所以精度好，但没法预计算文档向量，百万级库每次查询要几小时。RAG 是速度优先，所以让 bi-encoder 做粗排、Cross-Encoder 做 Rerank，两代结构各归其位，不是谁淘汰谁。
**追问 2**：三代精度一定高于 cross-encoder 吗，bi-encoder 精度损失在哪？
**答**：不一定，第三代牺牲的正是编码阶段看不到两句 token 之间交叉关系这一点，靠 Rerank 补。SimCSE 用「同一句话两次 dropout 作正样本、batch 内其他句子作负样本」无标注训练，还顺带缓解了 BERT 句向量各向异性。另外要分清「Embedding 算法」和 HNSW、IVF-PQ 这类「向量索引算法」，它俩完全不是一层，混答是常见失分点。

### X2-08 8. 什么是向量数据库？有没有做过向量数据库的对比选型？
**面试官**：8. 什么是向量数据库？有没有做过向量数据库的对比选型？
**我（60 秒口述）**：先纠认知，向量数据库的核心不是能不能存向量，普通关系库也能存、也能算相似度，关键是有没有 ANN 索引，能在大规模高维向量上低延迟找 Top-K，外加元数据过滤、混合检索、动态更新、权限与多租户。选型我按四类比：PG 加 pgvector 架构简单、事务一致性好、SQL 方便，适合初期和中小规模；ES 和 OpenSearch 混合检索、分词、高亮强，适合本就依赖关键词检索；Milvus、Qdrant、Weaviate 支持分布式、读写分离和多种专用索引；Pinecone、Zilliz Cloud 这类托管上线快但要看数据驻留和成本。拐点是实测延迟、召回、容量和多租户要求超出单机能力，不是追新。
**追问 1**：为什么中小规模你会先选 pgvector，而不是一步到位上专业库？
**答**：四个理由，架构简单不引入组件、当前规模性能够用、向量和业务数据同库天然支持事务和 JOIN、SQL 过滤方便，但必须配 HNSW 索引并用 EXPLAIN ANALYZE 确认命中。换专业库的代价是多一套运维、监控、备份和学习成本，所以判断拐点是「实测延迟、召回、容量和多租户要求超出单机能力」，不是追新。托管也不等于不用管。
**追问 2**：什么信号出现你会从 pgvector 迁到 Milvus，路径怎么走？
**答**：内存成为瓶颈、写入吞吐上去、要多租户隔离或专用索引能力时。路径是先按「条数 × 维度 × 每维字节」估容量，再考虑 IVFFLAT 或 IVF-PQ 量化换内存，然后分布式分片、独立向量集群与资源隔离，每步都用同一业务评测集验证召回率、延迟和成本。过滤条件在大规模下更容易让 ANN 退化，具体版本特性以官方文档为准。

### X2-09 9. 讲讲你用的向量数据库？数据量级是多大？性能如何？遇到过性能瓶颈吗？
**面试官**：9. 讲讲你用的向量数据库？数据量级是多大？性能如何？遇到过性能瓶颈吗？
**我（60 秒口述）**：这题我不背凭感觉的数字，按容量口径和压测口径讲。到百万级、每天有增量、要读写分离，我会选 Milvus 这类分布式库。量级先算账：内存约等于条数乘维度乘每维字节，100 万条 1024 维 float32 光原始向量就约 4GB，进程还要加 HNSW 图连接、metadata 和系统缓存，别把原始向量当进程总内存。性能我一定要求带硬件、ef、Top-K 和并发报 P50、P99、QPS，换 8 核、跨机房或调大 ef 数字能差一个量级。瓶颈盯两个：内存不足触发 swap 延迟断崖式上涨，根因常是操作系统换页而非索引算法；批量写入触发后台 Segment 合并抢 CPU 和 IO 把 P99 抖起来。定位靠监控和执行计划，数字以自己环境实测为准。
**追问 1**：swap 和 Segment 合并这两个瓶颈，生产里你怎么定位和解决？
**答**：定位靠监控和执行计划，不看体感。swap 用 SQ8 标量量化把 float32 压成 int8，内存能降到原来的几分之一、召回通常只掉 1 个百分点内，或配 mmap 把原始向量放磁盘只留索引；Segment 合并用时间错峰把批量写入挪到低峰，再化整为零每批控制在 500 到 1000 条、批次间隔几秒。量化到底损失多少召回，要在固定评测集上比 Recall@K 核对。
**追问 2**：数据再翻十倍到亿级，架构上怎么办，怎么验证没走偏？
**答**：按内存评估、IVF-PQ 等量化换内存、分布式分片、独立向量集群这条路径走，还要读写分离、批量导入离线化、按租户或业务域分区路由、缓存热点查询。每步都拿业务数据、Top-K、过滤条件、并发和召回率目标实测，同时记录召回率、延迟和资源占用，不看理论复杂度。具体索引类型和参数支持以对应向量库官方文档为准。

### X2-10 10. 你使用 RAG 给大模型一个输入，系统是怎样的工作流程？
**面试官**：10. 你使用 RAG 给大模型一个输入，系统是怎样的工作流程？
**我（60 秒口述）**：我按在线链路讲五步。收到 Query 先改写并抽取结构化过滤条件，把「钱能退吗」补成可检索表达，但原始 Query 一定和改写结果一起召回。接着用和离线索引完全相同的 Embedding 模型把问题向量化。第三步是元数据预过滤加多路召回，向量和 BM25 并行捞候选、用 RRF 按名次融合去重，再上 Cross-Encoder 精排，这里卡三级上限：粗召回 30 到 100 条、重排后 5 到 10 条、最终进上下文 3 到 6 条。第四步组装上下文，最相关证据放前、同文档相邻片段保序、矛盾片段标版本、每条保留来源。最后生成答案附引用，证据不足就拒答。每跳延迟是累加的，高并发要缓存、超时和降级。
**追问 1**：为什么原始 Query 必须保留，不能只拿改写结果去检索？
**答**：改写模型可能把「退款」错误理解成「取消订阅」，意思一变召回入口就歪了，原始 Query 一起召回并融合才能兜住。同理 Self-Query 抽出的是 metadata 过滤条件、不是检索文本，两者职责别混。改写的前提是不能替用户改变问题含义。
**追问 2**：线上答非所问，你按什么顺序定位，怎么保证改动有效？
**答**：按候选池、排名、上下文、回答四段走：先看正确证据有没有进候选池，Top-50 都没有时调 Rerank 毫无意义，要回去查解析、Chunk、过滤和改写；进了池没进上下文查 Rerank 和截断；上下文对了答案还错才查 Prompt 和模型。每次只改一个变量、用回归集复现，每跳的延迟也要记，因为改写、编码、召回、重排、生成是累加的。

### X2-11 11. 请你介绍一下向量检索和关键词检索的区别？
**面试官**：11. 请你介绍一下向量检索和关键词检索的区别？
**我（60 秒口述）**：一句话，一个看语义、一个看字面。向量检索用 Embedding 把 query 和文档编码成向量算余弦，能处理同义词和隐含意图，「怎么退货」也能命中「申请售后」；但它对精确词天然不敏感，M4 Pro、RTX 4090、错误码、SKU 这类换更强模型也治不了，因为只编码语义不看字面精确匹配。BM25 反过来，用 TF 加 IDF 并做饱和度限制打分，精确命中型号数字，可一遇同义词、词无重叠就零分，两者是盲区互补不是谁更强。还有个坑：余弦是 0 到 1、BM25 是任意正数，量纲和分布都不同，所以融合我用 RRF 只依赖名次，不把两路分数直接加权相加。
**追问 1**：为什么不能把两路分数归一化后直接加权，非要 RRF？
**答**：两路分数尺度和分布都不同，归一化本身不稳定、对权重参数敏感，换一批查询就得重调。RRF 用 `score(d) = Σ 1/(k + rank_i(d))`、k 常取 60 作平滑保底，只看排名不看原始分数，不用训练、计算量极小，排名靠后的候选也不会被一次失误彻底淘汰。两路还能并行执行，总延迟取最大值不是相加。
**追问 2**：哪些查询是纯语义方案最容易翻车的 Badcase，怎么防？
**答**：错误码、SKU、版本号、配置项、专有名词这类精确匹配查询，向量容易召回「相似型号」而不是精确实体。所以评测集必须专门含这类样本，且保留关键词通道；换 Embedding 模型或升级索引后要用同一批精确匹配问题做回归，别只拿语义类问题验收。

### X2-12 12. 如何润色用户的 Query（Query Rewrite）？目的是什么？
**面试官**：12. 如何润色用户的 Query（Query Rewrite）？目的是什么？
**我（60 秒口述）**：目的不是把问题说得好听，是把它变成可检索的表达，并顺带产出过滤条件。用户输入常缺对象、时间、范围，「这个报错咋整」「钱能退吗」直接检索基本捞不到。我按六类策略选：规范化改写把口语补成「退款政策、退款条件、退款流程」；Multi-Query 对多种说法生成变体；Query Decomposition 把对比型问题拆成子问题；Step-back 先检索上层背景；HyDE 查询太短时先生成假设答案再检索；Self-Query 从「2025 年 Java 政策」抽出年份类别做 metadata 过滤。两条硬约束：原始 Query 必须一起参与召回并融合，改写不能替用户改含义；Self-Query 产出的是过滤条件不是检索文本。
**追问 1**：每个问题都过一遍 LLM 改写，延迟和成本受得了吗？
**答**：受不了，所以不是所有问题跑全部策略，而是按问题类型路由，只对口语化、多意图、多跳、缺背景的问题触发，置信度低时才扩大或降级。多次 LLM 改写调用是这层的主要成本，我会拿召回覆盖率收益和 P95 延迟一起评，收益不明显的策略直接关掉。
**追问 2**：改写把意思改错了，这种 Badcase 怎么发现、怎么测？
**答**：原始 Query 一起保留融合就是第一道兜底。验证在固定评测集上比 Context Recall 和答案准确率，并把「改写后反而漏召回」的样本单独建一个回归集，每次换改写 Prompt 或模型都跑一遍。HyDE 尤其要加约束，别让它变成「先答再检索」的幻觉放大器。具体组件能力以对应框架官方文档为准。

### X2-13 13. 什么是多路召回？具体怎么做？
**面试官**：13. 什么是多路召回？具体怎么做？
**我（60 秒口述）**：多路召回就是同时开多种检索通道并行捞候选，再合并排序交给精排和生成，而不是只靠单一向量检索。出发点是三类盲区互补：向量对精确词不敏感、BM25 遇同义词失效、还有一类是用户提问角度和文档表述角度完全不同（「产品多久能送到」对「配送时效说明」），前两路都救不了，只能靠多 Query 扩展。典型三路：Dense 向量用同一 Embedding 取余弦 Top-K；Sparse BM25 中文先 jieba 分词、靠 TF 加 IDF 命中型号数字；第三路让 LLM 把原问题改写成 3 到 5 个角度变体分别检索、按 chunk 去重合并。融合用 RRF 绕开量纲不可比、可并行、延迟取最大。RRF 本质仍是粗排，后面必须接 Cross-Encoder 再取 Top-N，别把候选直接拼进上下文。
**追问 1**：召回不够，把 Top-K 从 20 调到 200 不就行了？
**答**：不行。Top-K 尾部相似度很平，调大只是多塞一堆几乎无关的 chunk，正确答案未必进来，反而稀释 LLM 注意力、推高 Rerank 输入量和 Prompt Token。正确做法是适度扩大 `recall_top_k` 到 30 到 100，再靠 Rerank 和压缩把噪声筛掉，`rerank_top_n` 控在 5 到 10、`context_top_n` 控在 3 到 6，三者在同一评测集上一起调。
**追问 2**：多路全上延迟和成本会不会爆炸，怎么定上限？
**答**：三路并行执行、总延迟取最大而非相加，本身就是控制；再叠按问题类型动态路由和置信度低降级，不是每个问题都跑全部通道——电商、IT 文档这类精确词密集用向量加 BM25 双路就够，客服等提问多变再加多 Query，高要求才三路全上再 Rerank。验证在同一评测集上比 Context Recall 和答案准确率，同时记端到端延迟与 LLM 调用次数。

### X2-14 14. RAG 检索优化策略有哪些？
**面试官**：14. RAG 检索优化策略有哪些？
**我（60 秒口述）**：我不按技巧清单答，按链路分层，每层故障位置不同。前置是文档解析和结构化，版面、表格、标题层级、OCR 决定上限。然后五个手段各管一段：Chunk 管证据边界，边界切断后重排只能在不完整候选里选；Metadata 管候选范围与溯源，权限过滤要在召回前参与；Hybrid 管精确词与语义互补；Query Rewrite 管把口语化、多意图问题变得可检索；Rerank 管「相关」到「可回答」的排序。后面还有上下文压缩去重、按证据强度排序，生成侧是证据不足拒答和关键结论引用。落地前提是先建 50 到 100 条覆盖 7 类问题的失败样本集，一次只改一个变量、固定评测集回归，把解析器到评估集这 8 项都版本化。
**追问 1**：RAG 答错时，很多人第一反应是换更强的 Embedding，你为什么不这么干？
**答**：因为得先确认正确证据有没有进候选池。PDF 表格解析错位、Chunk 把前置条件切走、Metadata 没按权限或版本过滤，这些情况正确文档压根没进候选池，换任何模型都补不回缺失证据。我的顺序是先数据治理再谈检索优化，解析质量往往比换 Embedding 更重要，也更便宜。
**追问 2**：怎么证明一次优化确实有效，而不是换了一种错法？
**答**：靠固定评测集和回放，同一批问题比 Context Recall、Context Precision、Faithfulness、Answer Relevancy，再加延迟和成本；Top-K 变大常出现「部分问题补回证据、另一些问题被噪声干扰」，没有固定集根本看不到两头。自动评估我用 RAGAS、DeepEval 一类，但 LLM-as-a-Judge 只是辅助信号，上线前必须抽样人工复核，校准它是否偏向长答案、是否漏判引用错误。

### X2-15 15. 了解哪些更复杂的 RAG 范式？
**面试官**：15. 了解哪些更复杂的 RAG 范式？
**我（60 秒口述）**：我先讲三代演进再讲四种高级范式。Naive 是「提问、向量检索、拼 Prompt、生成」的固定链路，一两天能上线；Advanced 在检索前后加改写、混合检索、Rerank 和压缩，是多数生产系统形态，但隐含假设是流程固定、只是每环做得更好；Modular 把检索、改写、生成拆成可替换模块，LangGraph、LlamaIndex Workflow 是这类实现。真正分水岭是流程本身能不能根据情况调整。Self-RAG 让模型输出四类 reflection token 判断要不要检索、片段相不相关、答案有无支撑、是否有用；CRAG 加轻量评估器做三级路由，不相关就降级网络搜索；GraphRAG 用实体关系、社区摘要和全局归纳处理关系与主题；Agentic RAG 把检索嵌进 Agent 循环、运行时自决再检索并设最大迭代防死循环。复杂度上 Self-RAG 和 GraphRAG 最高，得先确认痛点再选。
**追问 1**：Self-RAG 能直接拿一个现成的通用 LLM 来用吗？
**答**：不能。那四类 reflection token 要在专门构造的数据集上监督微调进词表，不能靠 Prompt 让通用模型直接套，开源版本也是基于 Llama2-7B/13B 这类底座训出来的。这也是它工程复杂度最高的原因，动手前要先确认有没有标注数据和训练评估能力，具体以官方文档为准。
**追问 2**：知识库本身覆盖不到的问题，哪个范式更合适，代价是什么？
**答**：CRAG，评估器判「不相关」就丢弃本地结果降级网络搜索，核心价值是覆盖不到时不乱答，阈值按业务调没有定值。Agentic RAG 更适合「分析近三年财报找营收增速放缓根因」这类多步骤问题，但代价是多轮调用、延迟和费用波动，必须设最大搜索轮数、读取量和总预算这类退出边界，还要防循环漂移。

### X2-16 16. 在什么场景下，你会选择使用图数据库来增强传统的向量检索？
**面试官**：16. 在什么场景下，你会选择使用图数据库来增强传统的向量检索？
**我（60 秒口述）**：判断标准只有一句：回答所需证据是不是必须经过实体关系、路径或跨文档主题才能拼完整。向量 RAG 检索 Chunk，擅长「这段话和我的问题像不像」，适合局部事实问答；Top-K 不会告诉检索器该沿「系统、负责人、复盘、链路」补齐证据，切块后 Chunk 又成了信息孤岛，定义、负责人、依赖、事故散在不同章节不再共享业务标识。适合上图的是四类：企业跨部门制度串联、IT 架构与故障影响分析、金融风控合规里对象之间的关系、跨文档主题归纳。落地用实体、关系、社区发现和社区摘要，Local Search 从已知实体扩邻居，Global Search 用社区摘要做 Map-Reduce 归纳。代价很实在：抽取、消歧、建模、评测和维护成本都上来了。
**追问 1**：扩大 Top-K 再加 Rerank，不也能把关系连起来吗？怎么验证该不该上图？
**答**：不能，关系链或全局主题缺少显式表示时，问题不会因为候选数变多就自动消失，Query Decomposition 加多次向量检索也不等价于图遍历。判断顺序是：相关文本没进候选集就先排查解析、切分和混合召回；候选文本已经齐全、但系统没法按业务关系把它们连起来，才用同一批语料记录索引 Token、索引耗时、查询 P95 和答案质量，比较图检索是否真改善目标问题。
**追问 2**：社区摘要会不会把无权限文档的内容泄露出去？
**答**：会，而且这是 GraphRAG 特有的坑。多个来源共同生成社区摘要时，无权文档的内容可能已经写进摘要，查询阶段只按 doc_id 过滤删不掉。所以正确做法是按稳定的权限分区分别生成摘要、查询时只使用当前用户完整有权访问的分区，高敏感或权限频繁变化的语料走鉴权后的局部检索，原始证据通过授权检查后再进上下文，返回引用前再核一次。

### X2-17 17. 如何规避 RAG 系统中大模型的幻觉？
**面试官**：17. 如何规避 RAG 系统中大模型的幻觉？
**我（60 秒口述）**：先摆正预期，RAG 降低的是无根据编造的概率，不能彻底消除幻觉，因为来源不止「模型凭空编」：检索漏召回让证据没进候选池、上下文噪声把旧版本或相近产品规则拼凑成错误结论、引用错配、模型不遵循指令，都会错答。我按四层防。一是 Prompt 限定证据边界，只基于给定上下文作答、不足明确说无法判断、关键结论附来源。二是检索后加证据质量判断，置信度低、证据互斥或无权访问关键文档时触发改写、扩范围、外部搜索或拒答转人工。三是引用校验必须在 Prompt 外执行，提示词没法独自验证模型是否遵守。四是用 Faithfulness 和 Citation Accuracy 离线加线上监控。还有个易错点：忠实于上下文不等于答案正确，照着过期手册答得再忠实也是错的。
**追问 1**：加了 RAG 还答错，你按什么顺序排查，怎么验证引用没配错？
**答**：按候选池、排名、上下文、回答四段定位，先分清是「没召回来」还是「召回来没用对」。引用校验一定放在代码里做，不能只写进 Prompt；验证用 Citation Accuracy 加人工抽样，专门检查引用位置是否真的支撑对应结论，以及答案里有没有超出检索结果范围的捏造。
**追问 2**：如果知识库里本身就存着新旧两版互相冲突的内容，怎么办？
**答**：把「存在冲突」当成一个正式状态传给生成层，而不是混在 Prompt 里赌模型选对；要求关键结论带来源和版本、只答证据支持的部分，不许用模型常识覆盖正式材料。两份证据权威相当、范围相同又无法裁决时，就诚实呈现「A 规定 10 天、B 规定 15 天，暂时无法确认」，附原文链接并追问地区或版本，医疗、金融、法务场景「不知道」是必要能力。

### X2-18 18. 怎么量化你的 RAG 效果？
**面试官**：18. 怎么量化你的 RAG 效果？
**我（60 秒口述）**：核心是把检索质量和生成质量分成两张账，只看最终答案分数没法定位是哪一环坏了。检索层看 Hit@K、Recall@K、MRR、Context Precision、Context Recall，回答该召回的有没有进前 K、找全没有、排得多靠前、放进上下文的有多少真相关；生成层看 Faithfulness、Answer Relevancy、Citation Accuracy、Noise Sensitivity，回答答案能不能被上下文支撑、切不切题、引用准不准、有没有被噪声带偏；再叠 P95 延迟、Token、重排耗时、缓存命中率。工具用 RAGAS、DeepEval、LangSmith。评测集我建 50 到 100 条，覆盖高频、线上失败、多跳、精确匹配、易越权过期、应拒答这 7 类，每条带 golden_answer、golden_context、metadata_filter、answer_type，开发集和终评集分开保管防泄漏。
**追问 1**：为什么不能只评最终答案对不对？
**答**：检索差和生成差最终都表现成「回答不准」，但优化方向完全相反：没召回退货政策要去查分块、混合检索和 Rerank，政策已进上下文却没给申请入口和时限，才该查 Prompt 和模型。还有个陷阱是图省事把检索结果直接当标准答案，那算出来的更像在评「模型有没有复述检索结果」，混淆了两层。
**追问 2**：执行超时和正常拒答，要不要算进指标分母？
**答**：不算，网络断开、模型超时、用户取消和正常拒答要分开记录，正常拒答完成了请求可以继续判断合理性，执行失败没有完整答案不能直接计入答案正确性或忠实度的分母。报告要同时给执行成功率、有效答案通过率和超时数量，比如 10 题里 2 题超时、其余 8 题通过，就报 80% 和 100% 两个数，只报 100% 会掩盖不可用的请求；没有效样本时返回 null 或「不适用」，别填 0 或 100%。

### X2-19 19. RAG 知识库如何实现动态与持续更新？
**面试官**：19. RAG 知识库如何实现动态与持续更新？
**我（60 秒口述）**：难点不在写入新内容，在同时满足动态性、准确性、一致性、可回滚、可观测五个目标。日常变化走增量更新：变更检测有 Webhook 事件驱动、CDC 监听 binlog、定时轮询扫 updated_at 三种，生产用事件驱动加轮询兜底防漏检，中间加消息队列解耦，靠 doc_id 加 content_hash 幂等去重。修改流程四步：查当前活动版本和旧 chunk_id，写入带新 version_id 且 status 为 building 的新数据不参与在线检索，校验向量库、元数据库、全文索引三端后用别名原子切到新版，再把旧版标记删除按保留策略异步清理。删除必须三端一致，用 outbox 记录变更、消费者幂等执行、reconciliation 修漏删乱序。全量重建则负责模型升级、切分策略迁移和故障恢复。
**追问 1**：为什么不能只新增不删除，先删后写或只写不版本过滤各有什么问题？
**答**：只写不清理会让过期内容、已删除文档和已无权访问的幽灵数据继续被召回，回答持续失真，审计和回滚也失去依据。先删旧再写新会出现短暂空窗，只写新记录却不做版本过滤又会同时命中新旧内容。正确姿势是「先写不可见新版本、原子切换活动版本、旧版标记删除」，权限变更还要触发重新索引，否则旧 acl 会让普通员工继续召回。
**追问 2**：Embedding 模型升级时怎么更新，灰度盯什么指标？
**答**：不同模型向量空间不通用、维度相同也不可比，所以必须在新索引全量重建，并行对比召回率和答案质量后别名切流，保留旧索引一段时间回滚，别原地改。灰度可以按文档数量、用户或问题类型小流量验证，盯检索命中率、平均回答延迟、引用准确性、用户负反馈率四个指标；阈值只是示例，要基于历史基线、离线评估集和线上 A/B 校准，不能直接照抄。具体能力以官方文档为准。

### X2-20 20. 在实际落地中，你觉得 RAG 最难的地方是哪里？
**面试官**：20. 在实际落地中，你觉得 RAG 最难的地方是哪里？
**我（60 秒口述）**：最难的不是把它跑起来，基础 Demo 一两天能搭好，难在调到生产可用，往往要几周迭代。我分三块并排主次：文档预处理是地基型瓶颈，检索调优决定天花板且归因困难，效果评估决定你会不会变成瞎猜。根因是链路长、误差单向传递还环环相扣：解析丢掉的表格列关系、页眉页脚、流程图，检索阶段没法从向量里还原，进去垃圾出来也是垃圾；召回内容就是系统天花板，LLM 再强也变不出没检索到的知识；端到端指标反馈又慢，答案错了分不清是 Chunking、检索还是生成的锅。第一难按格式分治，多栏 PDF 上版面感知解析器、扫描件走 OCR、高价值文档才用多模态；第二难靠失败样本分类排查；第三难把评估拆检索层和生成层两张账。
**追问 1**：为什么不是 Embedding 选型最难，三块里你先动哪块？
**答**：Embedding 只是其中一个点，而且解析错误导致正确文档根本没进候选池时，换模型补不回缺失证据。三块里我优先文档预处理，地基歪了上面全塌；顺序是先数据治理、再检索、最后生成。生产级 RAG 真正耗时的是文档解析质量、混合召回与重排调优、增量更新一致性和固定评测集回归，不是选哪个模型。
**追问 2**：怎么证明调好了，Demo 到生产还差什么？
**答**：靠固定评测集回归、一次只改一个变量、把解析器、Chunk 策略、Embedding、索引参数、改写 Prompt、Rerank、生成 Prompt、评估集这 8 项版本化，把瞎猜变成可回放的迭代闭环。Demo 到生产差的不是模型能力，而是稳定性、权限、成本、可观测、评测和数据治理六个维度，还有失败样本集和 Trace 关联，缺了这些上线后只能靠用户投诉发现问题。

### X2-21 21. 不同来源的文档发生知识冲突时，RAG 应该信谁？
**面试官**：21. 不同来源的文档发生知识冲突时，RAG 应该信谁？
**我（60 秒口述）**：三个想当然的答案我先否掉：不能信相似度最高的，不能无条件信最新的，更不能把裁决甩给一次随机生成。我的顺序是适用范围、来源权威度、版本状态、生效区间，四个都合格才用相关性排序。因为检索分数只回答「像不像」，不回答「该不该信」：员工群聊「听说改成 15 天」和问题一字不差、相似度最高却只是传闻；总部今天发的通用规则不能覆盖仍有效的上海细则；下月才生效的新制度虽最新今天不能执行。落地先给每份文档和 chunk 存身份证：source_id、owner、version、status、published_at、effective_from 和 effective_to、地区产品租户权限范围，权威顺序维护成来源注册表由领域负责人定，不写成开发拍脑袋的常量。
**追问 1**：为什么不能让 LLM 自己判断谁对，published_at 为什么要和生效区间分开存？
**答**：模型缺权威等级、版本状态和适用范围这些治理信息，让它自己判等于把责任交给一次随机生成；而且「最新发布」和「当前有效」是两件事，下月生效、已废止、试用版都可能发布时间更近，所以 published_at 与 effective_from/effective_to 必须分开。检索前先用 metadata 硬过滤掉权限不匹配、地区不匹配、已过期和未生效的内容，再召回排序，硬过滤加分层排序比一个万能公式更可解释。
**追问 2**：两份同等权威、范围相同又都有效，怎么测这套裁决没配错？
**答**：这种就该暴露分歧，不偷偷二选一——诚实呈现「A 规定 10 天、B 规定 15 天，暂时无法确认」，附原文链接、追问地区或版本、必要时转人工。评测集要主动加冲突样本：正式制度对群聊传闻、已废止对现行、总部规则对地区细则，并改变用户地区、身份和提问时间，考察正确来源选择率、过期答案率、引用准确率、冲突披露率和拒答表现；线上记录答案引用过的 source_id 与版本，发布走影子索引加小流量灰度，出错就把检索别名切回旧版。

### X2-22 22. 上下文窗口很大时为什么还需要 RAG？
**面试官**：22. 上下文窗口很大时为什么还需要 RAG？
**我（60 秒口述）**：不会取代，两者互补。长上下文窗口适合单次、少文档的完整阅读，比如分析一份完整财报 PDF、理解单个代码模块、总结长会议记录，这类要通读全文，切块反而漏掉全局脉络。但企业级海量知识库有四个硬约束：知识库规模远超窗口，文档、工单、合同动辄数千万到数亿 Token；延迟与成本成倍放大，即便配 Prefix Caching，每次带几十万输入 Token 的 TTFT 和账单也远高于只传几千 Token 的检索片段；注意力稀释也就是 Lost in the Middle，中间位置关键事实容易被看漏；还有权限隔离与审计溯源，要按租户、角色、ACL 过滤可见范围并记录引用了哪篇哪页。后两点恰恰是 RAG 检索层天然承担的，所以看的是成本、延迟、权限和溯源，不是能不能塞进去。
**追问 1**：既然能塞进去，成本和延迟到底差在哪，怎么验证不是我主观判断？
**答**：输入 Token 按量计费、TTFT 随长度上升，且混入大量无关文档会稀释注意力，塞得越多未必答得越准。验证就在同一批问题上比「全文直塞」和「检索后注入」两组的 Faithfulness、答案准确率、P95 延迟和单次成本，再看用户是否真的需要通读全文，用数据决定而不是看窗口参数。
**追问 2**：如果多个租户的知识混在一个大窗口里，权限怎么控？
**答**：这正是长窗口的弱项，生成层没法按当前用户动态删掉不该看的片段，一旦拼进去就是泄露。RAG 在召回之前用 metadata 硬过滤 tenant_id、acl 和版本，检索层天然承担前置权限过滤，引用还能回溯到具体文档和版本；权限变更要触发重新索引，否则旧 acl 会留下幽灵数据。所以选型依据是成本、延迟、权限和溯源，不是「能不能塞进去」。

### X2-23 23. RAG 与 Agent 自主文件检索应该如何选型？
**面试官**：23. RAG 与 Agent 自主文件检索应该如何选型？
**我（60 秒口述）**：我先把两个正交维度拆开：搜索方式（精确串、正则、关键词、语义索引）和取资料的流程（固定检索链路 vs 模型驱动的探索循环），题目比的是后者，降维成语义与关键词之争就跑题。预建索引是解析组织、建索引、查候选、整理证据、回答，价值是复用，一次建索引服务大量请求；代价是索引要维护、原文件变了没刷新就返回旧内容，也无法预知后续线索。自主路线是「线索、选搜索或读取、观察、判断还缺什么、继续」，下一次搜索由上一次观察决定，一份说明引用配置、配置又指向实现；代价是多轮调用、延迟和读取量波动，还不天然完整。最实用是「索引定位加 Agent 读原文补查」组合，硬约束是证据完整性与权限。
**追问 1**：让 Agent 全部自己找为什么不行，怎么算「找完了」？
**答**：它想不到的目录、每轮重新探索、找到一份就提前停，都会让必要证据一直没被读到；更关键的是「查到一个答案」和「证明检查过所有文件」是两种任务，Top-K 候选或搜了几轮都不自动证明无遗漏。工具返回先给路径、命中位置和必要片段比一次灌几千行更易继续，长文件分段读但要保留回查入口，第一批候选不能成为围墙。
**追问 2**：常变的工作区、还有权限差异，怎么选、成本怎么控、怎么验证？
**答**：常变工作区建索引有同步成本，直接读也可能读到旧副本，得按更新频率权衡；权限上索引检索、路径搜索、原文读取都由程序按当前身份控制，能被搜到不代表有权读。成本用最大搜索轮数、读取量和总预算这类退出边界卡住，验证比任务完成率、证据充分性、总延迟与费用，而不是单次搜索快慢。少量资料需通读时直接读全文反而最省。

### X3-01 1. 什么是 Function Calling？原理是什么？
**面试官**：1. 什么是 Function Calling？原理是什么？
**我（60 秒口述）**：这名字最误导人，模型根本没执行函数，它只输出「调哪个工具、参数是什么」的结构化意图，真正执行在宿主或业务侧。链路七步：服务端注册工具定义含 name、description 和参数 JSON Schema；用户提问；模型生成 tool_calls JSON；业务侧校验类型、必填、权限、归属、幂等键；执行真实工具；把结果带 tool_use_id 以 tool 消息回填；模型基于结果生成最终回答。价值是完成「自然语言意图到结构化参数」的映射，跨过用户说「我买的咖啡机还没发货」和后端要 userId、orderId、includeLogistics 之间的语义鸿沟。我特别强调模型决策、代码执行这个分工：正因执行权在宿主，才能顺带做权限控制、参数校验和执行沙箱，FC 也不等于 API 本身。
**追问 1**：为什么必须是 JSON 而不是自然语言，生产里怎么把契约立住？
**答**：自然语言没法稳定解析，会带解释性文字、漏字段、类型错位、编出未知枚举，解析器一报错整条链路就断。所以用 JSON Schema 定义字段、类型、枚举、必填和 additionalProperties，用 Structured Outputs 把约束前移到生成阶段，但服务端仍要校验——权限、业务状态、副作用都不能藏在 Prompt 里，Prompt 里的「不要越权」只算提醒不算边界。
**追问 2**：模型输出了工具调用，等于操作已经发生了吗，有哪些隐蔽的错？
**答**：不等于，模型只生成意图，操作发生在执行层。这里坑很多：Anthropic 的 `tool_use_id`、Gemini 的 `functionCall.id` 回填必须原样带回，否则并行调用结果会错配；Schema 只能知道 orderId 是字符串，不知道订单是不是当前用户的、有没有退款、调用者有没有客服权限，所以结构校验之外还得做业务校验和权限校验；写操作要由可信执行层生成幂等键去重。

### X3-02 2. LLM 是如何学会调用外部工具的？
**面试官**：2. LLM 是如何学会调用外部工具的？
**我（60 秒口述）**：结论是这不是参数量堆出来的涌现，而是后天专项训练出来的：SFT 教会怎么调，RLHF 教会该不该调。预训练只学预测下一个 token，语料里不存在「给一组工具 schema 到输出标准 tool_calls JSON」这种成对模式，没训过的模型遇到查天气只会说「我需要查询天气 API」，那是描述意图不是可解析请求。SFT 构造完整对话样本：system 注入工具说明、user 提问、assistant 输出结构化 JSON、tool 回填结果、assistant 给答案，几十万条模仿成模式。但正例偏多会过拟合出「遇事就调」，RLHF 补边界感：同题采样多种回答、标注员偏好排序、训只打分不回答的奖励模型、再强化学习调主模型。运行时以 Function Calling 落地，模型只出决策，宿主执行并回填，训练期能力和运行期机制要分层看。
**追问 1**：只做 SFT 不够吗，怎么验证模型的「该不该调」学到了？
**答**：不够。全是调用正例会养成「1+1 也去调计算器」的惯性，遇到调用失败也不知怎么处理。评测要分开看「该不该调」的拒选准确率、工具选择准确率、参数合法率，而不是只看最终回答对不对，可以借 BFCL、τ-bench 这类工具调用基准的思路分层评。
**追问 2**：标注数据从哪来，RLAIF 能不能全替代人工？
**答**：人工标注质量高但贵，用来做种子和评测样本；强模型批量生成再人工抽查是主流，量大成本低。RLAIF 用 AI 评委能省一到两个数量级、速度快，但评委的偏见会传递下去，比如认为「数学题都该调计算器」，业界常混用——关键数据人工保质量，量大的地方 AI 提效率。奖励模型打分能力全来自标注员，标准不稳就会学到歪标准，这是最容易被忽略的风险。

### X3-03 3. 大模型的 Function Call 能力是怎么训练出来的？
**面试官**：3. 大模型的 Function Call 能力是怎么训练出来的？
**我（60 秒口述）**：还是 SFT 加 RLHF 两阶段，区分度在训练数据和细节。一条样本五种角色消息：system 注入工具定义让模型认识工具、user 提问、assistant 输出结构化 JSON 是训练正确答案、tool 回填执行结果、assistant 给最终答案，输出一偏离就被损失函数惩罚、梯度回传纠偏。关键是场景多样性，至少覆盖单工具、多工具并行、调用失败处理、不需要工具直接答、多轮引用历史结果五类，缺一类就在那一类翻车。人工标注便于把控复杂场景，模型自动生成便于扩规模；合成数据入库前必须校验工具名参数是否符合 schema、可控环境验证执行结果、去重并人工抽查。RLHF 常用 PPO，一是训练稳、二是自带 KL 散度约束，逼着新旧输出分布别差太远，防训成只会重复套话。
**追问 1**：为什么非要有「不需要工具」的样本，并行样本怎么构造才不出错？
**答**：全是调用正例会养成遇事就调的惯性，边界感就靠这类样本和 RLHF 的偏好信号建立。并行样本要标清「查北京和上海天气」可以一次输出两个 tool_calls，但「先查订单号再查物流」有依赖只能串行，教错并行会在生产里出 Badcase。工具 schema 的 description 质量既影响训练也影响推理，是同一套契约的两端。
**追问 2**：线上 Badcase 怎么回流到训练，Self-Instruct 和蒸馏是一回事吗？
**答**：可以建数据飞轮：线上 Trace 里的失败调用、澄清样本经脱敏和人工复核后回流，把「该直接回答却调了工具」的边界样本单独建集做回归，防止下一轮微调把边界感训回去。Self-Instruct 是让模型生成指令与回答、筛选后微调，用更强教师模型生成调用轨迹训学生模型属于知识蒸馏，两者都可能用合成数据但不等价。工具 schema、Prompt 版本和训练数据要一起版本管理，接口字段变了同步重生成样本。

### X3-04 4. 什么是 MCP（模型上下文协议）？讲讲它的核心内容？
**面试官**：4. 什么是 MCP（模型上下文协议）？讲讲它的核心内容？
**我（60 秒口述）**：我的定义是 MCP 是 MCP Client 和 MCP Server 之间的通信协议，把外部工具和数据源怎么被标准化发现、描述、调用、返回定下来，别理解成「给模型加插件」。全称拆开最清楚：Model 面向大模型应用，Context 把外部上下文、工具和数据带给模型，Protocol 用标准协议固化交互。通信链路三部分：Host 是用户用的 AI 应用，比如 Claude Desktop、Cursor 或自建 Agent 平台；Client 在 Host 内和 Server 交换协议消息；Server 是开发者主要写的，把文件读取、SQL 查询、GitHub Issue 查询这些能力暴露出来，后面才是本地文件、数据库这些真实数据源。消息格式统一 JSON-RPC 2.0，方法像 tools/list、tools/call。边界要讲清：模型如何决策、任务如何编排仍属 Function Calling 和 Agent，MCP 只管接入。
**追问 1**：为什么用 JSON-RPC 2.0 而不是 REST，代价是什么？
**答**：REST 偏资源，比如 /users/1；工具调用偏「我要执行某个动作」，tools/call、resources/read 这种方法调用语义和 RPC 更贴，JSON 文本易读易调试、跨语言、不用额外序列化工具。代价是它没有 gRPC 那种强 IDL 和编译期类型约束，虽然能用 JSON Schema 描述参数，但 Schema 既是运行时校验规则也是给模型的提示，Server 仍要对所有参数严格校验。
**追问 2**：接了 MCP 是不是就安全、能直接上生产？
**答**：不能。Server 收到的参数一律当不可信输入，文件读取要限制目录、SQL 要参数化、高危操作要审批、返回数据要脱敏，`description` 和返回内容还得防夹带提示词注入。生产还要补 Trace ID、结构化日志、鉴权限流、超时熔断、工具级版本灰度与回滚、目录或 SQL 校验和第三方 Server 的供应链审计，协议统一了接入方式但不会替代这些责任。协议 revision 演进较快，具体以官方文档为准。

### X3-05 5. MCP 由哪几部分组成？
**面试官**：5. MCP 由哪几部分组成？
**我（60 秒口述）**：我按角色、能力、传输三层拆，不容易漏。角色层三件套：Host 承载用户交互和模型调用，Client 位于 Host 内和 Server 交换协议消息，一个 Host 可连多个 Server、通常每个 Server 一个 Client，Server 暴露能力、背后才是真实数据源。能力层 Server 侧三类：Tools 执行动作、可能改外部状态，Resources 只读上下文比如文件、日志片段、数据库 Schema，Prompts 可复用提示词模板；Client 侧还能提供 Roots 告知工作范围、Sampling 借 Host 侧 LLM 生成、Elicitation 执行中向用户补问，取决于 Host 是否实现。传输层消息格式统一 JSON-RPC 2.0，本地用 stdio、远程用 Streamable HTTP。可选能力和版本差异大，以官方文档为准。
**追问 1**：Tools、Resources、Prompts 为什么要分开，生产里怎么落？
**答**：会执行逻辑、可能改外部状态的放 Tools，便于按风险分级做权限、二次确认和审计；只读上下文放 Resources，可复用任务入口放 Prompts。工具名采用动词加名词，description 要写清适用条件、必填参数和禁用场景，比如查慢 SQL 的工具要写明什么时候不该调；描述写错（把黄瓜写成西红柿）模型就会选错，能力边界得让模型准确理解。
**追问 2**：新版规范说移除了 initialize 握手，面试里怎么讲才不踩坑？
**答**：把「消息格式与传输方式解耦」讲清就站稳了，同一套 JSON-RPC 消息可跑在任意传输层。握手、会话、通知这些随 revision 变化，比如较新的 revision 改成无状态自描述请求、移除会话 ID、把协议版本和客户端能力放进每个请求的 _meta，旧版握手作为兼容背景了解即可。接入前同时确认双方协议 revision、SDK 版本和 Host 能力；Roots 只是范围提示、不自动形成文件系统沙箱，这些细节以官方文档为准。

### X3-06 6. MCP 和 Function Calling 有什么区别？有没有实际跑过 MCP？
**面试官**：6. MCP 和 Function Calling 有什么区别？有没有实际跑过 MCP？
**我（60 秒口述）**：两者不是竞争或替代，是不同抽象层次。Function Calling 是「调用语言」，定义模型怎么表达调哪个函数、参数是什么，管单次调用的消息格式；MCP 是「工具生态协议」，定义工具怎么标准化打包、注册、被客户端发现、跨项目复用。最关键的是 MCP 底层依然靠 FC 驱动，所有魔法在宿主层，模型根本感知不到 MCP。用 HTTP 与 REST 类比最清楚，一个管怎么传、一个管怎么组织复用。算笔账：5 个应用各接 8 个工具就是 40 份对接代码，某字段一变同步改 5 处。跑过，我用 Claude Desktop 接文件系统 MCP：在 claude_desktop_config.json 的 mcpServers 下加 filesystem，写 command 为 npx、args 指向 server-filesystem 和允许目录，重启后 Host 自动起子进程、发现工具，直接问「读一下 report.md」即可，全程不写对接代码。
**追问 1**：接现成 Server 到底写多少代码，自己写 Server 最少几步？
**答**：接现成的就是配置加几行。自己写三步：用 SDK 的 list_tools 声明工具名、description 和 inputSchema，call_tool 实现执行逻辑并返回内容，stdio_server 以标准输入输出跑起来，三十行内能搞定。有个硬约定要记牢：stdio 下 stdout 是 JSON-RPC 消息通道，普通日志必须写 stderr，一行 print 混进去就可能让 Host 解析失败或断连。
**追问 2**：模型能不能感知 MCP，什么时候我不选它？
**答**：不能，Client 把工具定义转成模型原生 FC 格式传进去，模型视角就是一次普通 FC，完全不知道背后有 Server。推论是模型不支持 FC 时翻译层失效，MCP 完全用不起来。临时接一两个工具、快速原型、部署环境不许起子进程、或需要精细控制执行逻辑时，我用 FC 更合适；MCP Server 的部署、鉴权、版本兼容、可观测与排障都是额外运维成本。

### X3-07 7. Function Calling 也属于工具调用，请问什么场景下使用 Function Calling，什么场景下使用 MCP？
**面试官**：7. Function Calling 也属于工具调用，请问什么场景下使用 Function Calling，什么场景下使用 MCP？
**我（60 秒口述）**：核心判断一句：这个工具会不会在当前应用之外被用到？会就封装 MCP Server，不会就用 FC。但我会展示多维度框架，而不是「小项目 FC、大项目 MCP」这种单指标一刀切。机制差别是内嵌与独立：FC 的 schema 和调用逻辑写在项目代码里、换应用就重写，MCP 把工具做成独立进程、暴露标准接口，生命周期与应用解耦。落地按五问过：社区有没有现成 Server（GitHub、Slack、PostgreSQL、Puppeteer 都有，别重复造轮子）、要不要跨项目跨团队复用、综合看工具数量加 schema 复杂度加团队规模加变更频率、正式 Agent 系统还是 Demo、部署环境允不允许起子进程。反过来 FC 也有四类明确场景：快速原型、只服务单一应用、需精细控制执行逻辑、环境受限，选哪个本质是比较长期维护成本。
**追问 1**：为什么不给「超过 3 个工具就上 MCP」这种死门槛？
**答**：真正拐点是「感觉到散乱」，不是数量。五个复杂、多人维护、常变更的工具也能把 FC 拖进泥潭，两个极简且几乎不动的工具不值得引入独立 Server。判断本质是维护责任落在哪一侧：工具一多，schema 和调用逻辑散落各处，接口一变要改多处应用代码，MCP 把维护收口到 Server 一侧；同时也要算 Server 部署、鉴权、版本兼容和可观测的运维账。
**追问 2**：部署平台是 Serverless、不允许启动子进程，你怎么选？
**答**：stdio MCP 用不了，只能退回 FC 把逻辑写进主进程，或者评估 Streamable HTTP 远程 Server。另外 FC 还有三类场景要主动提：快速原型或 Demo、工具只服务单一应用（查本公司私有库，绝不会被别处用）、以及需要精细控制执行逻辑（权限校验、参数二次处理、链路追踪直接嵌代码，MCP 是独立进程、定制逻辑要额外约定）。两者不竞争，MCP 底层靠 FC 驱动。

### X3-08 8. 为什么有些特定的推理模型不支持 MCP 协议？
**面试官**：8. 为什么有些特定的推理模型不支持 MCP 协议？
**我（60 秒口述）**：根因是生成范式的结构性冲突，不是「厂商还没适配」，也不是上下文窗口不够。推理模型在答案前先跑一段完整思维链，thinking 是一次性连续生成、不能中途打断；工具调用天然多轮，需要生成到一半强制暂停等外部执行结果，脉络一断只能整个重来。问「保存状态恢复」代价极大：中间状态就是 KV Cache、体积庞大，暂停期间得原封不动占显存、几十秒不能服务别人，显存翻倍吞吐腰斩；更难的是工具结果在「想到一半」时改变输入，新旧思路可能矛盾。训练层还冲突：推理 RL 奖励「想到底且结论正确」，FC 训练要模型在合适时机打断自己输出 JSON。传导链是 thinking 连续、FC 支持不好、MCP 翻译层失效，本质是推理质量与工具能力的权衡。
**追问 1**：这到底是适配进度问题还是窗口问题，哪些模型真不支持？
**答**：把结构性冲突答成工程进度、或答「思维链太长占满窗口」，是这题两大雷。要分版本讲：o1-preview 官方明确不支持 FC，o1 正式版已支持，DeepSeek-R1 早期工具调用极弱，都是特定阶段的事实而非永久结论。硬混训常有三种失败：思考到一半跳出格式还错了的 JSON、彻底偏向一边（思考链缩水退化成普通模型或干脆不会调工具）、融合处推理断裂，具体能力以官方文档为准。
**追问 2**：我就要做「先取数再深度推理」的任务，怎么绕过这个折中？
**答**：后来的折中是让工具调用发生在思考阶段结束之后，模型先把推理链完整跑完、进入输出答案阶段才触发 FC，o3 和 Claude Extended Thinking 走这条路，interleaved thinking 允许在多次工具调用间穿插思考、部分缓解但本质仍是权衡，代价是思考阶段感知不到工具结果。绕法用两段式编排：先用普通模型或确定性工具取齐数据，再交给推理模型分析。选模型还要先查能力表，确认是否支持 tool calling、并行调用，以及 reasoning_content 或 Responses API 的 reasoning item 是否需随工具结果回传。

### X3-09 9. Skill 是什么？
**面试官**：9. Skill 是什么？
**我（60 秒口述）**：我理解 Skill 是可被 Agent 发现、按需读取的任务说明，本质是一份可复用的操作手册，最小形态就是一个目录加一个 SKILL.md。它解决「这类任务该按什么规则做」：接口返回格式、日志字段、慢 SQL 排查路径、Code Review 关注顺序都能写进去。结构上前面是 YAML frontmatter，至少 name（标识，小写连字符、不含保留字）和 description（做什么、什么时候用，是路由说明不是功能名），后面正文写流程、约束、示例和失败处理，复杂包再拆 scripts/、references/、assets/。边界要讲清：Skill 本身不提供工具能力，工具也不是必备部分，它更接近一次按需的上下文注入。放在链路里，Prompt 说用户要做什么，FC 发起动作，MCP 接外部能力，Skill 规定流程与约束，四者在不同位置。
**追问 1**：为什么 description 是最关键的字段，怎么验证它写得好？
**答**：因为 Agent 不会先把每个 SKILL.md 读一遍，而是先看描述判断该不该加载，写「处理 Excel 文件」这种只写能力不写场景的，就没法在需要时触发。好描述说清两件事：这个 Skill 做什么、什么场景下用，最好再带上用户可能说出口的词（PDF、表单、git diff 之类），方便规则或语义匹配。验证就攒一批典型 Query 看召回命中率和误触发率。
**追问 2**：Skill 和把规则全塞进 system prompt 差在哪，写的时候有什么坑？
**答**：全塞会白占上下文，窗口大了也不代表能挑出重点，还有 Context Rot 和 Lost in the Middle。Skill 靠渐进式披露按需加载，主文件建议控制在 500 行内、细节拆到 references/，还需要时再读。常见的坑是把 Skill 当项目 README 写、想把一个 Skill 写得太全、给 Agent 太多并列选择、术语来回换、以及让 LLM 去做格式转换和精确计算这类确定性工作，具体行数建议以官方文档为准。

### X3-10 10. MCP 和 Agent Skill 的区别是什么？
**面试官**：10. MCP 和 Agent Skill 的区别是什么？
**我（60 秒口述）**：两者不在同一层，不是二选一。MCP 是工具接入协议，规定 Client 和 Server 怎么发现、描述、调用能力，主语是「工具服务说我能提供这些函数」；Agent Skill 是任务知识与流程包，主语是「操作手册说用这些工具按什么流程做」，粒度粗得多，一个「数据分析报告」Skill 内部可能多步骤、调多个 MCP 工具，也可能完全不调工具只做文本分析。放进链路看分工最清楚：Skill 编排流程，每步调工具时靠 MCP 发现、靠 FC 触发，可以理解成菜谱、厨房、手的关系。还有个关键边界：Skill 的「加载」只是把工作方法补进模型当前工作信息，不更新权重、也不等于执行脚本，脚本仍要通过工具调用由宿主检查参数和权限后运行，MCP 也不替代模型推理。
**追问 1**：一个系统能不能只选其中一个？为什么？
**答**：能，只接一两个工具做原型不用 Skill，只做纯文本分析或固定规则审查不用 MCP，Skill 完全可以不含工具调用。但复杂任务里常见的是组合：Skill 定义流程、MCP 管工具发现、FC 做模型与工具通信，缺哪层都不完整。判断依据是任务有没有一套可复用的 SOP、以及能力要不要被多个宿主复用，不是看谁更「新」。
**追问 2**：官方材料说这些概念没有固定层级，我答「三层」会不会被怼？
**答**：把三层讲成常见的逻辑分层与依赖、而不是协议强制的固定调用链就稳妥。官方口径也强调 MCP Client 可以由规则引擎或界面直接发起 tools/call，组件怎么组合取决于运行时，不一定经过模型。所以我会补一句这是逻辑分层而非强制链路，既答出层次又不和「组件组合取决于运行时」冲突，具体以官方文档为准。

### X3-11 11. Function Calling、Skill、MCP 这三个有什么区别？
**面试官**：11. Function Calling、Skill、MCP 这三个有什么区别？
**我（60 秒口述）**：我先否掉「三个平行竞争方案」这个直觉，它们是从底到顶三层：Function Calling 是最底层的调用语言，MCP 在它之上做工具标准化，Agent Skill 在最上层把「用工具完成任务的知识和流程」封装成可复用模块，一句话记 FC 是手、MCP 是厨房、Skill 是菜谱。最快切入看谁在说话：FC 是「模型说我要调这个函数」，MCP 是「工具服务说我能提供这些函数」，Skill 是「操作手册说用这些工具按这个流程做」，主语、对象、粒度都不同。通信角色也不同：FC 在模型与函数之间是单次调用格式，MCP 在 Client 与 Server 之间是发现加封装管理，Skill 在 Agent 与知识模块之间按任务加载指令。时间线也印证层次，先解决怎么触发调用，再解决重复对接，最后才解决工具有了不知按什么流程用。
**追问 1**：为什么 FC 必须在底层，能不能跳过中间一层？
**答**：层级依赖是 Skill → MCP → FC：Skill 定义流程，每步调工具时靠 MCP 发现、靠 FC 触发。做菜类比能验证缺一层的后果：没有手拿不起刀，没有厨房空有菜谱，没有菜谱有满厨房厨具也不知先切什么后炒什么。用「分析近三个月销售数据找下滑产品线」串一遍最有说服力：Skill 加载报告流程，MCP 连数据库和 Python 执行器，FC 输出 tool_calls 取数，Client 路由回填，最后按模板出报告。
**追问 2**：把三者说成不同厂商的方案，问题出在哪？
**答**：最大雷就是「FC 是 OpenAI 的、MCP 和 Skill 是 Anthropic 的」，其次是把 Skill 降格成 prompt 模板、讲不出层级依赖。稳妥答法是把三层讲成常见逻辑分层与依赖，而非协议强制链路，并补一句组件可按需组合、运行时决定。另外别把 A2A 名片里的能力条目（也叫 Skill）和这里的 SKILL.md 能力包混为一物，具体概念边界以官方文档为准。

### X3-12 12. 什么是 A2A 协议？它和 MCP 协议的区别是什么？
**面试官**：12. 什么是 A2A 协议？它和 MCP 协议的区别是什么？
**我（60 秒口述）**：A2A 是 Google 发布的开放协议，解决多个 Agent 之间怎么通信协作；MCP 解决单个 Agent 怎么连工具和数据，一个向外连 Agent、一个向下连工具，一纵一横互补而非竞品，复杂系统里通常两个同时用。为什么需要：单 Agent 有工具数量、上下文窗口、专业能力三重天花板，多 Agent 的核心收益是上下文隔离，调度 Agent 把「行业趋势分析」委托市场 Agent，后者自己搜几十个网页、写草稿、反复迭代，中间过程都留在它自己上下文里，只把几百字摘要通过 A2A 返回。协作基础是 Agent Card，每个 Agent 在 /.well-known/agent-card.json 发布 JSON 名片，写清名称、能做哪类任务、是否支持流式和 push notification，新增 Agent 发名片就能被发现。任务单位是 Task，有 submitted、working、completed、failed 状态机，专为异步长任务设计，完成把结果作为 artifacts 返回。
**追问 1**：为什么 Task 非要状态机，生产落地还要补什么？
**答**：因为 A2A 专为异步长任务设计，竞品分析可能跑几分钟，提交后调度方能去处理别的事，靠轮询状态或 push notification 得知完成再取 artifacts，全程不需要知道接收方内部用了什么工具、调了几次 LLM，完全黑盒。生产还要补稳定 Task ID 与幂等去重、超时、取消传播、中间状态持久化，以及 artifacts 的权限校验与脱敏，别因来自「内部 Agent」就当可信内容。
**追问 2**：和微服务怎么对应，名片会不会被伪造？
**答**：后端视角看，Agent Card 约等于 API 文档，Task 状态机约等于异步消息队列，well-known 名片约等于注册中心记录，每个 A2A Agent 对外就是 HTTP 服务、不绑框架或语言。名片要做签名与可信发现，否则伪造名片能把任务引到恶意 Agent；A2A 也不替应用决定执行拓扑、不自动解决内部一致性，状态共享和冲突处理仍要应用设计，并和 MCP Server 一样纳入供应链审计。注意它名片里的 Skill 是能力条目，不是 SKILL.md。

### X3-13 13. MCP 协议通常采用什么通信方式？
**面试官**：13. MCP 协议通常采用什么通信方式？
**我（60 秒口述）**：分两层看最清楚：消息格式统一 JSON-RPC 2.0，传输本地用 stdio、远程用 Streamable HTTP，两者解耦，同一套消息可跑在任意传输层。消息层定义请求（带 jsonrpc、id、method、params，id 匹配响应）、响应（同 id 返回 result 或 error）、通知（无 id、不期待响应，比如工具列表变化时通知订阅方）。注意 tools/call 是协议方法、search_issues 是被调的具体工具，前者是「调用工具」这个动作、后者是「调哪一个」。失败还分两层：方法不存在或格式非法返回 JSON-RPC error，请求合规但业务执行失败在 result 里用 isError: true 返回，所以仅收到 HTTP 200 不代表工具成功。传输层 stdio 把 Server 作本地子进程、stdin 写一行 stdout 读一行、走内存 FIFO 不过网卡；Streamable HTTP 向单端点 POST，同步回普通 JSON、需流式的把同一响应升级成 SSE 流。
**追问 1**：MCP 是不是用 WebSocket，stdio 的日志该往哪写？
**答**：不是 WebSocket，早期远程的「HTTP + SSE 双端点」已被标记 deprecated，改成单端点 Streamable HTTP，关键是它没抛弃 SSE，流式部分底层仍是 SSE，只是合并端点。stdio 下 stdout 是 JSON-RPC 消息通道，普通日志必须写 stderr，否则被误当协议消息导致解析失败或断连；排查按三层区分：连接失败、JSON-RPC error（如 -32602 Invalid params）、result 里的 isError: true。
**追问 2**：双端点为什么被弃用，新版还改了什么？
**答**：同一对话拆 GET SSE 收推送和 POST 发请求两条通道，状态管理复杂，POST 后断网难以判断消息有没有被处理、SSE 会不会推回结果，合并成单端点对负载均衡和 serverless 更友好。后续 revision 还有无状态自描述请求、移除握手和会话 ID、版本与能力放进每个请求 _meta、通知方式调整等变化，接入前确认双方 revision、SDK 版本与 Host 能力，以官方文档为准。别把端点固定说成 /mcp（只是常见示例），也别把 stdio「不走网络」说成「Server 不联网」。

### X3-14 14. 说说 WebSocket 和 SSE 通信的区别及局限性？
**面试官**：14. 说说 WebSocket 和 SSE 通信的区别及局限性？
**我（60 秒口述）**：最本质区别是通信方向：SSE 是服务端单向推，客户端发消息要另起 HTTP；WebSocket 全双工，双方都能随时主动发。对 LLM 流式输出这种「模型一直推 token、用户只是看」的单向场景，SSE 完全够用，而且轻量、HTTP 原生、运维简单，所以主流流式 API 都选它。机制上 SSE 是对 HTTP 的巧用：GET 带 Accept: text/event-stream，服务端不关连接、持续往无限长响应体追加 data: 开头的纯文本，浏览器用 EventSource 逐条处理；文字天然适合 TCP 可靠有序，丢一个 token 整句意思可能就变了，你愿意等重传换正确内容。WebSocket 是独立协议，先发类 HTTP 请求升级、服务端回 101 Switching Protocols，此后变成全双工信道。用「中途打断」最能感受差别：SSE 要先关流再发新 POST，WS 直接在同一条连接发停止指令。
**追问 1**：SSE 就这么完美？生产里有哪些真实的坑？
**答**：至少三个。一是单向带来双通道架构，用户消息走 POST、回复走 SSE，靠 conversation ID 关联，服务端得找到对应长连接再推，状态管理和排障比 WS 单通道复杂。二是 HTTP/1.1 下同域名有 6 条连接上限，一条 SSE 占一条，多开标签页第 7 个被排队、看起来像页面卡死，HTTP/2 多路复用可解。三是只支持文本，语音图片要 Base64 膨胀约 33%，实时语音完全不可接受。断线重连要「接着上次不丢消息」，服务端必须支持 Last-Event-ID，很多实现省略了，用户重连看到的就是截断回答。
**追问 2**：横向扩容和代理穿透上，WS 有什么代价？
**答**：WS 是有状态连接，被负载均衡粘到某台后端后该用户所有消息都得发到同一台，新机器接不到老连接，常要把连接状态外移到 Redis 做发布订阅中转，多一跳、架构复杂；SSE 每次都是普通 HTTP 请求，LB 可路由到任意后端。另外企业代理、老 CDN、安全网关常不支持 WS 的 Upgrade 握手，直接当异常 HTTP 拒掉，SSE 始终是普通 HTTP、任何代理可透传；WS 还没内置请求-响应配对，要自己加请求 ID 维护「ID → 等待回调」映射表，断线重连的未决请求还得专门设计重试。

### X3-15 15. 为什么要用 WebRTC 协议？它和 WebSocket 在 AI 对话流中的核心差异是什么？
**面试官**：15. 为什么要用 WebRTC 协议？它和 WebSocket 在 AI 对话流中的核心差异是什么？
**我（60 秒口述）**：核心原因不是「支持 P2P 所以延迟低」，P2P 只是特点，真正分水岭在底层：WebSocket 基于 TCP，WebRTC 基于 UDP。语音铁律是「容忍丢包、绝不容忍延迟」，TCP 丢包强制重传、后续数据全等，延迟一堆积通话就卡死；UDP 不等重传，WebRTC 用丢包隐藏以前后帧插值生成合理音频替代，只极短暂音质下降，典型 50 到 150ms。文字正好相反，要每字准确有序，TCP 可靠有序是刚需。WebRTC 不是单一协议而是协议族：UDP 传输、DTLS 做密钥协商、SRTP 传媒体、RTP 带时间戳序列号、RTCP 质量反馈、ICE 处理 NAT 穿透、SDP 是握手协商书；还内置 AEC 回声消除、NS 噪声抑制、AGC 自动增益、ABR 自适应码率，用 WS 传语音这些全得自己造轮子。关键是 SDP 只是格式、需要信令通道，而这条通道常就是 WebSocket，两者配合不是替代。
**追问 1**：SDP 怎么传，为什么说用 WebRTC 还需要 WebSocket？
**答**：SDP 只是格式、不规定怎么传，需要一条信令通道，这条通道可以就是 WebSocket 或 HTTP。所以关键结论是两者配合而非替代：WS 传信令、UDP 通道传音频，用 WebRTC 做 AI 语音仍需 WebSocket。ICE 还有三级降级，同局域网直连、STUN 打洞建 P2P、失败走 TURN 中转；对称 NAT 对每个目标分配不同出口端口，STUN 探测的端口在对端连入时已变，必然失败只能 TURN。
**追问 2**：OpenAI Realtime API 为什么选它，落地成本在哪？
**答**：它要求端到端延迟低于 300ms、语音双向同时流动、可随时打断、无回声循环，TCP 系方案达不到，官方同时提供 WebRTC（浏览器/移动端）、WebSocket（服务端到服务端）、SIP（呼叫中心/VoIP）三类连接，以官方文档为准。代价很真实：信令服务器、STUN/TURN 部署运维、证书和 NAT 探测都要成本，网络受限时还可能 fallback 到 TCP/TURN，低延迟优势会打折；延迟要求不极致的场景常见折中是 getUserMedia 加 AudioWorklet 加 Base64 走 WebSocket，传输层是 TCP 而非 RTP/SRTP。

### X3-16 16. 有没有用过大模型的网关框架？网关层解决了什么问题？
**面试官**：16. 有没有用过大模型的网关框架？网关层解决了什么问题？
**我（60 秒口述）**：LLM Gateway 我理解成「API 网关能力 + 模型调用控制面」，是应用层和模型供应商之间的一层治理入口，不一定替代企业已有 API 网关。直连模型问题会集中暴露：模型名写死，换供应商到处改代码；API Key 分散、轮换困难；429 后业务各自疯狂重试越重试越糟；成本月底只知道总账单，没法按租户、功能、Prompt 版本归因；所有请求走同一旗舰模型，简单任务浪费钱；日志缺失，用户投诉「刚才 AI 胡说」时找不到输入输出。网关把统一接入、Provider Adapter、模型路由、Fallback、多维限流、Token 预算、成本统计、观测审计和缓存收口。但要分清 Router 只管「这个请求选哪个模型」，Gateway 管整次调用生命周期；对多数单团队项目，应用内一个轻量统一入口做超时、重试、日志、简单路由就够。
**追问 1**：Fallback 是不是失败就换个模型重试，生产怎么落地？
**答**：不是，先分错误类型：网络瞬断适合短重试后切备用，供应商 5xx 适合重试加熔断加切供应商，429 要读 Retry-After 必要时排队，上下文超限该压缩或减少检索片段而不是重打，参数错误和安全拒答不该重复打供应商。更关键的是带副作用、已执行工具调用或扣费的请求，切模型前要确认该步骤是否可重放；流式已经发给用户的片段不能两个模型拼成一段，每次 attempt 都要留痕并按幂等去重。
**追问 2**：怎么衡量网关做得好不好，什么时候才值得上独立组件？
**答**：按场景、模型层级和供应商分别看路由命中率、质量通过率、Fallback 率、平均成本、P95 延迟、TTFT、429 率、缓存命中率、结构化解析失败率，还有最易忽略的「路由漂移」——便宜模型升级后可能够用、原本稳的模型升级后某类任务变差，所以路由规则要像 Prompt 一样有版本、像代码一样做回归。是否上 LiteLLM、Cloudflare AI Gateway、Kong AI Gateway 这类独立组件，看团队技术栈、合规、流量、是否自托管和是否已有 API 网关，顺序是先解决工程治理再追求智能路由，具体选型以官方文档为准。

### X3-17 17. 工具很多时，Agent 如何做 Tool Routing，减少 Token 并避免选错工具？
**面试官**：17. 工具很多时，Agent 如何做 Tool Routing，减少 Token 并避免选错工具？
**我（60 秒口述）**：我不把上百个 Schema 全塞给模型，而是分层路由：先建结构化工具注册表，用产品、租户、角色、环境、任务状态做确定性硬过滤，再粗分类缩业务域、域内检索召回 Top-K，最后只把少量候选的完整 Schema 动态绑定给 LLM 精选并生成参数。全塞有四类问题：Token 上工具定义和系统提示、历史、检索资料抢上下文，Prompt Cache 只降费没让可见工具变少；选择混淆上 order_get、order_search、order_detail 描述都写「查询订单信息」，根源是边界没讲清；权限风险上把 payment_refund 暴露给普通客服，扩大误调用和注入攻击面；还有更长输入带来的延迟。落地我强调先鉴权再召回：检索器只能在当前请求有权看到的集合里搜，不能先全库召回再靠 Prompt 说这个不能用。
**追问 1**：为什么不能拿 Embedding 相似度的第一名直接执行，怎么评路由好坏？
**答**：相关性既不是权限也不是参数满足，「像」不等于「可调用」。召回层看 Recall@K、候选集大小和 Schema Token，精选层看选择准确率、相似工具误选率、无工具拒选准确率、参数合法率，业务层看任务成功率、端到端延迟、未授权工具暴露率与审批覆盖率，评测集要含 Hard Negative、多意图、无需工具、缺参数、无权限请求。粗分类要偏高召回、多意图保留多类别，精召回追求「别漏掉正确工具」而不是「排第一就执行」。
**追问 2**：正确工具压根没进 Top-K，或者模型输出了候选集外的工具名，怎么兜底？
**答**：正确工具没进 Top-K 要回召回层——改写查询、扩大 Top-K、重新粗分类，而不是让 LLM 在错误候选里反思；候选集外的工具名一律拒绝，执行前仍要过 Schema、权限、风险和审批校验。低置信时改写、扩大重召回或向用户澄清，高风险动作走确定性规则或人工审批，首选不可用切备用或降级只读。另外别把 Tool Routing（当前 Agent 能看到哪些工具）和 Multi-Agent Routing（任务交给哪个 Agent）混为一谈，为躲工具多就无原则拆几十个 Agent，只是把工具目录变成 Agent 目录。

### X3-18 18. 工具调用格式非法、参数错误、超时或失败时，Agent 如何容错？
**面试官**：18. 工具调用格式非法、参数错误、超时或失败时，Agent 如何容错？
**我（60 秒口述）**：我先分四类错误再分层兜底，核心原则一句话：可降级，但禁止模型编造业务事实。格式非法和参数错走校验修复：用 JSON Schema 拿到具体错误，比如某个字段必须是枚举、另一个必须是 number，把错误连同原始输出反馈给模型让它只修结构，最多重试 1 到 2 次，仍失败进降级。但 Schema 校验只是第一层，模型给的参数一律当不可信输入，后面还有业务校验（订单归属、状态流转、金额范围）和权限校验（身份、角色、租户、数据范围）。超时和失败这边：查询类设较短超时，写操作谨慎重试且必须配幂等，由可信执行层生成 idempotencyKey、唯一约束兜底；外部依赖失败返回明确错误码，模型拿到工具错误只能解释「当前无法完成」，不能猜结果。
**追问 1**：为什么不是一失败就把原始问题重跑一遍，怎么验证修复有效？
**答**：重跑既贵又没针对性，把具体校验错误反馈给模型、让它只修结构更省也更准。验证看结构化解析失败率、失败类型分布和降级命中率，并把所有失败样本写日志反推 Schema 和 Prompt 的改进点；别让「看起来能跑」掩盖格式漂移，尤其别把 temperature 设成 0 就当成稳定保证。
**追问 2**：重试会不会造成重复扣款，超时没收到响应到底算不算失败？
**答**：会，模型重试、网络重试、队列重试、业务服务重试会叠加，所以不能安全重试的工具就不该被 Agent 随意调用；退款、发券这类写操作还要拆成 prepare 和 confirm 两步做二次确认。超时没收到响应不等于操作没发生，要查状态、沿用稳定操作标识去重或保留「结果未知」，异步还要区分「请求已受理」和「工作已完成」。降级按场景分：工单分类失败进人工队列标 AI_PARSE_FAILED、缺订单号就追问用户、风险评分用规则引擎兜底、工具超时返回「系统繁忙」而不继续让模型猜。

### X3-19 19. 为什么要把 Agent 的工具执行流程封装成 CLI？
**面试官**：19. 为什么要把 Agent 的工具执行流程封装成 CLI？
**我（60 秒口述）**：核心是把「工具能力」与「调用入口」分开，让流程能独立运行、被不同调用方复用；业务逻辑与聊天状态解耦后，同一套能力既能给 Agent 调用，也能给开发者调试、脚本和定时任务用。Agent 用工具其实发生两件事：模型决定采取什么动作，模型之外的程序把动作真正执行出来；同一能力可有函数、命令行、网络接口多种入口，换入口不必改内部逻辑，CLI 就是「指定程序与参数、执行、通过输出与退出状态交回结果」的程序接口。落地我把「检查格式、读内容、转换、核对产物」这类确定流程交给代码，模型只选何时用；依赖拆成入口解析、业务核心、结果适配三层；机器契约上 stdout 返回结构化结果、stderr 记诊断，日志混进机器结果会让 JSON 解析失败。
**追问 1**：模型返回了命令，等于运行了吗，接入层还要做什么？
**答**：不等于，模型输出命令时操作还没发生。宿主要有执行适配层：解析模型请求、确认访问范围、启动固定程序、解析结果回传；还要分清 CLI 与 shell（后者处理管道、重定向、变量展开），把可执行文件与参数分别交给进程启动接口、让文件名作为一个参数传递，可减少命令拼接问题，但不能替代业务参数校验。业务工具接受文件标识而 CLI 接受路径时，适配器要解析标识并检查路径是否在允许范围。
**追问 2**：退出码 0 能当业务结果吗，放进子进程是不是就自动隔离了？
**答**：不能。0 通常只表示按约定正常结束，正常搜索无结果也可以是有效空结果；非零含义看工具定义，异步要分「请求已受理」和「工作已完成」，stderr 有内容不等于失败，超时没响应也不等于操作没发生。更要紧的是子进程通常继承宿主身份与环境，加一层 CLI 不会自动限制文件与网络访问，真正边界靠受限身份、隔离环境、OS 规则与业务接口落实。代价还有进程启动、数据传递和部署成本，只在当前程序里用的小函数直接调用更省事。

### X3-20 20. Agent 接入工具时应该如何选择 CLI 或 MCP？
**面试官**：20. Agent 接入工具时应该如何选择 CLI 或 MCP？
**我（60 秒口述）**：我的结论是两者处在不同层次、可以组合而不一定要互相替换：CLI 提供命令行执行入口，MCP 约定客户端与服务端怎样发现和调用能力。放进一条链路就清楚：Agent 宿主、MCP 客户端、MCP Server、CLI 或业务函数、实际资源，CLI 是执行入口，MCP 是外面的接入层，Server 后面可连函数、已有 CLI 或远程 API，协议规定交流方式、不要求改写底层算法。选型看调用方的接入需求与维护成本：单一可控宿主加已有稳定 CLI，直接适配更简单；一项能力要被多个兼容 MCP 的宿主复用，MCP 接入层更有价值。把「本地用 CLI、远程用 MCP」当分界站不住，本地或远程是独立部署选择，CLI 也完全能访问远程 API。
**追问 1**：直接适配 CLI 时宿主还要写哪些适配，MCP 标准化后还剩哪些责任？
**答**：有命令能执行不代表模型自然知道怎么用，宿主仍要提供工具名称、用途、参数说明，把结构化请求映射成程序参数，并把结果、诊断日志、退出状态按约定解释，不能把终端文字拼一起当业务结果。MCP 统一了 tools/list 拿工具名、描述和 inputSchema、tools/call 发参数返回，但宿主仍决定展示哪些工具、组织上下文，服务端仍负责业务实现、参数校验、权限和错误处理。还有个独立判断要点：模型支持工具调用，和宿主实现了 MCP Client，是两件事。
**追问 2**：已有 CLI 怎么用 MCP 包装，通道相同是不是就能直接当 MCP 消息？
**答**：新增一层 Server 把协议参数转成 CLI 参数、启动原程序、据退出状态与业务结果构造 MCP 返回；参数类型、结果内容、错误语义要对齐，「无匹配记录」不等于「程序启动失败」，超时与取消要核对实际行为。不能直接当：stdio MCP 和普通 CLI 都可能用 stdin/stdout，但 CLI 打印一份业务 JSON 就退出，MCP 服务要收发符合协议的消息、处理发现与调用，stdout 要保持可解析、诊断写 stderr。协议也不能替代权限与幂等，工具出现在列表里只说明可被发现，描述里的「只读」不能替代实际检查。

### X3-21 21. Agent 的代码执行沙箱应该如何设计？
**面试官**：21. Agent 的代码执行沙箱应该如何设计？
**我（60 秒口述）**：核心是让代码只拿到当前任务需要的权限，并把资源消耗限制在预算里；模型生成的代码按不可信处理，不能只靠 Prompt 约束。边界至少两方面且不能互代：访问限制（能碰哪些文件、网络、系统能力）与资源限制（能消耗多少 CPU、内存），看不到宿主文件也可能占满内存，几秒内也能读走敏感数据。我按四层设计。一是最小能力，每任务独立空间分只读输入、可写临时区和输出区，但工作目录不等于文件边界，要靠 namespace 挂载视图加访问权限，凭据不无差别继承。二是资源预算作用于整个进程组，用 cgroup 管 CPU、内存、任务数，CPU 配额与总时限两个都要。三是执行环境，容器轻但共享宿主内核，任意代码评估微虚机。四是沙箱外运行器管全生命周期。
**追问 1**：Prompt 里写「只允许完成当前任务」算不算边界，生产怎么落？
**答**：不算。程序真正能做什么取决于运行时拥有的能力，OS 处理文件读取、网络连接、进程创建时检查的是进程身份、访问权限和系统规则，不会因为代码来自「数据分析任务」就自动放行。把整个用户目录以可写方式挂进容器，等于把能力重新交出去；第三方 Server 至少先看源码，或用 Docker、cgroups、namespace 隔离，文件与网络权限要一起考虑，配置失败绝不能退回不受限宿主执行。
**追问 2**：主程序退了后台进程还在跑、符号链接指到目录外，怎么处理，隔离等于结果正确吗？
**答**：主程序创建后台进程后自己退出，只统计或停止主程序会漏，得把相关进程归入同一受控执行单元一起计量、限制、终止，Linux cgroup 就是按组管资源的账本。符号链接可能指向目录外，必须核对实际对象；结束后只导出允许范围内的产物、清理临时数据、任务之间隔开。隔离也不等于结果验证，产物存在不代表内容满足任务要求，仍要业务规则或测试检查，这是最容易被漏掉的一层。

### X3-22 22. Agent 的 Skill 加载机制是如何实现的？
**面试官**：22. Agent 的 Skill 加载机制是如何实现的？
**我（60 秒口述）**：Skill 通常采用渐进式加载。宿主先扫描允许的目录发现能力包，解析 SKILL.md 顶部 YAML frontmatter 的 name 和 description 形成轻量目录；模型据任务与描述判断需要哪个，或用户显式指定；宿主再把对应正文读进上下文，references/、assets/、scripts/ 这些参考、模板和脚本留在包里，执行到需要它们的步骤才取用。三层各答一问：元数据回答「该选哪个能力」，正文回答「选中后怎样开展」，资源回答「当前步骤需要哪些材料」，相对路径从 Skill 根目录解析。最关键一句是，这里的「加载」主要是把工作方法补进模型当前的工作信息，不会更新模型参数，也不等于执行脚本；脚本仍要通过工具调用由宿主检查参数和权限后运行，加载权限与执行权限不同。
**追问 1**：启动时把全部 SKILL.md 塞进 Prompt 行不行，「匹配到文件名」算加载成功吗？
**答**：不行，一次只用少数能力，全塞白占上下文还会 Context Rot、Lost in the Middle；主文件建议控制在 500 行内，细节拆到 references/。只匹配文件名更不算，正文还在磁盘、模型没拿到具体步骤；「选择」和「内容交接」必须接起来，模型输出「使用某 Skill」只表达选择，只有正文真正进入上下文才具备按它工作的材料。程序缓存与模型上下文是两个位置，别把预缓存当已加载。
**追问 2**：长任务压缩上下文后 Skill 还在吗，「Skill 没生效」怎么排查？
**答**：Compaction 后按来源重读时要核对内容版本，避免用旧版手册指导新任务；加载权限与执行权限也不同，允许读手册不等于允许改任意文件或访问外部服务。排查按四状态走：目录没暴露、能力选错、正文没读到、执行条件没满足。开放格式只约定包内内容怎么组织，发现位置、触发方式、load_skill 这类入口都由宿主实现、各不相同（Claude Code、Cursor、Codex、Copilot 并不统一），以官方文档为准。
