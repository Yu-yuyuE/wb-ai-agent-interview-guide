### J4-01 什么是 RAG？为什么需要 RAG？
**面试官**：什么是 RAG？为什么需要 RAG？
**我（60 秒口述）**：RAG 就是检索增强生成，回答前先从外部知识库捞出相关片段，跟原问题一起进 Prompt，让模型基于可核对的证据作答，而不是只靠参数记忆。为什么需要它，我讲三个约束：知识有截止点，新政策、新产品手册得靠检索动态注入；私有数据进不了公开训练集，按权限取片段就行、不用重训；纯生成的事实性幻觉难核查，RAG 能附出处把回答约束在证据上。但我从不说它能消灭幻觉，漏召回、上下文噪声、引用错配都会让答案跑偏，所以生产得配引用校验、拒答和 Faithfulness 监控，这是套工程闭环，不是接个向量库就完事。
**追问 1**：你刚说 RAG 不能消除幻觉，为什么加了检索还会错？生产上这层约束怎么落地？
**答**：因为幻觉不只来自模型凭空编，检索、上下文、生成任一段出错都会偏。我把失败样本分成漏召回、噪声拼凑、引用错配、指令不遵循四类分别查；Prompt 里写死「只基于给定上下文回答、不足明说无法判断、关键结论附来源」，但提示词管不住模型是否真遵守，所以引用校验和证据置信度判断必须放在 Prompt 外执行，再用 Faithfulness 和 Citation Accuracy 盯线上。
**追问 2**：如果用户问的知识库里根本没有，或者新旧两版政策都被召回了，你会怎么处理？
**答**：前者要能拒答，后者要靠版本治理，都不能硬答。证据不足、证据互相矛盾或用户无权访问关键文档时，我触发查询改写、扩大范围或外部搜索，仍不足就拒答、追问或转人工；新旧并存说明活动版本切换失效，得查 `active_version` 和 `is_deleted`，用「先写 building 新版本→原子切别名→旧版标记删除」四步兜住。

### J4-02 RAG 和传统搜索引擎有什么区别？
**面试官**：RAG 和传统搜索引擎有什么区别？
**我（60 秒口述）**：两者都有检索，但交付物不同：搜索返回按相关性排好的文档列表让人自己读，RAG 把召回片段送进 LLM 整合，直接产出带引用的自然语言答案。差异分三层：检索机制上搜索以倒排索引加 BM25 为核心，RAG 围绕给模型高信噪比证据设计、常叠向量召回和元数据过滤；结果形态上一个给原文列表、一个给解答；延迟成本上搜索几十毫秒、边际成本极低，RAG 多了 LLM 推理、首字到秒级还每请求烧 Token。落地判断我只看一件事：用户是要找原始材料，还是要综合多份材料得结论。找制度原文、核对接口、下模板，没必要上 RAG，很多企业两套入口都留着。
**追问 1**：你说很多企业两套入口都留着，生产上怎么决定一个请求走搜索还是走 RAG？
**答**：按用户目标和风险分流，不是全量上 RAG。简单查找、编号、标题、关键词定位走 ES/BM25 加权限过滤，链路短、可控、可审计；客服解答、技术排障、制度解读、跨文档总结对比才走混合检索加重排加引用溯源那套。我会用问题类型做个可解释的路由，低置信度还能降级，避免每个请求都付 LLM 的钱。
**追问 2**：RAG 链路里最容易出事、搜索反而没有的风险是什么？
**答**：是越权泄露和引用错误，搜索给原文链接反而更可审计。RAG 要做检索前按 `tenant_id`/`acl` 前置过滤、上下文脱敏、日志治理；我踩过的坑是向量库先返回 Top-10、其中 8 条无权访问，过滤后剩 2 条还被当成「只找到两条相关内容」，所以过滤必须参与查询而不是事后筛。

### J4-03 RAG 和微调怎么选？什么时候用 RAG，什么时候微调，什么时候两者结合？
**面试官**：RAG 和微调怎么选？什么时候用 RAG，什么时候微调，什么时候两者结合？
**我（60 秒口述）**：职责边界很清楚：RAG 补模型缺的外部或最新知识，微调治输出风格、格式、指令遵循不稳，别把微调当知识注入。我常拿开卷和闭卷打比方，RAG 是每次回答前查规章手册、制度改版只更新索引；微调是把细则背进权重，规则一变就得重训重评，还给不出原文出处、没法按用户权限细粒度隔离。所以知识密集问答、法规制度、产品文档、实时信息上 RAG；语气风格、固定格式、领域术语、垂类蒸馏才考虑微调。要结合是法律医疗金融那类场景：微调管术语和推理规范、RAG 注入实时事实和可追溯证据。工程上我先把 RAG 链路和评测集搭稳，确认痛点真是指令遵循，再评估微调。
**追问 1**：为什么不直接把领域知识微调进去，非要维护一套检索链路？
**答**：因为代价结构完全不同，知识会过期。RAG 更新知识库或向量索引即可，知识留在外部、检索时按 ACL 动态过滤；微调要重构训练集、训练加评估，知识过期后回滚成本高，还有灾难性遗忘和过拟合。6 维度对照里「数据安全」这行是硬伤：训练数据的模式进了参数，就很难按用户权限隔离，这对企业知识库基本不可接受。
**追问 2**：如果已经微调过一版，现在业务规则大改又上了新基座模型，你怎么排升级顺序？
**答**：先切 RAG 侧的数据和索引，再动模型，别两件事一起改。我会用索引别名做 `index_v1`/`index_v2` 切换、保留旧索引约 7 天快速回滚，Embedding 模型升级必须重建索引且查询侧校验版本；微调模型单独走 A/B 和回归集，一次只替换一个变量，这样差异才能归因到模型还是检索。

### J4-04 RAG 系统中 Embedding 模型怎么选？为什么？
**面试官**：RAG 系统中 Embedding 模型怎么选？为什么？
**我（60 秒口述）**：先看业务约束是闭源 API 还是开源私有化，用 MTEB 榜单初筛，但最终必须在自己的问题集上验召回率、延迟和部署成本。因为 Embedding 是把文本映射到高维稠密空间让语义相近的靠得更近，退款、退货流程用词不同也能召回办理指南，可榜单是公开评测，我们业务里有内部缩写、专有型号、错误码和脏输入，通用模型往往不够。落地分两类：闭源像 text-embedding-3 系列开箱即用、多语言好，开源像 BGE、Qwen3-Embedding 适合数据不出内网。含大量专名我一定配 BM25 兜底；还有两个硬约束——维度不是越高越好，索引的距离度量必须跟模型推荐一致，不然召回质量掉甚至命中不了索引。
**追问 1**：你说必须在业务集上验证，具体怎么用评测集判断该不该换模型？
**答**：固定其他变量只换 Embedding，在同一批标注问题上比 Context Recall 和最终答案准确率。我会把 `embedding_model`、`embedding_model_version`、`embedding_dimension` 写进元数据，查询时校验版本，对比时同时看延迟和内存成本。反例是测试环境用本地 sentence-transformers、生产用 OpenAI API，测试看着正常、上线召回直接腰斩——两个模型空间根本不通用。
**追问 2**：数据不能出内网，但开源模型效果差一截，你怎么权衡？
**答**：优先私有化开源模型，用混合检索和领域适配补效果，而不是为了几个点把数据送出去。我在内网用 BGE/Qwen3-Embedding 起基线，配 BM25 兜专有名词，再用失败的精确匹配样本决定是否做领域适配；`dimensions` 这类 Matryoshka 截断能降维省内存，但要重跑召回评测确认损失可接受。

### J4-05 余弦相似度、内积和欧氏距离有什么区别？
**面试官**：余弦相似度、内积和欧氏距离有什么区别？
**我（60 秒口述）**：余弦看方向、内积算乘积和、欧氏看绝对距离，向量做过 L2 归一化后三者排序等价，RAG 最常用余弦。机制上余弦对模长不敏感，文本长短和词频变化不容易扰动语义方向；内积在归一化后跟余弦等价还更快；欧氏受模长影响，归一化后排序也跟余弦距离一致。主流 Embedding 多以余弦或归一化内积作训练目标，所以默认余弦。落地我最在意一个坑：pgvector 里 <=> 是余弦距离、vector_cosine_ops，<#> 返回负内积、值越小越相似，<-> 是欧氏；查询运算符必须和建索引时的 operator class 严格一致，否则用不上向量索引、退化成全表扫描，我会用 EXPLAIN ANALYZE 确认命中才上线。
**追问 1**：既然归一化后排序等价，为什么还要分三种度量、不能统一用余弦？
**答**：因为等价是有前提的，且不同库、不同模型有各自的优化路径。若模型明确按 L2 训练或索引按 `vector_l2_ops` 建，就该用 `<->`；已归一化又追求计算效率可用 `<#>` 内积。还有个方向坑：余弦「相似度」和「距离」相反，`<=>` 返回的是距离，0 完全相同、2 完全相反，相似度要拿 1 减，混用会把排序整个反过来。
**追问 2**：线上突然召回全乱了，排查发现有人改过索引 operator class，怎么快速定位？
**答**：先看执行计划是不是从 Index Scan 变回全表扫描。我 `EXPLAIN ANALYZE` 核对查询语句的运算符和索引的 operator class 是否一致，再检查是否有过距离类型、过滤条件或索引参数的变更；这种问题常伴随 P95 延迟飙升，还容易被误当成召回质量下降去乱调 `ef_search`，其实是配置漂移不是模型坏了。

### J4-06 RAG 的幻觉问题怎么解决？RAG 一定不会产生幻觉吗？
**面试官**：RAG 的幻觉问题怎么解决？RAG 一定不会产生幻觉吗？
**我（60 秒口述）**：RAG 靠提供原文证据降低无根据编造概率，但不能彻底消除幻觉，必须配引用校验、拒答机制和评测反馈。我先纠个误区：幻觉不只是模型凭空编，检索漏召回让正确证据没进候选池、上下文混入旧版本或相近规则被拼成错结论、引用错配、没遵循指令，都会错答。落地分四层：Prompt 限定证据边界，只基于给定上下文、不足明说无法判断、关键结论附来源；检索后加证据质量判断，置信度低或证据矛盾就改写、扩范围或拒答转人工；引用校验放 Prompt 外，因为提示词表达拒答但没法验证模型是否遵守；再用 Faithfulness 和 Citation Accuracy 盯线上。边界要讲清：忠实于上下文不等于答案正确，照过期手册答可以很忠实却违反当前政策。
**追问 1**：你怎么监控「加了 RAG 还在幻觉」这件事，指标怎么设？
**答**：用 Faithfulness 盯「答案能否被上下文支撑」，用 Citation Accuracy 盯「引用位置是否支撑对应结论」。我会把回答拆成事实主张逐条核对上下文，纯拒答和空答案要单独处理、不能当满分样本；RAGAS 的 Noise Sensitivity 是 0 到 1 越低越好，偏高时先查分块、Reranker 和上下文排序，再查 Prompt 有没有写「只使用相关资料」。
**追问 2**：知识库里压根没有答案，模型却照着参数知识答对了，算不算幻觉、要不要拦截？
**答**：算「不可追溯的正确」，高风险场景同样要拦。它这次对不代表下次对，也没法附出处；我的做法是 Prompt 要求无依据就明说无法判断，并对「凭参数答对但 `golden_context` 未命中」的样本单独标记，用拒答行为评估而不是给检索满分。

### J4-07 什么是 Lost in the Middle 问题？怎么应对？
**面试官**：什么是 Lost in the Middle 问题？怎么应对？
**我（60 秒口述）**：上下文混进大量无关文档时，模型对中间位置关键事实的提取准确率明显下降，本质是注意力稀释，应对思路是缩小证据范围加排序加压缩，而不是无脑加长窗口。后果挺具体：把相似但不相关的段落当依据、忽略中间的重要信息、回答变长却不聚焦、引用错来源、成本和首字延迟一起上去。落地我做四件事：最相关证据放前面、按证据强度排序、相邻片段保序；压缩去重只留能支撑一个结论或例外的片段；靠 RAG 检索层天然收缩范围；跨文档对比按主题分组、时间分析按时间线。边界是别指望窗口变大就忽略信噪比，长上下文和 Lost in the Middle 其实是一体两面。
**追问 1**：排序规则具体怎么定，你怎么验证证据真的被用上了？
**答**：五条规则：最相关放前、相邻片段保序、矛盾片段标更新时间和版本、被引用片段保留来源、低置信度和高置信度不混放。验证我用自定义 `Context Usage` 指标诊断「材料进了 Prompt 却没被用上」，特意不叫 RAGAS 的 `Context Utilization` 免得口径混淆；再抽样人工复核，因为 LLM-as-a-Judge 对中间内容漏判挺常见。
**追问 2**：如果 Top-K 必须给到很大才够召回，中间位置问题又回来了，怎么破？
**答**：扩的是粗召回候选池，不是直接拼进上下文。我把 `recall_top_k` 放到 30–100，经 Rerank 选 5–10、压缩后 `context_top_n` 只留 3–6 条送进 Prompt；既提高证据进池机会，又不让噪声和 Token 一起爆，首字延迟也可控。把新增候选直接拼进上下文是最常见的错法。

### J4-08 长上下文窗口是否会取代 RAG？
**面试官**：长上下文窗口是否会取代 RAG？
**我（60 秒口述）**：不会，两者互补：长上下文适合单次、少文档的通读，企业级海量知识库问答仍得靠 RAG 先把证据范围缩小。128K 到 1M+ Token 的窗口分析一份完整财报、总结长会议记录确实合适，这类任务切块反而漏全局脉络。但进企业场景撞四个硬约束：知识库动辄数千万到数亿 Token 远超窗口；即便勉强塞进去，每次带几十万输入 Token 的 TTFT 和账单成本远高于只传几千 Token 的检索片段，Prefix Caching 也救不回来；注意力稀释；还有按租户、角色、ACL 严格过滤和记录引用了哪篇哪页的权限与溯源，RAG 检索层天然承担。落地按三条主线选：只定位原始文件走搜索，知识频繁变动要权限隔离加引用走 RAG，单篇长文全局阅读才直接喂全文。
**追问 1**：你说成本救不回来，能不能给个可量化的判断口径？
**答**：看每次请求的输入 Token 和 TTFT，而不是窗口上限。同样一个普通问答，塞几十万 Token 的输入成本和首字延迟，对比只传几千 Token 检索片段差一个量级；我会用 P95 延迟、Token 用量和缓存命中率做工程指标，在评测集上跟 RAG 方案一起比，不靠「窗口够大」拍脑袋。
**追问 2**：长上下文方案里怎么做到按用户权限只看到该看的页？
**答**：很难，这正是我不用它替代 RAG 的关键原因。全文喂进去等于放弃检索层的 ACL 前置过滤，除非在拼上下文前按 `tenant_id`/`acl` 逐段裁剪并留审计，但那就又变成一套检索了；RAG 能在召回前收紧 `tenant_id`、文档类型、版本和更新时间，还能明确记录回答引用了哪篇哪页，合规场景这点没法妥协。

### J4-09 RAG 系统的评估指标有哪些？
**面试官**：RAG 系统的评估指标有哪些？
**我（60 秒口述）**：必须检索质量和生成质量分开评，再叠工程指标，只看最终答案分数没法定位是哪一环坏了。检索侧我看 Hit Rate@K、MRR、Context Recall、Context Precision，分别盯正确证据进没进前 K、第一个正确排多前、证据找全没、放进上下文的有多少真相关；生成侧看 Faithfulness、Answer Relevancy、Citation Accuracy；工程侧再加 P95 延迟、Token、重排耗时、缓存命中率。工具上 RAGAS 把这几项拆得清楚，LangSmith 管 Trace。落地我有两个坚持：LLM-as-a-Judge 只是辅助信号，上线前至少抽样人工复核，校准它是不是偏爱长答案、漏判引用错误；每次改动都在同一评估集上比这几项加延迟成本，并分别记录粗召回、重排后、最终上下文三个阶段，别把候选池高召回当成模型真看到的证据覆盖率。
**追问 1**：指标这么多，一次调优你到底以哪几个为准？
**答**：检索改动看 Context Recall 和 MRR，生成改动看 Faithfulness 和 Answer Relevancy，任何改动都带上 P95 延迟和成本。我固定评估集、一次只改一个变量，用 Recall@K/Context Precision 这些可复现口径；反例是只报一个 E2E 分数，检索差和生成差都表现成「回答不准」，方向完全相反。
**追问 2**：有的题知识库里本来就没答案，指标会不会算错？
**答**：会，得标成「不适用」而不是给满分或 0。知识库外问题没有期望证据，Recall 分母为零，应转去评拒答行为；执行失败和正常拒答也要分开记，不计入答案正确性分母。示例是计划 10 题、2 题超时、其余 8 题全过，报告要同时给执行成功率 8/10、有效通过率 8/8 和超时数 2，只报 100% 会掩盖不可用请求。

### J4-10 RAG 的优势和局限性是什么？
**面试官**：RAG 的优势和局限性是什么？
**我（60 秒口述）**：优势在知识更新、私有数据隔离、引用溯源，生产落地要提前认五个工程代价，核心局限一句是检索质量直接决定回答上限。优势落到四点：像开卷考试、制度改版只更新索引、按 ACL 动态过滤、回答附原文出处。局限我讲全不只说会幻觉：一是检索质量决定上限，表格解析错位或前置条件被切块截断，证据没进候选池，LLM 再强也恢复不了；二是旧版本、相近规则混进上下文误导生成；三是端到端延迟，改写、编码、多路召回、重排、生成每跳累加，高并发要缓存超时降级；四是向量库、全文索引、元数据库一致性难维护，处理不好召回幽灵数据；五是每次查询都拼片段当输入 Token 加索引运维开销。Demo 跑通只是接了向量库，真正耗时的是解析质量、混合召回调优、增量一致性和固定评测集回归。
**追问 1**：你刚提「幽灵数据」，生产上真遇到过吗、怎么修的？
**答**：遇过，典型是文档删了或降权后还能被召回。根因往往不在向量库，是删除没在向量库、元数据库、全文索引三端一致，或权限变更后旧 `acl` 没更新；我用「软删除 + 延迟物理删除 + 删除审计日志」，以元数据库作 source of truth 配 `index_status` 和 reconciliation 扫描差异，敏感文档还要清 rerank 缓存和 LLM 上下文缓存。
**追问 2**：如果 QPS 翻十倍，这五个代价里哪个先爆？
**答**：先爆的是延迟和 Token 成本，不是检索质量。改写、编码、多路召回、重排、生成每跳都吃资源，我会先上热点查询缓存、设超时和降级（重排或改写失败就回退纯向量召回），把 `recall_top_k`/`rerank_top_n` 按 SLO 收紧；容量上再评估 HNSW 内存和是否拆专业向量库，而不是先动模型。

### J4-11 什么场景适合用 RAG？什么场景不适合？
**面试官**：什么场景适合用 RAG？什么场景不适合？
**我（60 秒口述）**：答案依赖外部资料、资料长或更新频繁、要按权限隔离并附原文引用的适合；只定位原始文件、需要通读单篇全文、或答案不依赖外部知识的，不必上 RAG。适合的方向我数五类：客服售后、研发运维助手、医疗临床辅助、法律合规检索、企业内部知识助手。不适合的依据有两组：一是很多日常需求只想拿到文档本身，下载制度原文、核对接口、找合同模板，关键词返回列表链路更短、成本更低、结果可控，选搜索还是 RAG 就看用户要找原始材料还是综合多份材料得结论；二是单篇少文档要通读全文时，长上下文比切块检索更保全局脉络。易错点是别把不适合 RAG 说成不适合检索，多数场景是该用搜索或长上下文，不是不用检索。
**追问 1**：有个客户想做「合同模板查找」，你怎么判断该给他搜索还是 RAG？
**答**：先问用户目标，找模板、编号、标题、关键词这类精确查找走 ES/BM25 加权限过滤就够。我拿一批真实问题跑两种链路，比「能否定位到原文」和单次成本；如果需求其实是「对比这三类合同的责任条款差异」，才升级到混合检索加重排加引用溯源。7 维度对照表里「用户目标」那一行就是判断依据，别为了用 RAG 而用。
**追问 2**：场景里有大量跨文档但关系简单的问题，你会不会为了省事直接上 GraphRAG？
**答**：不会，先确认相关文本有没有进候选集。GraphRAG 的适用判断是「候选文本已齐全但系统无法按业务关系连起来」才验证；若只是没召回，先查解析、切分、BM25 和重排。跨文档不等于关系推理，简单问题用向量加混合检索加 rerank 往往更划算，图结构只会把权限过滤和评测复杂度抬上去。

### J4-12 什么是 Embedding？为什么需要把文本转成向量？
**面试官**：什么是 Embedding？为什么需要把文本转成向量？
**我（60 秒口述）**：Embedding 是把一段文本交给模型压成固定维度的稠密向量，相当于给文本一组语义坐标，语义越近向量距离通常越近，让检索跳过字面差异做语义匹配。为什么要转，因为向量库并不理解文本，它存和算的就是这些向量：离线是文档 Chunk 经 Embedding 写库，在线是 Query 用同一个模型编码后找最相似 Top-K。对照着看更清楚，BM25 靠词频字面匹配，退货和退款流程容易失效；向量语义搜索能处理同义词和隐含意图，但依赖 Embedding 质量。落地我有两句判断：文档切分策略和 Embedding 模型共同决定语义召回的理论上限，向量库只是把这个上限在可接受延迟内兑现；查询必须用与索引相同的模型，再叠元数据过滤、混合检索、权限与多租户隔离，才叫生产级。
**追问 1**：你说向量库不理解文本，那「语义」到底是谁给的？
**答**：是 Embedding 模型给的，向量库只负责算距离。它存的是 768 到 3072 维的浮点数组，检索时按余弦或内积找 Top-K；所以换模型等于换坐标系，同一句话用 `text-embedding-3-small` 和 `all-MiniLM-L6-v2` 编出来没有可比性。证据是暴力搜索 100 万条 1024 维向量约 1,000,000×1,024 次乘法、延迟易到秒级，ANN 才把它压到几十毫秒。
**追问 2**：多租户场景，Embedding 和向量库这层要额外做什么？
**答**：把 `tenant_id` 和 `acl` 当一等公民写进元数据，并在召回前参与查询。我不会等 Top-K 返回再筛，因为 10 条里 8 条无权、过滤后剩 2 条会被误读成「只找到两条相关」；能由 Metadata 表达的范围先收紧再算相似度。向量维度选 1536 还是 3072 也直接影响内存和索引构建时间，得跟容量一起算。

### J4-13 RAG 场景为什么需要向量数据库？
**面试官**：RAG 场景为什么需要向量数据库？
**我（60 秒口述）**：真正要解决的不是能不能存 Embedding，而是能不能在大规模高维向量里低延迟找出最相关的 Top-K。普通关系库也能存向量、用函数算相似度，但没有专门向量索引通常只能全表扫描 O(n)，Chunk 到几十万上百万就撑不住生产延迟；ANN 靠图导航、空间划分、量化把距离计算次数降下来。而且向量语义检索只是 RAG 召回方式之一，BM25、SQL、图查询都能当通道。落地我盯三类能力：高维 ANN 检索，百万级从秒级暴力扫描压到几十毫秒但必须拿业务数据、Top-K、过滤条件、并发和召回目标实测；大规模承载，持久化、增量更新、分片；以及元数据过滤、Hybrid Search、动态更新、权限与多租户隔离。边界是高频更新删除会让索引膨胀、tombstone 累积、召回和延迟波动，得配 VACUUM、REINDEX、执行计划和评测集持续看。
**追问 1**：你凭什么说需要向量库，而不是给 PG 加个 SQL 函数算相似度？
**答**：拿规模、QPS 和延迟目标实测，而不是看能不能算。PG + pgvector 在项目初期、强一致、中小型规模其实够用，HNSW 能满足当前业务就不该引入新组件；我用 `EXPLAIN ANALYZE` 确认命中 Index Scan，再比召回率和 P95。只有规模、QPS、多租户隔离或专用索引超出单机实测能力，才评估 Milvus/Qdrant/Weaviate。
**追问 2**：从 100 万涨到 1 亿，向量库这层最先撑不住的是什么？
**答**：HNSW 的内存和构建成本，因为它除原始向量还要存大量节点连接关系。我先按「向量数×维度×每维字节 + 图连接开销」估容量，内存见顶就换 IVFFLAT 或 IVF-PQ/IVF_RABITQ 量化压缩，再考虑分布式分片和独立向量集群；每步都用同一评测集验召回率、延迟和成本，别忘了多一套系统就多一套运维、监控和备份。

### J4-14 ANN 算法为什么可以接受不是 100% 精确的结果？
**面试官**：ANN 算法为什么可以接受不是 100% 精确的结果？
**我（60 秒口述）**：ANN 接受不保证 100% 找到绝对最近邻、以很高概率找到足够相似结果这个工程取舍，用一点召回损失换几个数量级的速度提升。为什么能接受有两层：算法层，精确最近邻 ENN 像 KD-Tree 在低维有优势，维度一高剪枝下降、可能退化接近暴力扫描，所以高维主流是图、量化、哈希三类 ANN，核心是提前把数据组织好、跳过绝大部分不相关向量；业务层更关键，RAG 最终答案受限于正确证据是否进候选池，只要召回率够高，ANN 那点精度损失能靠扩大候选池加 Rerank 补回来，而延迟是硬约束。落地三类对上号：HNSW 图导航、IVF-PQ 聚类加压缩、LSH 落桶。边界是近似不是随便返回，调参要同时记延迟、资源占用和召回率，拿真实业务问题测，不能只看理论复杂度。
**追问 1**：召回损失具体怎么补，补的时候会不会把成本又吃回去？
**答**：靠「扩大粗召回候选池 + Rerank」补，成本可控在重排层。我把 `recall_top_k` 设 30–100 让证据有机会进池，再用 Cross-Encoder 精排选 5–10、压缩后留 3–6 进 Prompt，不把新增候选直接拼上下文；精度损失被筛掉，延迟主要花在可控的重排量上。反例是一味放大 Top-K，噪声和 Token 一起涨。
**追问 2**：有没有哪类查询 ANN 的近似损失特别致命？
**答**：错误码、SKU、版本号、专有名词这类精确匹配，近似容易召回「相似但错误」的实体。这类必须保留 BM25/关键词通道做 Hybrid，用 RRF 按名次融合；我见过「ABX-4421 型号参数」被向量召回成相似型号，靠关键词精确命中才救回来，所以精确词通道不能省。

### J4-15 有哪些向量索引算法？各自优缺点是什么？
**面试官**：有哪些向量索引算法？各自优缺点是什么？
**我（60 秒口述）**：主流是 Flat、HNSW、IVFFLAT、IVF-PQ、IVF_RABITQ 五类，差别都在召回率、延迟、内存、构建成本的取舍位置。逐个说：Flat 遍历全量算距离、100% 准确无损，适合小规模、低 QPS、离线评测和召回基准；HNSW 分层导航小世界图，查询快召回高但吃内存、构建慢，百万级常见、千万级要重点评内存；IVFFLAT 用 K-Means 聚类加倒排桶，内存友好构建快，但要先训练、召回略低、得调 lists 和 probes；IVF-PQ 聚类加乘积量化，支持海量开销低但精度损失最大；IVF_RABITQ 随机旋转后每维压成 1 bit，是 2024 年提出、Milvus 2.6.x 已提供的省内存路线。落地按场景排：基线用 Flat，中大规模高召回低延迟用 HNSW，内存敏感用 IVFFLAT。常踩的坑是把向量数据库和索引算法混成一层，Milvus、pgvector 是库，HNSW、IVFFLAT 是算法。
**追问 1**：你项目里实际用哪个，为什么？
**答**：用 PostgreSQL + pgvector 的 HNSW，理由是「当前规模下检索速度、召回率和工程复杂度比较均衡」。建索引类似 `USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64)`，和结构化业务数据同库、复用事务和 SQL 过滤；我用 `EXPLAIN ANALYZE` 确认命中，再在评测集上比召回率。规模涨到千万、内存见顶才考虑 IVFFLAT 或迁 Milvus。
**追问 2**：同样一百万条向量，为什么有人说 HNSW 够、有人说必须量化？
**答**：因为容量不能只看条数，维度、过滤比例、QPS、Top-K 和硬件不同结果差很多。同样一百万条，1536 维和 768 维、带不带严格 `WHERE` 过滤，内存和延迟完全不是一个量级；HNSW 还要额外存图连接指针。我的判断顺序是先估内存、看执行计划，再决定是加内存、换 IVFFLAT 还是上量化，不按固定倍数拍板。

### J4-16 Flat、HNSW、IVFFLAT、IVF-PQ 分别适合什么场景？
**面试官**：Flat、HNSW、IVFFLAT、IVF-PQ 分别适合什么场景？
**我（60 秒口述）**：四个按精度到速度到内存梯度排：Flat 做基线和小规模，HNSW 做高召回低延迟，IVFFLAT 做内存或构建成本敏感，IVF-PQ 做超大规模内存敏感。机制上，Flat 暴力搜索 100% 准确但 O(n)；HNSW 是分层图，查询从顶层大跨度跳跃、底层精细找，属于 ANN 不保证 100% 召回，层级由 level = floor(-ln(random()) * mL) 这类公式构建；IVFFLAT 把空间聚成桶、先找最近几个桶再桶内暴力；IVF-PQ 在聚类之上做乘积量化极致压缩，支持海量但有精度损失。落地把参数落到 SQL：pgvector 的 HNSW 用 vector_cosine_ops 配 m=16、ef_construction=64，IVFFLAT 用 lists=100。一个易错点必须点破：IVF-PQ 是精度损失最大的那个，别答成召回率最高；选哪个最终看规模、内存预算和能不能接受那点损失。
**追问 1**：IVFFLAT 的 `lists` 和 `probes` 你怎么定，凭感觉调吗？
**答**：不凭感觉，按起步规则加评测集。pgvector 建议数据不超过 100 万行时 `lists` 取 `rows/1000`，超过取 `sqrt(rows)`，`probes` 越大召回越高、查询也越慢；我固定其他变量，在标注问题上扫几组值比召回率和 P95，够用就停。调完还要 `EXPLAIN ANALYZE` 确认索引命中，别把过滤导致的退化误判成参数问题。
**追问 2**：HNSW 上加了严格的 `category='Java'` 过滤，结果只返回 3 条而不是 Top-10，怎么回事？
**答**：近似索引通常先按向量距离找候选再应用过滤，候选里满足条件的本来就少。我会先增大 `ef_search` 或 `LIMIT` 扩候选，或建 `CREATE INDEX ... WHERE category='Java'` 的部分索引；pgvector 0.8.0+ 还能用 iterative index scan，配 `hnsw.max_scan_tuples` 在结果不足时继续扫。预过滤虽直观，但可能让索引失效退化成暴力扫描，得看执行计划再选。

### J4-17 HNSW 和 IVFFLAT 有什么区别？
**面试官**：HNSW 和 IVFFLAT 有什么区别？
**我（60 秒口述）**：一句话，HNSW 靠图的连通性找邻居，IVFFLAT 靠聚类缩小范围；前者查询更快更稳但吃内存，后者内存友好构建快但需调 lists、probes、召回略低。机制上 HNSW 建多层图，查询像走高速，上层大跨度跳、下层局部精找，除原始向量还要存大量节点连接关系，所以内存大构建慢，但召回率通常高且稳定；IVFFLAT 用 K-Means 切桶，查询只探最近几个桶、桶内暴力，结构简单构建快，代价是相同召回目标下性能和稳定性一般不如 HNSW，数据分布明显变化时可能要重训聚类中心。落地怎么选很直接：追求低延迟高召回、内存够优先 HNSW；更看内存和构建速度、愿意调参，考虑 IVFFLAT。还有个前置条件常被漏：IVFFLAT 得先有足够数据再建索引，因为要先聚类。
**追问 1**：你们 HNSW 上线后文档一直在增删改，索引怎么维护？
**答**：高频更新删除会让索引膨胀、tombstone 累积，得定期 `VACUUM`、`REINDEX` 并看执行计划。我会把查询延迟、召回率评测和执行计划一起当健康检查，不指望 `VACUUM` 单独修召回；每次调距离运算符、operator class、过滤条件或索引参数后都 `EXPLAIN ANALYZE` 复核。生产建议固定 pgvector 版本，升级前跑回归评测。
**追问 2**：如果数据分布因为业务改版整个漂移了，两个索引分别会怎样？
**答**：IVFFLAT 更敏感，聚类中心基于旧分布，可能要重新训练；HNSW 的图结构也会老化但通常还能撑。我不会只在原索引上调 `probes`，而是用评测集确认召回是否掉，再决定重训 `lists` 或重建；真到分布大变，走 `index_v2` 重建 + 别名切换 + 保留旧索引回滚，比原地修补稳。

### J4-18 HNSW 的 `ef_search` 参数怎么调？调大和调小分别会怎样？
**面试官**：HNSW 的 `ef_search` 参数怎么调？调大和调小分别会怎样？
**我（60 秒口述）**：ef_search 是查询时的搜索范围、也是最重要的运行时参数：调大召回率上去但延迟和 CPU 一起涨，调小延迟降但漏召回风险上升，正确做法是在评测集上找平衡点、够用就停。先把三个参数分清楚：m 是每个节点最大连接数，建索引时定，越大图越密召回越高但内存和构建时间上去；ef_construction 是构建时搜索范围，越大索引质量越好、构建越慢；ef_search 是会话级运行时参数，建好索引后能单独调、不用重建。落地我用 pgvector 默认 m=16、ef_construction=64、ef_search=40 起步，通过 SET hnsw.ef_search = 100 扫值，配 EXPLAIN ANALYZE 确认命中，再用一批人工标注问题比召回率、延迟和答案质量。边界是它不需要无限调大，达到业务可接受召回就该停，否则只是拿延迟和 CPU 换很小的收益。
**追问 1**：你说够用就停，具体停在哪个值、怎么算「够」？
**答**：以评测集上召回率曲线的拐点为准，兼顾 P95 延迟和 CPU。我会同时记录查询延迟、资源占用和召回率，常见范围 `ef_search` 40–200+，一旦再往上召回只涨一两个点、延迟明显上升就停；用 `EXPLAIN ANALYZE` 确认没有退化成全表扫描，避免把过滤问题误当成 `ef_search` 不够。
**追问 2**：大促 QPS 翻几倍、延迟告警了，你会直接把 `ef_search` 调小吗？
**答**：会，但它是会话级降级手段，不是唯一手段，且要接受召回损失。我优先按 SLO 分层：热点查询走缓存、超时降级回退更保守的召回，`ef_search` 临时调小换延迟；同时盯 Context Recall 有没有掉，别为了压 P95 把正确证据挡在候选池外。长期还是回到容量评估，看是不是该扩内存或换索引类型。

### J4-19 向量数据库和传统数据库最核心的区别是什么？
**面试官**：向量数据库和传统数据库最核心的区别是什么？
**我（60 秒口述）**：核心不是能不能存向量，而是有没有专门 ANN 索引在大规模高维向量上低延迟做 Top-K 相似度检索，以及围绕向量负载的过滤、更新、分片、多租户能力。传统关系库能存向量、能算相似度，但没专门索引通常只能全表扫描 O(n)，撑不住生产延迟；传统库强项本来是事务、JOIN、SQL 过滤、备份恢复，向量库额外给持久化、增量更新、分片、距离度量、混合检索和 ANN 联合查询。落地按四类方案选：PG 加 pgvector 这类扩展适合初期、强一致、复用 SQL；ES、OpenSearch 混合搜索能力强；Milvus、Qdrant 原生专业；Pinecone 云托管上线快。边界是托管不等于不用管，索引参数、召回评测、权限隔离、成本监控还是自己的。顺手答个高频追问：MySQL 8.x 没有官方 VECTOR 类型，9.x 有但偏存储与基础函数，还不是成熟生产级 ANN，已绑 MySQL 就外接向量组件，别硬塞。
**追问 1**：为什么不干脆用 MySQL 加个向量字段，非要引入 PG 或新组件？
**答**：因为 MySQL 那套 `VECTOR` 主要解决「存」，没解决「高效 ANN 检索」，而 RAG 卡的是后者。`VECTOR` 列还不能用作任何键（主键、外键、唯一键、分区键都不行）；PostgreSQL 扩展能力强，pgvector 加全文 `tsvector`/pg_bm25 能一套 PG 承担多种能力，对中小规模更友好。我的判断是「先简化技术栈，等规模、QPS、隔离要求上来再拆专业组件」。
**追问 2**：选云托管向量库，权限和多租户这块有哪些坑？
**答**：最容易漏的是「以为托管方兜底了」：索引参数、召回评测、ACL 隔离、成本监控仍要自己做。我会把 `tenant_id`/`acl` 写进每个 Chunk 的元数据并在召回前参与查询，用同一条 Trace 记过滤条件；成本上盯索引维度和查询量，3072 维比 1536 维内存和账单都高一截，得跟召回收益一起算。

### J4-20 如果向量数据从 100 万增长到 1 亿，架构上需要做什么调整？
**面试官**：如果向量数据从 100 万增长到 1 亿，架构上需要做什么调整？
**我（60 秒口述）**：不是一步换库，而是沿内存评估、索引替换或量化、分布式分片、独立向量集群逐级走，每一步都用业务评测集验召回率、延迟和成本。我先看规模信号：HNSW 百万级常见、千万级要重点评内存，亿级且 QPS 延迟苛刻时原生向量库通常比 pgvector 更合适。落地先按向量数乘维度加图连接开销估容量，但同样一百万条在维度、过滤比例、QPS、Top-K 不同时结果差很大，不能只看条数；内存见顶先换 IVFFLAT 或 IVF-PQ 量化压缩，需要分布式扩展和多租户隔离再评估 Milvus、Qdrant。设计上补权限前置过滤、按 doc_id 加 version_id 去重、别名灰度切换和回滚。代价很实在：多一套系统就多一套运维、监控、备份成本。
**追问 1**：从 pgvector 迁到 Milvus，除了性能，团队实际多背了什么？
**答**：多一套系统的运维、监控、备份、一致性补偿和学习成本，还有三端同步的复杂度。PG 的好处是向量和业务数据同库、天然事务一致；拆出去后向量库、元数据库、全文索引不在同一事务域，一次写三端容易部分成功，得以元数据库作 source of truth 配 `index_status` 和 reconciliation。所以我的原则是「先简化技术栈，等规模真上来再拆」。
**追问 2**：亿级下带严格 `tenant_id` 过滤，ANN 会不会反而退化？
**答**：会，pgvector 近似索引常先 ANN 找候选再过滤，过滤很严时候选不足、结果少于 Top-K，甚至退化成更慢的扫描。缓解手段是增大候选集、部分索引 `WHERE tenant_id=...`，或 pgvector 0.8.0+ 的 iterative index scan 配 `hnsw.max_scan_tuples` 继续扫；亿级我更倾向按租户或业务域做分区与路由，把过滤变成分区裁剪，而不是让全局 ANN 硬扛。

### J4-21 为什么选择 PostgreSQL + pgvector？什么时候应该换专业向量数据库？
**面试官**：为什么选择 PostgreSQL + pgvector？什么时候应该换专业向量数据库？
**我（60 秒口述）**：PG 加 pgvector 的价值就四个理由：架构简单、性能够用、事务一致性好、SQL 查询方便；当规模、QPS、延迟、多租户隔离或专用索引能力超出单机实测能力时，才换专业向量库。拿实际项目说，既要存简历、面试记录这类结构化数据，也要存文档 Embedding，一组 PG 全扛最省事：不引入额外组件、HNSW 的速度和召回满足当前业务、向量与业务数据同库天然支持 ACID、JOIN、备份恢复、能直接 WHERE 过滤。但 SQL 方便有个前提，过滤条件可能影响索引命中，必须 EXPLAIN ANALYZE 检查，查询运算符还要和建索引时的 vector_cosine_ops 严格一致，否则退化全表扫描。什么时候换我说得很明确：需要分布式扩展、独立资源隔离、多租户，或向量到亿级、QPS 和延迟很苛刻时评估 Milvus、Qdrant。边界是别把换专业库当万能解，代价是多一套运维、监控、备份、学习成本。
**追问 1**：你说「实测能力」，具体怎么判断 pgvector 已经到头了？
**答**：看 P95 延迟、召回率、内存水位和执行计划，而不是拍脑袋。我用 `EXPLAIN ANALYZE` 确认是否 Index Scan，跑固定评测集比 Context Recall 和延迟；当 HNSW 内存成瓶颈、严格过滤频繁退化、或写入吞吐撑不住，就是拆专业库的信号。SQL 里 `1 - (embedding <=> $1)` 算余弦相似度、`<=>` 距离 0 完全相同 2 完全相反、按距离升序取 LIMIT 5，这些都得和 operator class 对上。
**追问 2**：如果换库的同时还要升级 Embedding 模型，怎么排期不出事？
**答**：两件事分开做，且都用别名和版本快照兜底。模型升级必须重建索引，我先在新库用新模型建 `index_v2`、新旧并行对比召回率和回答质量，确认稳定再用别名切流量、保留旧索引约 7 天回滚；库迁移单独走双写加 reconciliation 对账。一次只替换一个变量，差异才能归因，回滚时记得把模型和索引一起切回旧版本。

### J4-22 RAG 文档处理管线通常包含哪些步骤？
**面试官**：RAG 文档处理管线通常包含哪些步骤？
**我（60 秒口述）**：文档从上传到进向量库至少过六到七个环节：文件上传、格式校验、Layout 解析、清洗去噪、Chunking、Metadata 补全、入库，而且质量校验必须前置到解析和切分阶段分层抽样，不能留到入库之后。为什么强调前置，因为 Embedding 模型和向量库只能处理输入给它们的文本——多栏 PDF 阅读顺序错乱、表格列关系丢失、OCR 错字一旦进索引，检索阶段没法从向量里还原，上传前半段直接决定后半段效果上限。落地把每环问题对上号：格式校验防 MIME 不符选错解析器、Layout 防页眉页脚、清洗去乱码和重复空行、Chunking 防语义截断、Metadata 没存来源页码版本权限就没法过滤和引用、入库防维度不一致和 Token 超限。边界一句：别只答解析、切分、向量化三步，格式校验、Metadata、三道校验关卡和异常降级队列才是生产级和 Demo 的分水岭。
**追问 1**：你说校验要前置，三道关卡具体卡在哪、失败怎么降级？
**答**：上传阶段卡文件（基于魔数 Magic Bytes 的真实 MIME、大小、加密），解析结果卡字符数为空或异常偏短、乱码比例，切分质量卡块数量、最小/最大长度和长度标准差。降级有明确路径：空文件或格式伪造直接拒绝入库记审计日志、纯扫描件 PDF 路由到 OCR 加版面分析、复杂解析器失败切备用解析器再转人工复核；参数上乱码率 > 0.05、有效内容 < 50、`minChunkSize < 20` 都会告警或报错。
**追问 2**：一份 100 页合同有 10 页表格解析失败，能不能先上 90 页？
**答**：合同法规这类要求证据完整的，必须阻断上线并通知人工，不能标「完整入库」。允许部分入库的普通参考资料也得在元数据里记缺失页码，防止系统对缺失范围给出确定性回答；我会把该文档状态标「部分可用」、记录缺页页码，权限上再确认这些页对应的 `acl` 没漏配，避免越权或答非所问。

### J4-23 文档解析、清洗、结构化分别解决什么问题？
**面试官**：文档解析、清洗、结构化分别解决什么问题？
**我（60 秒口述）**：解析解决把不同格式还原成可读文本并保住版面或语法结构，清洗解决去噪防止 Embedding 失真，结构化解决保住标题层级、表格行列、字段关联这些证据边界，三者不能全丢给同一个纯文本提取器。机制上各有坑：PDF 本质是版面绘制指令，文本顺序未必等于阅读顺序，双栏论文用基础 PyPDF 按流提取会把左右栏上半句拼一行；Word 靠 Heading 样式组织，但业务文档常拿加粗放大当标题，得用 heading_stack 栈维护 section_path；Excel 拆成纯文本就断了字段和数值对应；扫描件靠 OCR，受分辨率、印章遮挡、倾斜影响。落地按格式选工具：多栏或复杂表格上 Docling、LlamaParse 这类版面感知解析器，扫描件先纠偏再上 OCR 加业务规则校验，Excel 大表走 Text2SQL。边界是格式校验要基于文件魔数验真实 MIME，防止 exe 改名成 pdf。
**追问 1**：OCR 具体会错成什么样，对检索的影响能举个例子吗？
**答**：最典型是字符混淆，数字 `0` 和字母 `O`、数字 `1` 和字母 `l`，直接让产品型号、合同编号检索失效。还有表格框线断裂导致跨列串行、双栏或批注和正文混排导致段落错乱；我会对型号、身份证号、金额用正则或「分项之和等于合计」这类业务规则校验，失败页面告警转人工。像 `0Auth2` 被识别成 `OAuth2` 这种，字面匹配和向量都会跑偏。
**追问 2**：版面感知解析器比 PyPDF 贵不少，怎么判断值不值？
**答**：先用失败样本和评测集算收益，别全量上。我从高价值文档和高频 Badcase 入手，比如财报合并单元格、跨页表格解析出列数不一或数值校验不平的页面打标人工复核；在同一批覆盖表格、跨段条件、专有名词的问题上比 Context Recall 和答案准确率，确认解析收益盖得住新增处理成本和等待时间，再逐步扩大，不把全量文件直接交给视觉模型。

### J4-24 Chunk 切分为什么不能只按固定长度切？
**面试官**：Chunk 切分为什么不能只按固定长度切？
**我（60 秒口述）**：固定长度不感知段落、表格和代码块边界，会把条件与结论、表头与数值、列表项与前置说明硬切开，导致无论召回哪块都缺上下文。举个原文例子，售后政策「除以下情况外均可七天无理由退货：（一）定制商品……」若列表刚好跨在切分边界，前块只剩均可退货、后块只剩例外项，模型很容易漏掉限制条件。这叫语义丢失：前置条件、指代对象或结构关系被削弱，单看 Chunk 还原不了原意，典型是条件与结论分离、指代丢失、表格行列破坏、专有名词断词。但我也不把固定长度一棍子打死，它实现简单耗时极低，短文档和单条 FAQ 可以当评测基线。改进按成本从低到高排：章节路径回填、摘要与假设问题多检索入口、Contextual Chunking、Late Chunking。边界是语义切分离线要对大量句子算 Embedding、成本明显高，还得配最小最大块长。
**追问 1**：换切分策略后，你怎么证明不是「换了一种错法」？
**答**：用固定评测集回放，比 Context Recall 和最终答案准确率。我拿通用基线「512 Token 块长、50–100 Token 重叠」和递归字符切分 `["\n\n","\n","。"," ",""]` 当对照，在同一批覆盖表格、跨段条件、专有名词的问题上跑；每次只改 `chunk_size`/`chunk_overlap` 一个变量，看分块后长度均值、P95 和过小块占比，收益能复现才算数。
**追问 2**：代码知识库也这么切吗？
**答**：不按 Token，按语法边界。我用 `RecursiveCharacterTextSplitter.from_language(Language.PYTHON, ...)` 或 Tree-sitter 沿 `class`、`def`、注释块切，保住调用语义；否则把参数和返回条件拆开，召回就废了。Contextual Chunking 虽有效但要额外 LLM Token，我先只在高频失败的高价值文档上试，并用 Prompt Caching 压成本。

### J4-25 Chunk 大小、Overlap、语义边界应该怎么取舍？
**面试官**：Chunk 大小、Overlap、语义边界应该怎么取舍？
**我（60 秒口述）**：没有万能值，三者要按文档类型和查询类型分别建索引，在同一批问题上比 Context Recall、Context Precision、答案正确率和平均上下文 Token 之后再定；Overlap 只缓解边界截断，替代不了语义完整。机制上有个关键结论：事实型查询偏好 256 到 512 Token 的细粒度块，跨段落分析型更适合 1024+ Token 或页面级切分，这引出 Parent-Child——用 200 到 400 Token 子块建索引提匹配精度，命中后按 parent_id 拉 1000 到 1500 Token 父块送进 LLM，代价是多维护 DocStore 和一次回查。落地按文档给起步范围：FAQ、接口说明 200 到 500 Token，技术文档 400 到 800，法规合同优先按条款切，代码按类、函数切。有个数据我记着但不迷信：NVIDIA 基准里页面级平均准确率 0.648，可 FinanceBench 上 1024-Token 的 0.579 反而略高于页面级 0.566，说明页面级并非通吃。边界是重叠过大让索引膨胀、Top-K 一堆重复文本。
**追问 1**：512、800、1000 Token 你到底怎么选，不会凭经验吧？
**答**：这些只是第一轮实验索引的候选值，不是结论。我给每组建独立索引，在同一评估集上比 Context Recall、Context Precision、答案正确率和平均上下文 Token，再保留一组；还要检查分块后长度均值、P95 和过小块占比。语义切分只对主题混杂、偏概念查询、更新不频繁的语料划算，接口文档已有 OpenAPI path、参数表时按结构切更稳。
**追问 2**：业务要从中文技术文档扩到法规合同，切分策略要跟着怎么变？
**答**：从「按 Token」切到「按条款结构」切，且历史数据要一起迁。法规合同优先按编、章、节、条、款切并回填层级路径，保住条款完整性；这属于 Chunk 策略变更，会影响全部历史文档的 `chunk_id`、向量和全文索引条目，不能只对新文档生效，得双索引灰度加别名切换加回滚，评测标注也要改用稳定事实 ID 而不是旧 Chunk ID。

### J4-26 表格、代码块、图片、多模态内容进入 RAG 前怎么处理？
**面试官**：表格、代码块、图片、多模态内容进入 RAG 前怎么处理？
**我（60 秒口述）**：核心设计是检索表示与生成素材分离：向量和全文索引存易匹配的文本块、表格说明、图片描述，DocStore 存未压缩的完整表格、父段落和高清原图，命中后按 doc_id 回查再组装给生成模型。因为解析时丢掉非文本元素，涉及图表的提问就因缺证据答错。图片分三条路：多模态 Embedding 加原图回传给 MLLM，但通用 CLIP 对密集中文小字区分度有限；MLLM 生成图像详述走文本检索；把这套工程化就是 Multi-Vector Retriever。表格用 Docling 还原成 Markdown 或 HTML，大表按行拆时每块顶部必须重复完整表头，纯数字财务表再生成含时间范围、统计维度的语义摘要。图表要把图题、坐标轴、图例、单位和正文引用段一起传给 MLLM，避免把百万元误读成元。边界是先过滤装饰图标，别把全量文件交给视觉模型。
**追问 1**：上多模态这条路，成本和链路复杂度会增加多少，你怎么控？
**答**：主要多两块：离线 MLLM 生成描述或摘要的 Token 和等待时间，以及 DocStore、对象存储、多套索引的运维。我不全量处理，先按尺寸阈值、纵横比、跨页重复频率滤掉无信息量图片，只在高价值文档和失败样本上试；生产把示例里的 `InMemoryByteStore` 换成 S3 + Redis/PostgreSQL，`id_key="doc_id"` 回查原图，观察解析收益是否盖得住新增成本。
**追问 2**：一张架构图里都是中文小字和密集连线，CLIP 召回总是不准，怎么办？
**答**：通用 CLIP 对这类图本来就不擅长，别硬调。我改用 MLLM 结合图片上下文标题和正文引用段生成详细文字描述（图中文字、节点流向、核心结论）走文本检索，或 ColPali 直接对页面图像生成多向量表示；关键是把「谁依赖谁」写成文本证据，命中后回传高清原图给多模态 LLM 复核，而不是只靠图文向量相似度。

### J4-27 文档处理阶段如何保留标题层级、页码、来源和权限元数据？
**面试官**：文档处理阶段如何保留标题层级、页码、来源和权限元数据？
**我（60 秒口述）**：解析阶段用栈维护 section_path，切分时把标题层级前缀回填到每个 Chunk 并同步写进 Metadata，每个 Chunk 至少绑定来源文档 ID、版本号、页码、章节路径和权限 ACL，这样既支持前置过滤也能答案溯源。为什么 Metadata 关键，因为它既决定哪些 Chunk 能进候选池，也让结果能回到原文、页码和对应版本；我要求至少存 source_id、section_path、page、created_at、tenant_id、acl，更新链路里还带 content_hash、version_id、chunk_strategy、embedding_model_version、is_deleted。落地最要紧一条：权限过滤要在召回前参与查询。我见过向量库先返回 Top-10、其中 8 条无权，过滤后剩 2 条被误当成只找到两条相关；能由 Metadata 表达的范围先收紧再算相似度。Word 解析用 heading_stack 防父标题被子标题覆盖。边界是别只在答案里附链接而 Chunk 不带 page、section_path、acl，那就没法过滤、没法引用、还容易越权；权限变更要触发重索引。
**追问 1**：标题层级回填具体怎么落地，几乎不花钱吗？
**答**：几乎不增算力，就是把文档标题和各级父标题拼到 Chunk 开头，例如 `[订单系统 > 退款规范 > 特殊商品] 正文...`，并同步写进 `section_path` 字段。它能有效消除「过去三年中该比例持续下降」这类指代不明；对比 Contextual Chunking 要额外调小模型生成 50–100 Token 背景，章节路径回填是性价比最高的一步。
**追问 2**：某文档从全员可见改成仅高管可见，元数据这层要动什么？
**答**：必须触发重新索引或至少原子更新 `acl` 字段，否则旧 `acl` 会让普通员工继续召回，形成「幽灵数据」。若向量库支持原子更新元数据，可只改 `acl` 不重建向量；否则按 `doc_id` 重刷该文档全部 Chunk 的权限字段。二次校验要发生在组装模型上下文之前，返回引用前再核一次作防御性检查，并记审计日志。

### J4-28 Chunk 质量差会带来哪些召回和生成问题？
**面试官**：Chunk 质量差会带来哪些召回和生成问题？
**我（60 秒口述）**：Chunk 质量差会同时毁掉召回和生成，而且下游 Rerank、换 Embedding 都补不回候选池里根本不存在的证据。我分两头看：召回侧是漏召回和召回噪声，生成侧是答案残缺和张冠李戴。机制很直白——块太大，一个相关句子把整段无关说明带进上下文、拉低 Context Precision；块太小，只留结论、丢掉前置条件和例外；边界被切断更麻烦，条件与结论分离、指代丢失、表格行列破坏、专有名词断词。原文有句我特别认同：条件被切进相邻块后，即使后面用重排，也只能在不完整的候选里做选择。落地靠分层校验兜底：上传验格式和真实 MIME，解析验字符数和乱码率，切分验块数量、长度标准差、极小碎片块和超长块。边界是生产文档质量参差，必须给失败文档明确降级路径，且每次调整后在固定问题集上回归。
**追问 1**：有没有那种「看着入库成功了、其实已经坏掉」的典型 Case？
**答**：有，50 页扫描版 PDF 用纯文本解析器只抽出几十个空白字符，链路却标了「入库成功」。所以我要求解析结果校验统计乱码字符和不可见控制字符比例，异常偏短就自动路由到 OCR 加版面分析；还有「100 页文档 10 页表格解析失败」，绝不能把剩下 90 页标成「完整入库」，合同法规类要阻断上线。
**追问 2**：修复 Chunk 之后，怎么确认不是把别的问题改坏了？
**答**：靠固定评测集回归，一次只改一个变量。我把这批失败样本纳入 50–100 条评估集，记录五项检查结果（证据是否被召回、排名、进上下文的内容、回答是否受约束、改动能否复现），修复后在同一批问题上比 Context Recall、Context Precision、Faithfulness 和答案准确率，顺带看延迟和成本，确认没有引入新回归再灰度。

### J4-29 如何从零搭建一套企业级文档处理管线？
**面试官**：如何从零搭建一套企业级文档处理管线？
**我（60 秒口述）**：按格式复杂度分三阶段推进，不要一上来就在所有文件上叠高成本视觉模型；先打通基线评测，再治理复杂版面，最后按坏例引入父子分块和多模态。阶段一做结构化纯文本基线：打通 Markdown、HTML、规范 Word 解析，实现基于标题层级的递归切分，把 doc_id、section_path、更新时间、权限 ACL 写进 Metadata，跑通基础评测集；阶段二治理复杂版面 PDF 和表格，接 Docling、LlamaParse 与 OCR，补齐三道质量校验和异常降级队列；阶段三当坏例分析发现细粒度召回和长上下文完整性冲突时，才引 Parent-Child，业务强依赖架构图、财报图表时再接 MLLM 描述和 Multi-Vector。落地把六环节、三校验、降级队列串起来，并做版本化 8 项记录，设计上权限过滤前置、按 doc_id 加 content_hash 去重、更新走别名灰度和回滚。边界是从零最忌两件事：一上来全量上 MLLM 导致成本失控，以及漏掉固定评测集回归这一收尾。
**追问 1**：评估回放具体怎么建，第一版要多少题？
**答**：先整理 50–100 条能逐条检查的高价值问题，覆盖高频、失败、精确匹配、权限与拒答场景。每条带 `question`、`golden_answer`、`golden_context`、`metadata_filter`、`answer_type`，分开保管开发集和终评集（holdout），同题改写放同一侧防泄漏，还要留同领域干扰文档；有基线后依次比固定长度、结构化、Parent-Child、语义 Chunk，每次只改少量变量并在灰度流量里继续观察离线收益。
**追问 2**：管线要上线，你会列哪几条硬性检查项？
**答**：四条：索引和查询用同一套 Embedding 模型及版本、所有候选进模型上下文前完成鉴权、文档更新通过活动版本或别名原子切换、`doc_id`/`content_hash`/`version_id`/索引状态和审计日志贯穿链路。灰度先按 10% 文档或 5% 用户小流量，盯 `retrieval_hit_rate@10`、延迟、引用准确性和负反馈率，任一告警就暂停；回滚靠别名指回旧索引，权限泄露则先立刻阻断入口再修索引。

### J4-30 RAG 召回率低应该怎么排查？
**面试官**：RAG 召回率低应该怎么排查？
**我（60 秒口述）**：先分清正确证据是否进候选池，召回率低属于粗召回阶段故障，要沿文档、索引、召回侧逐段查，这时候调 Rerank 没有意义。我按召回、排序、上下文、生成四层定位，本层只管第一层：粗召回 Top-50 没出现正确证据时，检查六项——文档是否真入库、解析是否正确、Chunk 是否切断关键事实、Metadata 过滤是否过严、Query 是否需要改写分解或 HyDE、是否需要 BM25 或 Hybrid。第一步先把失败样本分类，看 20 到 50 条，分成没召回、召回但靠后、进上下文没用上、理解错、引用错、该拒答没拒答、权限时间版本过滤错七类，避免同时改 Prompt、模型和检索参数。落地优化闭环是线上问题到离线评估到定位瓶颈到策略调整到灰度发布再回到失败样本，每个样本留好五项检查记录。边界一句：别一上来换 Embedding 或盲目扩大 Top-K，先做数据治理再谈检索优化。
**追问 1**：为什么召回低的时候调 Rerank 没用？
**答**：因为 Rerank 只改变已有候选的顺序，不会把候选池里不存在的文档变出来。原文讲得很直白：候选池没有答案，重排只能改变错误结果的顺序；正确做法是回到粗召回侧查解析、Chunk、Metadata 和查询。我会先用 Context Recall 确认「正确证据是否进 Top-50」，没进就绝不浪费时间换重排模型。
**追问 2**：排查一圈发现文档确实入库了，但就是召不到，还有哪些隐蔽原因？
**答**：查「幽灵数据」和索引侧配置。活动版本可能指向旧版、`is_deleted` 被误标；距离运算符和索引 operator class 不一致会退化成全表扫描，`EXPLAIN ANALYZE` 能看出来；`ef_search`/`probes` 过小、重建后 Embedding 模型不一致也会让召回腰斩。我会把该样本纳入评估集，修复后回放确认「正确证据进入粗召回 Top-50」。

### J4-31 Chunk 策略、Metadata、Hybrid Search、Query Rewrite、Rerank 分别解决什么问题？
**面试官**：Chunk 策略、Metadata、Hybrid Search、Query Rewrite、Rerank 分别解决什么问题？
**我（60 秒口述）**：五者处理的故障位置不同，不能用同一个手段解决所有失败样本，我的记法是：Chunk 管证据边界、Metadata 管候选范围与溯源、Hybrid 管精确词与语义互补、Query Rewrite 管问题可检索化、Rerank 管相关到可回答的排序。逐个说：Chunk 决定召回单位能带走多少条件和结论，边界被切断后重排也只能在残缺候选里选，折中是 Parent-Child 或给块加摘要、可能回答的问题这些语义入口；Metadata 决定哪些 Chunk 能进候选池、让结果回到页码和版本，权限要在召回前参与；Hybrid 让向量按语义、BM25 按词项并行召回后 RRF 融合再 Rerank；Query Rewrite 把钱能退吗补成可检索表达且不能替用户改含义，原始 Query 要一起召回；Rerank 用 Cross-Encoder 判断是否真含回答所需的条件和结论。边界是别把正确文档排在 TopK 之外一律归成召回问题，那可能是排序问题。
**追问 1**：五个手段预算有限，你先上哪个？
**答**：先做数据治理和 Metadata，再上 Hybrid 和 Rerank，Query Rewrite 视 Badcase 补。因为解析和 Chunk 决定上限、权限过滤是合规硬要求，Hybrid 对错误码、SKU、版本号这类精确查询是刚需；Rerank 解决「语义相近但不含答案」最立竿见影。我会用失败样本七分类决定优先级，每次只改一处、在固定集上比 Context Recall 和 MRR，别五个一起上。
**追问 2**：用户问「查 2025 年 Java 相关政策」，五个手段里谁负责年份和类别？
**答**：是 Self-Query 从问题里抽结构化过滤条件，落到 Metadata 前置过滤，不是 Query Rewrite。Query Rewrite 产出检索文本，Self-Query 产出 `year=2025, category=Java` 这类条件并和 Metadata 联动；我会把这类条件在召回前收紧，避免向量把 2023 年或别的语言政策排前面。若同时有口语化表述，再叠一层规范化改写。

### J4-32 Hybrid Search 是什么？BM25 和向量检索怎么融合？
**面试官**：Hybrid Search 是什么？BM25 和向量检索怎么融合？
**我（60 秒口述）**：Hybrid Search 就是向量语义召回加 BM25 关键词召回并行，用 RRF 倒数排名融合或归一化加权合并名次、去重后再交给 Rerank；RRF 只依据候选名次融合，不必把 BM25 分数和余弦分数换算到同一尺度。为什么要两路，因为覆盖互补：向量处理同义改写和隐含意图，如何取消订阅能匹配到关闭自动续费；BM25 处理错误码、型号、版本号这类精确命中，向量反而容易召回相似型号。落地链路是 Query 到两路召回、RRF 融合、去重合并、Rerank、Top-N，Azure AI Search、Weaviate 都把 Hybrid 加 RRF 当常见方案。有个易错点一定点破：别因为文档高度结构化、查询几乎不含关键词就一律不用，错误码、SKU、专有名词占比高的查询必须保留关键词通道。边界是为什么不直接把两个分数加权——两者分布和尺度不同，直接加权要归一化且对参数敏感，RRF 只看名次更稳，常见形式 k 约 60。
**追问 1**：上了 Hybrid 之后，怎么确认它真比纯向量好、不是噪声变多？
**答**：在固定评测集上按查询类型分组看，别只看总体。我重点看精确匹配类（错误码、SKU、版本号）的 Recall@K 和 MRR 是否提升，同时盯 Context Precision 有没有被关键词通道的噪声拉低；用五类查询表逐类对比，确认语义类和精确类都不回退，再调 RRF 权重和 `recall_top_k`。
**追问 2**：两路召回都放大候选，延迟和重排成本会不会失控？
**答**：会，所以扩的是融合前的候选、不是直接拼进上下文。我把粗召回控制在 30–100，经 Rerank 选 5–10、压缩后留 3–6 进 Prompt；融合只多一次倒排检索和 RRF 计算，成本远小于 LLM 生成。真到高并发，热点查询缓存和超时降级（回退单路）比继续放大候选更有效。

### J4-33 Query Rewrite、HyDE、Self-Query 分别适合什么场景？
**面试官**：Query Rewrite、HyDE、Self-Query 分别适合什么场景？
**我（60 秒口述）**：三者补的是不同的查不准：Query Rewrite 补口语化、缩写、上下文缺失、多子问题、太细缺背景，HyDE 补查询太短且与文档形态差异大，Self-Query 补问题里内嵌的过滤条件。展开说，Rewrite 有规范化改写、Multi-Query、Query Decomposition、Step-back 这些策略；HyDE 是先让模型生成一段假设答案，再用假设答案的向量去检索真实文档；Self-Query 从查 2025 年 Java 相关政策里抽出年份和类别，产出结构化过滤条件和 Metadata 联动。落地我守一条铁律：无论用不用组件，原始 Query 都要和改写结果一起参与召回并融合，因为改写模型可能把退款错理解成取消订阅，原始入口能保住正确召回。边界是 HyDE 别当成先答再检索的幻觉放大器不加约束，改写也不能替用户改变问题含义；对比表里也点明 HyDE 和 Query Rewriting 解决的是 query 与 doc 表述差异，并没解决多跳推理。
**追问 1**：上了 Query Rewrite，怎么防它把问题改偏？
**答**：保留原始 Query 通道，并在评测集上盯 Answer Relevancy 和 Context Recall。我会把改写前后的问题和命中证据记进 Trace，抽样人工看改写是否改变含义；反例就是「退款」被理解成「取消订阅」，若没有原始 Query 并行召回，正确文档直接消失。Multi-Query 还要去重，避免多个改写把同一批噪声反复送进候选池。
**追问 2**：「查 2025 年 Java 相关政策」里，年份和类别应该交给 Rewrite 还是 Self-Query？
**答**：交给 Self-Query 抽成结构化过滤条件，在召回前参与 Metadata 过滤，而不是拼进检索文本。因为「2025」「Java」是精确约束，写成文本靠语义匹配容易被相近年份或别的语言政策挤掉；我会用 `year=2025, category=Java` 先收紧 `tenant_id`、版本、更新时间范围，再算相似度。这也对应 Query Rewrite 产出文本、Self-Query 产出条件的边界。

### J4-34 Rerank 解决什么问题？为什么不能只依赖向量相似度排序？
**面试官**：Rerank 解决什么问题？为什么不能只依赖向量相似度排序？
**我（60 秒口述）**：向量分数衡量的是表达是否接近，Rerank 分数应该服务于这段内容能否回答当前问题；双塔向量相似度会把语义相近但不含答案的片段排在前面，所以不能只靠它。机制上，双塔分别编码 Query 和文档算距离，适合从海量里快速取候选；Cross-Encoder 把 Query 和候选一起编码，成本更高但能判断候选是否真含回答所需的条件和结论。原文那个例子我一直记着：问线程池为什么会触发拒绝策略，向量可能召回核心参数、拒绝策略枚举、触发条件、示例代码，前两条语义接近但第三条才是答案核心，Rerank 就是把第三条顶上来。落地放在五步链路里：Metadata 预过滤、Hybrid 粗召回 30 到 100、去重合并、Rerank 选 5 到 10、压缩后写 Prompt。边界最关键一句：Rerank 不会补回候选池里不存在的文档，先查 Context Recall，粗召回没有正确片段就回到解析、Chunk 和查询侧，别继续换重排模型。
**追问 1**：正确证据在 Top-50 却没进上下文，你怎么查？
**答**：按五项查 Rerank 层：模型是否适配语言和领域、Rerank 输入是否过长被截断、分数融合是否把关键词结果压下去、相邻 Chunk 合并是否带进噪声、`rerank_top_n` 是否过小。我会用 MRR 和 Context Precision 量化排序改善，并分别记录粗召回候选、重排后 Top-K、最终上下文三个阶段，避免把候选池高召回当成模型真看到了证据。
**追问 2**：换了个更贵的 Rerank 模型，收益怎么算值不值？
**答**：看目标语言、领域的 MRR 和答案质量提升，减去多出来的延迟和推理成本。我在同一评测集上 A/B，Cross-Encoder 主链路成本可控，LLM 打分虽能给理由但慢、贵、稳定性受 Prompt 影响，只适合小流量高价值判断；若 Context Recall 本来就低，换任何重排模型都没用，钱要花在解析和 Chunk 上。

### J4-35 上下文压缩有什么价值？什么时候会伤害答案质量？
**面试官**：上下文压缩有什么价值？什么时候会伤害答案质量？
**我（60 秒口述）**：压缩围绕当前 Query 保留证据、降低 Token 和噪声，但选择性抽取可能漏掉隐含条件、查询相关摘要可能引入改写偏差、结构化抽取依赖 Schema 设计，压过头就会丢证据。为什么需要它，因为窗口变大不等于可以忽略注意力、延迟、成本和信噪比，不相关片段会占着模型阅读位置，导致抓错证据、忽略中间信息、回答不聚焦、成本和首字延迟上升；原则是每个片段都要能支撑一个结论或条件。三种方式各有风险：只留相关原句可能漏隐含条件，压成摘要可能改写偏差，抽字段吃 Schema 设计。落地先按规则过滤和去重、只对较长片段调 LLM 压缩，别为每个 Chunk 都付一次模型调用；压缩必须围绕 Query，不是统一摘要。边界是证据质量判断和引用校验仍要在 Prompt 外执行，压缩解决不了引用对不对。
**追问 1**：压缩之后答案反而漏了关键限制条件，怎么定位？
**答**：多半是选择性抽取把隐含条件删了，或摘要改写出偏差，这正是 Chunk 语义丢失的下游版本。我会对照原文看被压掉的片段是否含「除……外」「仅当」这类条件，改回保留原句或降低压缩比；用 `Context Usage` 诊断「材料进了 Prompt 却没被用上」，并查是不是证据被埋在中间位置被 Lost in the Middle 淹没。
**追问 2**：多跳或对比类问题，压缩是不是反而帮倒忙？
**答**：对，这类问题需要保留多条分散证据和它们的关系，压狠了就断了。我会对多跳推理、对比表、需结构化输出和引用约束的样本放宽压缩、甚至不压缩，改用按主题分组或时间线组织；「上下文正确但答案错误」的六项检查里，就包括「问题是否需要多跳推理或对比表」「是否需要先压缩再生成」，得按问题类型决定压缩力度。

### J4-36 RAG 优化为什么必须先建立失败样本集？
**面试官**：RAG 优化为什么必须先建立失败样本集？
**我（60 秒口述）**：没有固定样本集和回放，就没法判断一次改动改善了哪些问题、又引入了哪些回归，讨论向量库选型和调参都没有判断依据。生产级 RAG 要有评估和回放，没有回放就不知道变好了还是只是换了一种错法。我拿三条常见错误佐证：只调 Embedding——表格解析错、Chunk 丢前置条件、正确文档根本没进候选池时，模型换得再好也补不回缺失证据；不做评估——Top-K 变大后部分问题补回证据、另一些问题被噪声干扰，没固定集看不到两种变化同时发生；盲目扩大 Top-K。落地建最小评估集 50 到 100 条，覆盖高频、线上失败、业务关键、多跳、精确匹配、易越权或过期、应该拒答七类，每条存 question、golden_answer、golden_context，每次改动版本化 8 项。边界两条：开发集和终评集分开，同题改写放同一侧防泄漏；反复用来修规则的题不能再宣称是独立盲测。
**追问 1**：评估集建好之后，一次调优你怎么判定「通过」？
**答**：在 holdout 上比关键指标且无回归，才算通过。我固定评估集、一次只改一个变量，比 Context Recall、Context Precision、Faithfulness、Answer Relevancy 加延迟和成本；自动生成标签 `PENDING` 不算通过也不算失败，报告要同时给有效评分样本数和待复核数量，没有有效样本时返回 `null` 或「不适用」，别填 0 或 100%。
**追问 2**：有人拿知识库文档自动生成了一批题当盲测，你觉得靠谱吗？
**答**：可以当种子，但必须人工抽样审核，且不能和开发集混。冷启动用文档作种子生成问题、参考答案、难例是可行路线，但同源生成的近似题要按家族放同一侧，否则命中率虚高；还要保留同领域干扰文档，不然「知识库只有 5 个片段、Top-K 设 8、返回全文就很高命中率」根本区分不出检索策略好坏。

### J4-37 线上 RAG 出现“答非所问”，应该按什么路径定位？
**面试官**：线上 RAG 出现“答非所问”，应该按什么路径定位？
**我（60 秒口述）**：按候选池、排名、上下文、回答四段顺序定位，也就是召回、排序、上下文、生成分层，每段对应不同修复方向，且每次只改一处并用回归集复现。第一步把失败样本分类成七类，别同时动 Prompt、模型和检索参数。第二步看正确证据有没有进候选池：粗召回 Top-50 没出现时查文档入库、解析、Chunk、Metadata、Query 改写、Hybrid 六项，此时继续调 Rerank 没有意义。第三步证据在候选池但没进上下文：查 Rerank 模型、输入截断、分数融合、相邻 Chunk 合并、rerank_top_n 五项。第四步上下文正确但答案错：查 Prompt 边界、冲突版本、中间位置淹没、是否多跳或对比。落地要求先复现原始快照再一次只替换一个变量：保留相同证据换模型、保留相同模型换检索结果、固定被测输出只换 Grader，差异才能归因；线上把各阶段关联到同一条 Trace。边界是别把答非所问一律当生成模型能力问题。
**追问 1**：Trace 里你最少要记哪些字段，才能把四层拆开？
**答**：至少记候选片段、排名、过滤条件、实际上下文、完整回答与引用、各阶段耗时。具体是请求 ID、会话 ID、版本信息、原始问题与改写后问题、粗召回 Top-K 与重排后 Top-K、检索/重排/首个 Token/总耗时与用量、业务终态、拒答原因、异常重试；分别记录粗召回候选、重排后 Top-K、最终上下文三个阶段，避免把候选池高召回当成模型实际看到的证据覆盖率。
**追问 2**：如果同时改了 Prompt、Rerank 模型和 Top-K，结果变好了，能上线吗？
**答**：不能，因为没法归因，也不知道哪个改动引入了回归。原文明确反对同时修改这三者；我会回退到只留一个变量，用固定回归集重跑，确认改善可复现且 holdout 上没掉其他指标，再走灰度。差异很小、样本很少时还要对重点样本重复运行、报告波动，别凭一次高分宣布稳定提升。

### J4-38 GraphRAG 解决什么问题？和标准向量 RAG 有什么区别？
**面试官**：GraphRAG 解决什么问题？和标准向量 RAG 有什么区别？
**我（60 秒口述）**：GraphRAG 把检索对象从文本 Chunk 扩展到实体、关系、路径和社区摘要，解决向量 RAG 不擅长的多跳推理、跨文档归纳和全局主题问题；代价是抽取、消歧、建模、评测和维护成本显著上升。区别按最核心几点讲：向量 RAG 检索 Chunk、判断这段话和我的问题像不像，适合答案就在某几个片段的局部事实问答；GraphRAG 把实体和关系显式建模，查询沿图关系收集证据，更擅长理解这些对象之间到底怎么连起来，适合多跳关系、跨文档归纳和复杂业务分析，还能展示节点、关系、路径和来源。落地我特别提醒别把 GraphRAG 等同于微软那套社区摘要或 Neo4j，它是宽泛称呼，以 Neo4j 为中心的实现也可直接用属性图和 Cypher。引入判断坚持从现有 RAG 的失败样本开始；评估时在同一批语料上记索引 Token、耗时、查询 P95 和答案质量再比较。
**追问 1**：怎么判断我的 Badcase 真该上 GraphRAG，而不是继续调向量？
**答**：看「候选文本是否已齐全、但系统无法按业务关系连起来」。若相关文本压根没进候选集，先查解析、切分、BM25 和重排；只有失败样本持续指向多跳关系、跨文档归纳或结构化约束，才验证图结构。我会先做对照实验，在同一评测集上比图检索相对「向量加混合加 rerank」的收益和成本，试点只抽少量高价值实体和关系、每条保留原文证据。
**追问 2**：上了 GraphRAG 之后，索引和更新成本主要涨在哪？
**答**：涨在抽取、消歧、社区发现和摘要生成的额外 LLM 调用，以及「更新一篇文档可能牵动一片图」。同一文档更新后可能要重算实体节点、关系边、社区划分、社区摘要、实体摘要、向量索引、权限索引七类对象；全量重建会放大成本，增量更新就得记来源和依赖范围。我会在落地阶段四才引入社区发现和全局检索，且评测跟不上就不把全局检索开放给高风险场景。

### J4-39 为什么说 Chunk 是信息孤岛？
**面试官**：为什么说 Chunk 是信息孤岛？
**我（60 秒口述）**：切块把长文档变成可检索单元的同时，也把跨章节事实拆开了，进入索引后这些片段不再共享明确的业务标识，所以语义接近和关系完整是两件事。原文例子很直观：一个系统的定义、负责人、依赖的数据库和事故记录可能散在不同章节，进索引后不再共享业务 ID；相似度能把相关段落排到前面，却不表示这些段落已被识别为同一系统的上下游证据。这跟语义丢失互为表里——后者讲块内上下文被剥离，信息孤岛讲跨块关系断裂。落地按成本从低到高补：章节路径回填把标题拼进每个 Chunk；Parent-Child 用 parent_id 关联回父段落；GraphRAG 用实体 ID 把跨 Chunk 的事实连成图。边界是最容易踩的误区——以为扩大 Top-K 就能连起关系，其实扩大 Top-K、加 rerank 仍以片段排序为中心，关系链缺少显式表示时不会自动消失。
**追问 1**：信息孤岛和「语义丢失」到底差在哪，面试里怎么一句话分清？
**答**：一个讲块内、一个讲块间。语义丢失是块内前置条件、指代对象、表格行列被切没，单看这个 Chunk 还原不了原意；信息孤岛是块与块之间本该属于同一业务对象的事实被拆散、没有共享 ID。对应手段也不同：前者靠章节回填、Parent-Child、Contextual Chunking，后者靠实体 ID 和图关系。
**追问 2**：我把 Top-K 从 5 加到 50，跨章节问题还是答不好，为什么？
**答**：因为候选变多只提高了「相关片段被捞到」的概率，没给出「这些片段属于同一系统、按什么路径相连」的显式结构。50 条塞进上下文还会触发 Lost in the Middle、Token 和噪声一起爆；正确方向是先看是不是根本没召回（查解析、BM25、Hybrid），确认候选齐全仍连不起来，再考虑图结构或迭代式多跳检索，用同一评测集比收益和成本。

### J4-40 向量相似度为什么不擅长多跳推理？
**面试官**：向量相似度为什么不擅长多跳推理？
**我（60 秒口述）**：Top-K 相似度只告诉你哪些片段像问题，不会告诉检索器应该沿系统、负责人、复盘、链路这类受约束路径去补齐证据。原文例子最能说明：问 A 系统的负责人最近参与过哪些和支付链路相关的故障复盘，要完成四次受约束跳转——从 A 系统找负责人、定位该负责人参与的复盘、按支付链路过滤；A 系统说明和支付故障复盘都可能被召回，但 Top-K 本身不会告诉检索器要沿这条路径把证据串起来。落地有了显式关系之后，检索能沿路径扩展：从实体找邻居、从关系找上下游、从事故找影响范围，这也是 GraphRAG 能处理多跳的关键，比如 Neo4j 的 VectorCypherRetriever 先向量命中节点再执行预先约束的 Cypher。边界一个易错点：别以为 Query Decomposition 加多次向量检索就等价于图遍历，HyDE、Query Rewriting 解决的是表述差异，并没解决多跳推理。
**追问 1**：怎么判断一个多跳问题，向量链路是「没召回」还是「连不起来」？
**答**：看各跳证据是否都进了候选池。我在 Trace 里逐跳记命中片段：若某跳（比如「负责人参与的复盘」）压根没召回，那是召回问题，查解析、Chunk、BM25、Query Decomposition；若各跳片段都在、答案仍拼不出，才是关系缺失。用实体、关系召回率这类检索层指标比只看 E2E 分数更能定位。
**追问 2**：沿图扩展时会不会把无权访问的节点一起带进来？
**答**：会，这是 GraphRAG 比向量 RAG 更难的权限点。节点、边、邻居、社区摘要都可能泄露，用户能看某个节点不代表能看它的邻居；我要求原始证据通过授权检查后才进模型上下文，二次校验发生在组装上下文之前，返回引用前再核一次。高敏感或权限频繁变化的语料走鉴权后的局部检索，别用预生成的跨权限摘要。

### J4-41 GraphRAG 中实体、关系、社区发现分别是什么？
**面试官**：GraphRAG 中实体、关系、社区发现分别是什么？
**我（60 秒口述）**：实体是图谱最小业务对象也就是节点，关系显式记录对象间依赖、影响、负责等联系也就是边，社区发现把连接紧密的节点聚成主题群并为其生成摘要，三者是构建 8 步里的核心三段。实体不一定是严格人名组织，也可以是业务系统、技术组件、条款，抽得太粗或太碎都伤质量。关系把订单中心和支付故障之间是依赖、影响还是仅仅同时出现显式化，这是向量只给语义相近做不到的。社区发现把连接紧密的节点聚成社区，支付稳定性是摘要阶段生成的标签、不是算法产出的，Microsoft 路线常用 Leiden、Louvain 划分层级社区。落地把实体抽取当领域建模做：用 JSON Schema 强约束格式、Few-shot 覆盖正反边界例、每个实体强制 source_text_span 溯源。边界是别忘了图谱归一和实体消歧，多个别名合不合并不能全靠 LLM 猜。
**追问 1**：实体抽取最容易出什么问题，你怎么兜？
**答**：抽重、抽错、抽太碎，尤其同名实体、别名、缩写、噪声实体。我不让 LLM 自由输出，用 JSON Schema 强约束、Few-shot 告诉它什么不该抽、设最大实体数上限、强制 `source_text_span`；生产再配术语词典、别名表、置信度阈值和评测集做归一。「没有来源追溯的图谱，不建议直接用于高风险问答」，关系字段里的 `source_span` 就是给人工核对留的。
**追问 2**：抽取用的 LLM 升级了，图谱要全量重抽吗？
**答**：不必全量，靠 `extraction_model_version` 做差量重抽和 A/B 对比。我会把每条关系的抽取模型版本记进字段，升级后先在一小批语料上比实体、关系召回率，确认新模型更稳再逐批迁移；社区划分和摘要也要跟着刷新，因为它们依赖底层实体关系，这正对应「更新一篇文档可能牵动一片图」的成本。

### J4-42 全局检索和局部检索有什么区别？
**面试官**：全局检索和局部检索有什么区别？
**我（60 秒口述）**：局部检索 Local Search 从已知实体向邻居和关联文本扩展，服务围绕特定实体的问答；全局检索 Global Search 先聚合社区或主题摘要再由模型归纳排序，服务跨语料的主题问题。机制上，Local 适用订单中心依赖哪些服务、某故障的上下游链路，起点是实体，返回邻居、关系路径和相关原文片段；Global 适用这批报告里反复出现的风险主题是什么，走社区摘要 Map-Reduce，不是更大 Top-K 的向量检索，且全局回答仍不替代原文核验。中间还有 DRIFT Search，在实体邻居之外加社区摘要。落地最关键一步是查询路由：局部事实走向量或局部图检索，实体关系走局部图检索，多跳走图遍历加向量补证据，全局归纳走社区摘要。边界一句我很认同：一个成熟系统不会把所有问题都扔给 GraphRAG，很多简单问题用向量检索更便宜、更快、更稳；Text2Cypher 还得限制在 Schema 白名单和只读账户内。
**追问 1**：一个「某故障影响了哪些接口」的问题，你怎么确认该走 Local 而不是 Global？
**答**：看有没有明确实体起点、要不要 Relations 路径。有具体故障实体、答案沿 `[:AFFECTS]` 这类边扩展就是 Local；只有「这批事故整体暴露了什么架构风险」那种跨语料归纳才走 Global。我会在查询路由里记下判定依据和日志，用实体召回率、关系召回率（检索层）和 Faithfulness（生成层）分别验，别把全局回答当事实核验结果。
**追问 2**：Global Search 的社区摘要里混进了无权文档，查询时按文档 ID 过滤能挡住吗？
**答**：挡不住，多个来源共同生成的摘要里敏感内容已经写进去了，事后按 ID 过滤删不掉。我的处理是按稳定权限分区分别生成摘要、查询时只用当前用户完整有权访问的分区，权限高度动态就不预生成跨权限摘要；高敏感语料走鉴权后的局部检索，原始证据过授权检查再进上下文。这也说明全局检索不该随便开放给高风险场景。

### J4-43 GraphRAG 的社区摘要有什么价值？它的成本在哪里？
**面试官**：GraphRAG 的社区摘要有什么价值？它的成本在哪里？
**我（60 秒口述）**：社区摘要让跨语料归纳成为可能，先把语料聚成主题群再让 LLM 全局归纳，但每次生成和更新都要额外 LLM 调用，语料扩大后抽取与摘要刷新成本同时上升，还有丢约束、引入幻觉、权限泄露的风险。价值在跨文档主题归纳：单次 Top-K 只能看到局部窗口，召回太多 Token 成本和噪声一起爆炸，社区摘要正好补这个空。成本按四类额外 LLM 调用算：抽取实体关系、生成实体描述、生成社区摘要、版本更新时刷新摘要。落地建议先以一小批全局问题验证答案质量，再决定是否引入多层社区摘要和 Global Search；阶段四重点评社区划分是否合业务直觉、摘要是否遗漏约束、不同权限用户看到的摘要是否安全。边界是别忽略更新一篇文档可能牵动一片图，实体、关系、社区、摘要、向量、权限索引七类对象可能要重算或失效。
**追问 1**：社区摘要这套，索引成本怎么向老板解释值不值？
**答**：不给拍脑袋倍数，用同批语料的可观测对比说话。我会记录索引 Token、索引耗时、存储、查询 P95 和答案质量，跟「向量加混合加 rerank」基线放一张表；价值只在「跨文档主题归纳」这类问题上体现，若失败样本多是简单事实问答，这笔额外 LLM 调用就不划算。先一小批全局问题验证，再决定要不要多层社区。
**追问 2**：社区摘要生成错了或泄露了，怎么回滚？
**答**：摘要是派生物，回滚要连底层实体关系和社区划分一起处理，不能只删摘要文本。我会保留每版摘要的源文档 ID 用于审计和失效更新，按权限分区重建受影响社区；若涉及泄露，第一步不是慢慢修索引，而是立刻下线相关知识库或租户检索入口、禁用问题索引、强制引用前鉴权，只有无法界定影响面才考虑全局停服。

### J4-44 GraphRAG 如何做权限过滤？
**面试官**：GraphRAG 如何做权限过滤？
**我（60 秒口述）**：GraphRAG 的权限过滤不能只看文档级别：节点、边、邻居、社区摘要都可能泄露，权限边界必须在摘要生成时处理，查询阶段仅按文档 ID 过滤删不掉已混入摘要的敏感内容。因为节点、边、邻居、全局摘要都可能泄露，不只是文档级；尤其多个来源共同生成社区摘要时，无权文档的内容可能已写进摘要，按文档 ID 过滤删除不了。落地守三条原则：按稳定权限分区分别生成摘要，查询时只用当前用户完整有权访问的分区，权限高度动态时不预生成跨权限摘要；摘要保留全部源文档 ID 用于审计，但不能用权限交集当放行条件；高敏感语料走鉴权后的局部检索。边界是最容易错的那句——以为给摘要挂上源文档 ID、查询时按 ID 过滤就行，原文明确否定。
**追问 1**：权限频繁变动的租户，社区摘要到底还预不预生成？
**答**：不预生成跨权限摘要，改走鉴权后的局部检索。因为权限组合一变，预生成摘要里的敏感内容没法靠查询过滤撤掉；我让原始证据逐条过 `tenant_id`/`acl` 授权检查再进上下文，全局归纳这类需求要么按稳定分区出摘要、要么直接禁用。这比「先生成再想办法过滤」安全得多。
**追问 2**：某文档从全员可见改成仅高管可见，GraphRAG 这层要动哪些对象？
**答**：不止文档，节点、边、邻居、社区摘要、权限索引都可能带旧权限信息。我会触发重新索引（支持原子更新就只改 `acl` 元数据），按源文档 ID 找到受影响的社区并标记摘要失效、按分区重建；同时记 `doc_id`、`change_type`、`timestamp`、`operator`、`result` 审计日志，监控 `acl_mismatch_count`，返回引用前再做一次防御性鉴权。

### J4-45 什么场景适合 GraphRAG？什么场景不适合？
**面试官**：什么场景适合 GraphRAG？什么场景不适合？
**我（60 秒口述）**：判断标准是回答所需的证据是否必须经过实体关系、路径或跨文档主题才能拼完整；一旦上 GraphRAG，数据治理范围就从 Chunk 和向量扩展到实体、关系、摘要及其版本。适合四类：企业知识库复杂问答、IT 架构和故障影响分析、金融风控合规供应链、跨文档主题归纳。不适合或先做稳向量混合检索的也四类：数据量小问题简单、文档质量太差（向量 RAG 的错误通常是找错几段文本，GraphRAG 的错误可能是整张关系网方向错了）、实时性要求极高、团队缺图建模和评测能力。落地判断顺序我背得很熟：若相关文本没进候选集，先排查解析、切分和召回；若候选已齐全但系统无法按业务关系连起来，再验证 GraphRAG。边界是别把有跨文档问题直接等价于该上 GraphRAG，评测还要分检索层、生成层、业务层指标。
**追问 1**：客户说「我们有很多跨文档问题」，你怎么给他降降温、先验证再上？
**答**：先做 Badcase 归因，别被「跨文档」三个字带跑。我把失败样本按五类归：单纯没召回关键词→先优化 BM25 和 query rewrite，Chunk 切分不合理→先优化 Chunking，需要跨实体关系推理→才适合图结构，需要全局主题归纳→社区摘要，需要精确过滤和权限约束→结构化查询；再在同一评测集上对照实验，记索引 Token、耗时、存储、P95 和答案质量，确认图检索真改善目标问题。
**追问 2**：团队第一次做，怎么控制 GraphRAG 的试错成本？
**答**：从阶段三轻量图谱起步，不上来就全量社区摘要。只抽系统、接口、负责人、事故、制度条款几类核心实体，只留依赖、负责、影响、属于、引用少量高价值关系，图谱只用于检索扩展、不直接做最终事实判断，每条关系保留原文位置、版本和权限信息；入口分类器要可解释、置信度低降级回 Vector RAG、路由日志可回溯。评测跟不上就不开放全局检索给高风险场景。

### J4-46 成熟系统为什么会组合关键词检索、向量检索、多向量检索和图检索？
**面试官**：成熟系统为什么会组合关键词检索、向量检索、多向量检索和图检索？
**我（60 秒口述）**：因为不同问题类型的失败原因不同，单一检索通道只能覆盖一类证据形态；成熟系统按问题类型动态路由并保留降级路径，用可解释的分类器把每类问题交给最便宜且够用的检索方式。各通道分工：BM25 管错误码、SKU、版本号精确命中；向量检索管同义改写和隐含意图；多向量管 Chunk 内细粒度匹配、表格图片摘要与原始素材分离；图检索管多跳关系、影响范围、全局主题归纳；Text2Cypher 管精确过滤和报表类问答。落地就是 Hybrid RAG 路由：入口分类器到事实型 Vector RAG、关系型 Local Search、全局型 Global Search，置信度低降级回 Vector RAG 再 LLM 生成。三个关键点：分类器要可解释、降级策略要明确、路由日志要可回溯。边界是最常见的误解——把组合理解成所有问题都跑全部通道再融合，那样延迟和成本直接爆；GraphRAG 只是关系检索的一条路线，该用同一评测集比收益和成本。
**追问 1**：入口分类器判错了怎么办，路由这块怎么兜底？
**答**：靠降级和日志，不靠分类器 100% 准。我把置信度低或图检索失败的请求统一回退到 Vector RAG 保底有答案，路由日志记下每类的判定依据和最终通道，定期用 Badcase 回流修分类器；分类器本身要可解释（轻量规则或小模型），别用黑盒拍板。上线前用查询类型 5 行表逐类测，确认没有哪类被系统性送错通道。
**追问 2**：全部通道都留着，运维和延迟成本怎么控？
**答**：按「按需触发」而不是「全量并行」。简单事实型只走向量或加 BM25，关系、全局型才启图检索和社区摘要；我用三级上限 `recall_top_k` 30–100、`rerank_top_n` 5–10、`context_top_n` 3–6 控制每路候选，热点查询缓存、超时降级。已有向量基础设施的可以「外部向量库 + Neo4j」把向量存 Weaviate/Qdrant 再映射回节点，省一套迁移成本。

### J4-47 RAG 知识库为什么不能只新增不删除？
**面试官**：RAG 知识库为什么不能只新增不删除？
**我（60 秒口述）**：只写新向量不清理旧版本，会让过期内容、已删除文档和已无权访问的幽灵数据继续被召回，回答持续失真，而且审计、恢复、跨索引同步全失去依据。文档明明更新了、回答还是老样子，更常见的原因不是模型，是更新链路只做了写入新内容，没处理旧版本、权限和索引一致性。更新要同时满足五个目标：动态性、准确性、一致性、可回滚、可观测。落地修改文档走四步：按 doc_id 查元数据库记当前活动版本和旧 chunk_id 列表，写带新 version_id 的 Chunk 且 status 为 building 不参与在线检索，校验三端后把活动版本原子切到新版，旧版标记删除异步清理。三端一致性靠 outbox pattern 记变更事件、消费者幂等执行、定期 reconciliation 对账。边界是六个常见坑：只插不删、Embedding 模型混用、Chunk 策略变了历史不重建、删除后仍被召回、权限元数据不同步、变更检测漏检。
**追问 1**：直接「先删旧记录再写新记录」会出什么事？
**答**：出现短暂空窗，期间查不到任何版本；反过来「先写新记录但不做版本过滤」会新旧同时命中。正确是「先写不可见 building 新版本 → 校验三端 → 原子切别名 → 旧版标记删除」四步，配合 `active_version` 过滤。`upsert` 也有坑：它只覆盖同一主键实体，文档重新切分后 `chunk_id` 变化，仍要按 `doc_id + version_id` 清理旧版本残留。
**追问 2**：一篇文档从全员可见改成仅高管可见，只删旧向量够吗？
**答**：不够，这是「幽灵数据」的典型来源，权限变更必须触发重新索引。若向量库旧 `acl` 没更新，普通员工仍可能召回；支持原子更新 ACL 字段就只改元数据不重建向量，否则按 `doc_id` 重刷。我会用别名灰度切换加保留旧索引回滚，审计日志记 `change_type`、`operator`、`result`，并监控 `acl_mismatch_count` 确认源系统与索引 ACL 一致。

### J4-48 增量更新和全量重建怎么选？
**面试官**：增量更新和全量重建怎么选？
**我（60 秒口述）**：常见组合是增量更新处理日常变化，全量重建负责模型升级、切分策略迁移、数据结构变更、严重故障恢复和定期健康维护，两者配合系统才不容易长期漂移。增量适合变更频率适中、要实时性、规模较大的场景，依赖三种变更检测：Webhook 事件驱动延迟最低、CDC 监听 binlog 适合结构化源、定时轮询简单但有延迟；生产更稳的是事件驱动加轮询兜底，中间用 Kafka 解耦。全量重建适用五类：Embedding 模型升级这个硬需求、Chunk 策略调整、数据结构变更、严重故障恢复、定期健康维护。落地我最怕服务中断，用别名切换五步：查询走 prod_index 指向 index_v1，后台建 index_v2，验证通过把别名指到 v2，保留 v1 约 7 天快速回滚，确认没问题再删。边界两个易错点：把全量重建当日常手段，以及三端不在同一事务域的部分成功，得以元数据库作 source of truth 加补偿重试。
**追问 1**：事件驱动加轮询兜底具体怎么防漏检和乱序？
**答**：轮询负责兜漏、版本号负责防乱序。我让每个事件带 `source_version`、`updated_at` 或单调 `revision`，写入前校验 `event.version >= current_version`，旧事件直接丢弃或记审计；对同一 `doc_id` 用 Kafka key 做分区有序消费，乱序丢弃打点监控。幂等靠 `doc_id + content_hash` 或 `doc_id + version_id` 唯一约束加 `INSERT ... ON CONFLICT DO NOTHING`。
**追问 2**：Embedding 模型必须升级，重建期间线上查询不能断，怎么排？
**答**：走蓝绿，不原地改。我在新索引用新模型重建全量，新旧并行一段时间比召回率和回答质量，确认稳定后用索引别名切流量，保留旧索引约 7 天回滚，删旧前确认无问题；查询侧校验 `embedding_model_version`，不匹配就拒查或降级。回滚时记得把模型和索引一起切回旧版本，别只切索引。轮询周期不能统一按周或月，要根据索引实现、删除比例、重建成本和一致性指标定。

### J4-49 Embedding 模型升级后，为什么通常需要重建索引？
**面试官**：Embedding 模型升级后，为什么通常需要重建索引？
**我（60 秒口述）**：因为索引时用的 Embedding 模型必须和查询时用的模型一致，不同模型的向量空间不通用，混用等于在两个不同空间里算相似度，整个排序基础已经坏了，重建绕不过去。看维度更好懂：同一句话用 text-embedding-3-small 和 all-MiniLM-L6-v2 编出来没有可比性；维度不同通常放不进同一个索引；维度相同但模型不同，相似度分数也不具备可比性。生产最容易忽视两个场景：模型升级，历史数据必须重编码重入索引；本地模型和 API 模型混用，测试用本地、生产用 API，上线召回率直接腰斩。落地把模型信息写进元数据 embedding_model、embedding_model_version、embedding_dimension，每次查询校验版本，不匹配就拒查或降级；升级走蓝绿五步：新索引重建、新旧并行对比、别名切流量、保留旧索引回滚、确认后删除。边界是别以为维度相同就能混用，切分策略、解析方式变化也应触发重建或双索引灰度。
**追问 1**：升级前怎么证明新模型确实更好，而不是白重建一次？
**答**：新旧索引并行，在同一评测集上比召回率和回答质量。我固定其他变量，只比 Context Recall、MRR、答案准确率和 P95 延迟，顺带看 `embedding_dimension` 从 1536 到 3072 带来的内存和索引时间成本；指标不升或成本不可接受就不切。元数据里记 `embedding_model_version`，查询侧校验版本是防止「切了索引没切查询」的最后一道闸。
**追问 2**：切到新模型后线上召回掉了，怎么最快恢复？
**答**：别名把流量指回旧索引，且查询侧模型一起切回旧版本。前提是旧索引还按保留策略留着（约 7 天），升级前记录过旧 `model_name`、`model_version` 和对应索引；旧索引已清理才需要基于旧模型重建。这也是我强调「蓝绿加别名加保留期」而不是原地改的原因，恢复是秒级切别名，不是重跑几小时全量。

### J4-50 Chunk 策略变更会影响哪些历史数据？
**面试官**：Chunk 策略变更会影响哪些历史数据？
**我（60 秒口述）**：Chunk 策略变更影响全部历史文档：切分结果、Chunk ID、向量与全文索引条目，以及依赖 Chunk ID 的评测标注都得跟着动；不能只对新文档生效，否则一个知识库里会混着多套切分逻辑，召回评估也会乱。还有个容易漏的细节：调整分块后 chunk_id 往往会变，所以比较策略时不能用旧 Chunk ID 判断新分块是否命中，得用原文位置或稳定事实 ID 标注再映射。落地给两种迁移：全量重建，或先写新版索引逐批迁移旧文档、验证后切活动版本的双索引灰度，但同一评测和检索链路要能区分策略版本，不能让两套策略在没有版本标记的情况下混用。元数据里把 chunk_strategy、chunk_size、chunk_overlap 和 content_hash、version_id 一起记，评估和回滚才有依据。边界是别只重建向量库不重建全文索引，三端要一致；也别沿用旧评测集的 Chunk ID。
**追问 1**：双索引灰度期间，怎么比新旧切分谁好？
**答**：用稳定事实 ID 标注，在两套索引上跑同一评测集。我不拿旧 `chunk_id` 直接判命中，而是用 `expectedEvidence` 的稳定 ID 和 `golden_context` 对齐，分别算 Context Recall、答案准确率和平均上下文 Token；链路里带 `chunk_strategy` 版本标记，确保查询不会同时打到两套策略。确认新版无回归，再用别名原子切活动版本、保留旧索引回滚。
**追问 2**：Chunk 策略变更和 Embedding 模型升级，都要重建吗，能合并做吗？
**答**：都影响全量，但性质不同：Embedding 升级是硬需求必须全量重建，Chunk 策略变更可版本化索引逐批灰度迁移。我不建议合并做，因为一次只替换一个变量才能归因；两者都要走别名切换、灰度、回滚，且三端（向量、元数据、全文索引）一起迁，别只动向量库。版本化 8 项里正好包含 Chunk 策略版本和 Embedding 模型版本，分开记、分开切。

### J4-51 如何避免同一文档多个版本同时被召回？
**面试官**：如何避免同一文档多个版本同时被召回？
**我（60 秒口述）**：用先写不可见新版本、原子切换活动版本、旧版标记删除的版本化机制，配合 active_version 过滤、索引别名、双索引切换，并靠 doc_id 加 version_id 与 content_hash 保证幂等去重。为什么修改比新增复杂，关键是旧版本怎么办——既要避免查询同时看到两版，也要避免更新过程中暂时查不到任何版本；原文点了两个错误做法：直接先删旧再写新有短暂空窗，直接先写新但不做版本过滤会新旧同时命中。落地防重复用唯一约束 doc_id 加 content_hash 或 doc_id 加 version_id，chunk_id 用完整内容哈希避免前缀碰撞，配 ON CONFLICT DO NOTHING；并发场景先查再写不安全，更稳是唯一约束、乐观锁或事务 outbox 三选一，index_status 走四态、claim_token 加 10 分钟租约防重复处理。乱序事件处理四件：事件带 source_version、写入前校验版本丢弃旧事件、同一 doc_id 用 Kafka key 分区有序消费、乱序丢弃打点。边界是别把软删除当版本隔离，is_deleted 只解决删除状态。
**追问 1**：消息队列重复投递或 worker 重启，怎么保证不写重？
**答**：靠幂等键，不靠「先查再写」。我用 `doc_id + version_id` 唯一约束让数据库拒绝重复，向量 `upsert` 以 `chunk_id` 为幂等键，`ON CONFLICT DO NOTHING`；处理侧用 `claim_token` 加 `claimed_at` 抢占，`processing` 且超过 10 分钟租约的任务可被接管，并用 PostgreSQL 风格 `RETURNING` 拿抢占结果，避免依赖不同驱动 `rowcount` 不一致。
**追问 2**：先收到 v3 再收到 v2，怎么防止旧版本把新的盖掉？
**答**：写入前校验版本号，旧事件直接丢弃或记审计日志。每个事件带 `source_version`、`updated_at` 或单调 `revision`，`event.version >= current_version` 才允许写；同一 `doc_id` 的消息用 Kafka key 落同一 partition 保分区有序，再对乱序丢弃做监控打点。这样即使网络重排，活动版本也只会被新版本推进，不会回退。

### J4-52 知识库更新如何做灰度、回滚和审计？
**面试官**：知识库更新如何做灰度、回滚和审计？
**我（60 秒口述）**：灰度按文档数量、用户、问题类型小流量验证并盯四个指标，回滚靠索引别名加版本快照加权限应急阻断，审计靠更新操作日志与全链路可观测性。灰度三种做法：先更新 10% 文档、先让 5% 用户看新索引结果、或先验证精确查询这类敏感问题；四个指标记着 retrieval_hit_rate@10 降超 5%、延迟升超 20%、引用准确性降超 3%、负反馈率升超 2%，但原文强调阈值只是示例，要基于历史基线和 A/B 校准，任一告警先暂停灰度。回滚四类：别名切回旧索引、模型升级把模型与索引一起切回旧版本、数据版本用 version_id 从快照恢复、权限回滚最特殊——若泄露，第一步是立刻下线相关检索入口、强制引用前鉴权。审计记 doc_id、change_type、operator，失败重试走指数退避加死信队列。边界是上线检查四件事：同一套模型版本、候选进上下文前鉴权、别名原子切换、审计贯穿链路。
**追问 1**：灰度时四个指标都没报警，是不是就能全量了？
**答**：还不能，得看离线回归集和 holdout。我先在固定评测集上确认 Context Recall、Faithfulness 没有回归，灰度流量里再观察一段时间；阈值只是示例，要基于自己历史基线和 A/B 校准，不能直接照抄。另外只检查差评样本得到的是问题分析结果、不能代表全流量质量，抽样要保留正常流量也覆盖新问题类型和拒答。
**追问 2**：全量后发现新索引把一篇无权文档召回给了普通员工，第一步做什么？
**答**：先阻断影响面，不是慢慢修索引。我立刻下线相关知识库或租户检索入口、禁用问题索引、强制引用前鉴权，只有无法界定影响面才考虑全局停服；同时用别名把流量切回旧索引，按 `doc_id` 查审计日志定位是哪次权限变更漏了 `acl` 重刷，修完用 `acl_mismatch_count` 归零验证再恢复。这跟普通召回回滚不同，泄露场景优先级是止损。

### J4-53 RAG 评测为什么要分检索质量和生成质量？
**面试官**：RAG 评测为什么要分检索质量和生成质量？
**我（60 秒口述）**：因为检索差和生成差最终都表现为回答不准，但优化方向完全相反；分段评测是定位问题的基本前提。举个例子，用户问怎么退款答错，先看退货政策有没有被召回：没召回就查分块、向量库、混合检索权重和 Reranker；政策已经进了上下文、回答仍没给申请入口、时限和材料，再去看 Prompt、模型和上下文注入方式。落地把链路画成两张账：检索层看相关内容有没有进上下文，用 Recall@k、Hit Rate@k、MRR、Context Precision、Context Recall；生成层看模型有没有基于这些内容回答，用 Faithfulness、Answer Relevance、Context Usage、Noise Sensitivity。还要固定评测对象：粗召回候选、重排后 Top-K、最终上下文分别记录，别把候选池高召回当成模型实际看到的证据覆盖率。边界是三大陷阱：用检索结果直接当标准答案、忠实度当正确性、执行失败混入分母；没有有效样本时返回 null 或不适用，别填 0 或 100%。
**追问 1**：老板只给最终答案评分，你怎么把检索和生成拆开？
**答**：先补可观测数据，再做固定上下文对照实验。我在 Trace 和日志里补出候选片段、实际上下文和引用，对每个失败样本补五项检查；定位时一次只替换一个变量：保留相同证据换模型、保留相同模型换检索结果、绕过 Agent 直接调工具、固定被测输出只换 Grader，差异才能归因。判据是 `golden_context` 未命中（Hit@K 或 Evidence Recall@K 低）归检索侧，证据进 Prompt 但答案仍错（Faithfulness、Context Usage 低）归生成侧。
**追问 2**：模型照着一份过期手册回答，Faithfulness 很高，这算好答案吗？
**答**：不算，忠实度和正确性会背离。Faithfulness 只检查回答能否被给定上下文支撑，模型照过期手册答可以很忠实却违反当前有效政策；反过来模型凭参数碰巧答对但上下文没依据，也不能认定忠实。所以我会把「证据时效合格率」这类自定义指标加进生成质量账，并在上下文里标注更新时间和版本，别让单一指标掩盖合规问题。

### J4-54 MRR、NDCG、Recall@K、Context Precision、Faithfulness 分别衡量什么？
**面试官**：MRR、NDCG、Recall@K、Context Precision、Faithfulness 分别衡量什么？
**我（60 秒口述）**：五个指标分两层：前四个评检索排序和证据覆盖，Faithfulness 评生成忠实度。一句话记：MRR 看第一条相关结果排第几，Recall@K 看该找的找全没，Context Precision 看相关上下文是否排在前面，NDCG 看整体排序质量含相关度分级与位置折损，Faithfulness 看回答能否被上下文支撑。展开口径：MRR 对每题首条相关结果的倒数排名求平均、未命中记 0，和 Hit@K 的区别是有没有对排多前；Recall@K 是被召回相关文档数除以总相关文档数，常看 Recall@3 或 Recall@5；Faithfulness 把回答拆成事实主张逐条查上下文能否支持，纯拒答和空答案要单独处理。NDCG 我得诚实标注：源文档没给定义，按通用定义是 DCG@K 除以 IDCG@K，它考虑整个列表、支持多级相关度、对靠后位置对数折损，但不冒充原文指标。边界是几个高频混淆：Hit@K 当 Recall@K、Context Recall 当 Recall@K、Faithfulness 当答案正确性；知识库外问题 Recall 分母为零应标不适用、转评拒答。
**追问 1**：这五个里，一次检索改动你主要看哪几个？
**答**：看 MRR、Recall@K 和 Context Precision，生成改动才看 Faithfulness。前四个传统 IR 指标通常需要标注相关文档 ID，这是 Golden Set 最花时间的部分；文档级标注太贵可先用 RAGAS 这类基于 LLM 的指标起步，但依赖 LLM 判断、要人工抽样。示例：需「20 MB」和「7 天」两条证据、Top-3 只命中 1 条，则 Hit@3 = 1、Evidence Recall@3 = 1/2、RR@3 = 1/2，命中一条不代表资料找全。
**追问 2**：Noise Sensitivity 偏高，按你这套指标该往哪查？
**答**：它是 RAGAS 指标，0 到 1 越低越好，检查回答里的错误声明是否可归因于无关检索上下文。分数偏高先查分块、Reranker 和上下文排序；如果资料已排到前面，再查 Prompt 是否缺「只使用相关资料」的约束。另外绝对阈值如「Faithfulness 低于 0.75 不通过」、从 0.82 降到 0.79 算不算回归，都得结合固定评测集和重复运行的波动判断，别凭一次高分宣布稳定提升。

### J4-55 原始文档已经入库，但相关问题始终召回不到正确 Chunk，你会从哪些环节开始检查？
**面试官**：原始文档已经入库，但相关问题始终召回不到正确 Chunk，你会从哪些环节开始检查？
**我（60 秒口述）**：这是正确证据没进候选池的粗召回故障，按文档、解析、Chunk、Metadata 权限、Query、召回通道六段顺序排查，也就是分层里的第一层，这时候调 Rerank、换生成模型都无效。第一步确认文档是不是真入库、哪个版本、is_deleted 有没有被误标、active_version 是不是还指向旧版；第二步查解析——多栏 PDF 顺序、表格列关系、OCR 错字、有没有部分页面解析失败被标成部分可用；第三步查 Chunk 是否切断关键事实；第四步查 Metadata 过滤是否过严，tenant_id、acl、版本、更新时间有没有把正确 Chunk 挡在候选外；第五步看 Query 要不要改写、分解或 HyDE；第六步看要不要 BM25 或 Hybrid。索引侧再补三查：距离运算符和 operator class 是否一致、ef_search 或 probes 是否过小、是不是重建后 Embedding 模型不一致。落地把样本纳入评估集、修复后回放确认正确证据进粗召回 Top-50。边界是别一上来换 Embedding 或扩大 Top-K，也别漏幽灵数据、旧版本这个方向。
**追问 1**：文档明明在库里，为什么还要先查「幽灵数据、旧版本」？
**答**：因为「入库」不等于「当前活动版本可检索」。文档可能被改过五版、只插不删，或 `is_deleted` 误标、`active_version` 指向旧版，查询默认只保留 `is_deleted=false` 且限定活动版本；我会按 `doc_id` 查元数据库核对版本，用 `EXPLAIN ANALYZE` 看是否命中 Index Scan。这类问题换 Embedding 模型一点用没有。
**追问 2**：排查一圈是英文 PDF 里的 `micro-\nservice` 断词导致的，怎么修才不复发？
**答**：这是专有名词断词，得在解析、切分层修，不是检索层。我改用按语义边界或语言感知的切分，跨行连字符还原、按 `class`、`def` 或条款结构切，并把章节路径回填进 Chunk；同时在评测集里加一条覆盖该专有名词的精确匹配样本做回归。修复后回放确认正确证据进 Top-50，并记录 `chunk_strategy` 版本，避免以后换解析器又悄悄退化。

### J4-56 正确文档进入了候选池，却总是排在 TopK 之外，应该调整召回还是引入 Rerank？
**面试官**：正确文档进入了候选池，却总是排在 TopK 之外，应该调整召回还是引入 Rerank？
**我（60 秒口述）**：既然正确证据已在候选池，问题在排序而不是召回，应优先引入或优化 Rerank 与融合策略；但先确认 TopK 指哪一层，因为三级上限不同。我按四层定位，本题落在第二层排序：先分清 recall_top_k 30 到 100、rerank_top_n 5 到 10、context_top_n 3 到 6，正确文档是在粗召回里但没进重排后 5 到 10，还是在重排后但没进最终上下文，两者修复方向不一样。若已上 Rerank，查五项：模型是否适配语言和领域、输入是否过长被截断、分数融合是否把关键词结果压下去、相邻 Chunk 合并是否带进噪声、rerank_top_n 是否过小；若没上，就讲清双塔向量只衡量表达接近、Cross-Encoder 把 Query 和候选一起编码能把含条件与结论的片段顶上来。落地用 MRR、Context Precision 量化改善，分别记录三阶段。边界是最常见的错答一律扩大 recall_top_k——扩候选只增加机会，同时拉高重排输入、Prompt Token 和噪声；也要记 Rerank 不会补回候选池里不存在的文档。
**追问 1**：怎么确认是排序问题、不是召回问题？
**答**：看 Context Recall 和正确证据在粗召回里的位置。我先把粗召回拉到 Top-50 看正确文档在不在：在，就是排序或融合问题，去调 Rerank 和 RRF 权重；不在，才是召回问题，回解析、Chunk、Metadata、Hybrid。用 MRR 量化「第一个正确结果排多前」、Context Precision 量化进上下文的纯度，比只盯 E2E 分数准。
**追问 2**：上了 Cross-Encoder 之后 P95 涨了，怎么权衡？
**答**：控的是重排输入量，不是砍掉重排。我把 `recall_top_k` 稳在 30–100、`rerank_top_n` 5–10，只对候选做一次精排，压缩后 `context_top_n` 留 3–6 进 Prompt；专用 Reranker 担主链路，时间、权限、版本这类确定条件交给规则重排，LLM 打分只放离线或低流量复杂判断。若正确文档在粗召回尾部极靠后，再顺带查 `ef_search`、`probes` 和 Hybrid 通道，但主因仍是排序。

### J4-57 检索结果正确，模型仍然引用了错误片段，如何检查上下文顺序、截断和指令约束？
**面试官**：检索结果正确，模型仍然引用了错误片段，如何检查上下文顺序、截断和指令约束？
**我（60 秒口述）**：这是上下文、生成段故障，按上下文顺序、截断与压缩、冲突版本、证据边界指令、引用校验五项检查，且引用校验必须在 Prompt 外执行。第一，顺序：最相关证据有没有放前面、证据是否被埋在中间被 Lost in the Middle 淹没；第二，截断与压缩：Rerank 输入是否过长被截断、context_top_n 是否过小、选择性抽取是否漏隐含条件、摘要是否引入改写偏差；第三，冲突版本：有没有旧版和新版政策同时进入、有没有标更新时间和版本；第四，指令约束：Prompt 有没有写清只基于给定上下文、不足明说无法判断、关键结论附来源、不把相似文档当当前版本这四条；第五，引用校验——提示词能表达拒答但无法验证模型是否遵守，所以要用 Citation Accuracy 检查。落地用自定义 Context Usage 诊断材料已进 Prompt 却没被用上。边界是别只改 Prompt 措辞而不查截断和版本冲突。
**追问 1**：怎么证明模型是「没看到正确片段」还是「看到了但引错」？
**答**：看实际上下文里有没有那条证据，并对照引用位置。我在 Trace 里记录「实际上下文、完整回答与引用」，若正确片段压根没进 Prompt，是截断或 `context_top_n` 过小；若进了但引用指向别的片段，是排序、冲突版本、指令约束问题。用 Citation Accuracy 和「引用支持」逐条核，比只看最终答案准。
**追问 2**：上下文里新旧两版政策都在，模型引了旧版，光改 Prompt 有用吗？
**答**：不够，得在上下文层修。我会给互相矛盾的片段标注更新时间和版本、把低置信度和高置信度分开，按「最相关放前、相邻片段保序」重排，必要时在组装前按 `active_version` 过滤只留当前版本；这其实是「新旧版本被同时召回」的更新链路问题，要回查 `active_version`、`is_deleted` 和别名切换，而不是只靠一句「以最新版为准」的提示词。

### J4-58 同一份文档的新旧版本被同时召回，数据和索引更新链路可能出了什么问题？
**面试官**：同一份文档的新旧版本被同时召回，数据和索引更新链路可能出了什么问题？
**我（60 秒口述）**：说明活动版本切换或旧版本清理失效：要么只写新向量没停旧版本，要么写入删除没在向量库、元数据库、全文索引三端原子一致，要么事件乱序让旧版本覆盖了新版本。按更新链路逐段查：是不是只插新向量不删旧向量；修改流程有没有走先写 building 不可见新版本、校验三端、原子切活动版本、旧版标记删除四步，还是先删后写造成空窗、先写不做版本过滤造成并存；有没有 active_version 过滤或索引别名，查询是否默认只保留 is_deleted 为 false 且限定活动版本；三端是否部分成功，得以元数据库作 source of truth 加 reconciliation；删除是否只清了向量库没清全文索引；幂等与乱序，先收到 v3 再收到 v2 有没有被版本校验拦下。落地修复用 active_version 过滤、索引别名、双索引切换，监控 partial_index_count 和 acl_mismatch_count。边界是别只查向量库不查全文索引与元数据库。
**追问 1**：四步流程里哪一步最容易漏，导致新旧并存？
**答**：最容易漏的是「新版本先 building 不可见加原子切活动版本」这中间态，图省事直接写新记录又不带版本过滤。我要求查询默认 `is_deleted = false` 且限定 `active_version`，切换用别名原子完成；`upsert` 只覆盖同一主键，重新切分后 `chunk_id` 变了，仍要按 `doc_id + version_id` 清旧残留，否则旧块还在池里。
**追问 2**：监控看到 v3 上线后又退回 v2 的内容，怎么定位？
**答**：查乱序事件有没有被版本号拦下。每个事件应带 `source_version`、`updated_at` 或单调 `revision`，写入前校验 `event.version >= current_version` 丢弃旧事件，同一 `doc_id` 用 Kafka key 分区有序消费；我会看乱序丢弃的打点和审计日志 `change_type`、`result`，并用 reconciliation 对比元数据库、向量库、全文索引的活动版本，确认三端一致。

### J4-59 只有最终答案好坏的评分时，如何判断问题出在检索还是生成？
**面试官**：只有最终答案好坏的评分时，如何判断问题出在检索还是生成？
**我（60 秒口述）**：用分段复盘加固定上下文对照实验把 E2E 分数拆开：先在 Trace、日志里补出候选片段、实际上下文和引用，再做 A/B——固定上下文换模型、固定模型换检索结果。第一步补齐可观测，把问题、检索、上下文、模型调用和结果关联到同一条 Trace；第二步对每个失败样本补五项检查；第三步定位时一次只替换一个变量、保留其他不变：保留相同证据换模型、保留相同模型换检索结果、绕过 Agent 直接调工具、固定被测输出只换 Grader，差异才能说明来自模型、第三方系统、架构、代码还是评分器；第四步判据：golden_context 未命中归检索侧，证据已进 Prompt 但答案仍错归生成侧。落地建最小评估集 50 到 100 条含 golden_context，LLM-as-a-Judge 只作辅助信号并用 Cohen's kappa 校准。边界三坑：用检索结果直接当标准答案、把有相关文档等同于模型看到了、执行失败与正常拒答分开记。
**追问 1**：A/B 里「固定上下文换模型」具体怎么操作？
**答**：把同一份检索证据冻成快照，只换生成模型或 Prompt 跑同一批题。若换模型后答案明显变好，问题在生成侧；若怎么换都错，回到检索侧查证据覆盖。我会用固定快照回归（冻结检索语料、工具返回、数据库初始状态和目标时间），示例口径里 Hit@3=1、Evidence Recall@3=1/2、RR@3=1/2 正好说明「命中一条不等于资料找全」，得按证据级判。
**追问 2**：10 题里 2 题超时，其余 8 题答案都好，报告怎么写？
**答**：不能只报 100%。执行成功率 8/10 = 80%、有效答案通过率 8/8 = 100%、超时数量 2 要同时给，正常拒答完成了请求可继续判它是否合理，执行失败没完整答案、不计入答案正确性或忠实度分母；没有有效样本时返回 `null` 或「不适用」，别填 0 或 100%。这样报表才不会掩盖不可用的请求。

### J4-60 某类问题需要跨多篇文档查关系，如何判断应该优化向量 RAG，还是引入 GraphRAG？
**面试官**：某类问题需要跨多篇文档查关系，如何判断应该优化向量 RAG，还是引入 GraphRAG？
**我（60 秒口述）**：按归因顺序判断：先看相关文本是否已进入候选集，没进就先优化解析、切分、BM25 或混合检索和重排；只有候选文本已齐全但系统无法按业务关系连起来、且失败样本持续指向多跳关系或全局归纳时，才引入 GraphRAG。原文说得直白：没有召回文本时先检查解析、BM25、向量检索和重排，已经召回相关文本、但问题依赖明确的实体关系或多跳证据时，再评估图结构。Badcase 先归类：单纯没召回就先优化 BM25、query rewrite 和 Chunking，只有指向跨实体关系或全局归纳才验证图结构。落地先用同一批语料做对照实验，记索引耗时、P95 和答案质量，比较图检索是否真改善；试点用轻量图谱，每条关系保留原文证据。偶发关系型问题先试更低成本的迭代式多跳检索。边界是把跨多篇文档直接等价于必须上 GraphRAG，若根因是没召回，图结构只会把问题复杂化。
**追问 1**：你说先做对照实验，具体拿什么当基线、看什么指标判赢？
**答**：基线是「文档解析稳定、Chunk 可评测、向量加 BM25 混合、rerank 可插拔、引用可追溯、权限可靠」的向量 RAG，不是裸向量。我在同一评测集上比索引 Token、索引耗时、存储、查询 P95 和答案质量，检索层看实体、关系召回率与社区一致性，生成层看 Faithfulness、Answer Relevance、Context Precision，业务层看采纳率、转人工率、引用点击率；只有目标关系型问题显著改善且不拖垮简单问题，才判赢。
**追问 2**：试点上了轻量图谱，权限和回滚怎么兜？
**答**：图谱这层权限比向量更难，节点、边、邻居、摘要都可能泄露，所有原始证据要过授权检查才进上下文，二次校验放在组装上下文之前。回滚上我把 `extraction_model_version`、`version_id` 和源文档 ID 记全，关系型 Badcase 没改善就降级回 Vector RAG（入口分类器置信度低时的明确降级路径），涉及泄露则先阻断检索入口再按分区重建受影响社区，别慢慢修索引。
